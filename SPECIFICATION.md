## 1. Цель проекта

**DAR {}** — декларативный предметно-ориентированный язык описания кредитных конвейеров с русским синтаксисом, предназначенный для риск-технологов, бизнес-аналитиков и разработчиков банковского сектора.

### 1.1. Решаемая проблема

В кредитном конвейере три стороны (бизнес, риск, разработка) работают с правилами в разных форматах. При каждом изменении смысл теряется при переводе между форматами, объяснение отказа требует ручного разбора, тестирование отделено от описания правил.

### 1.2. Решение

Один декларативный файл `.dar`, который одновременно является:
- **Требованием** (читается бизнесом)
- **Исполняемым кодом** (выполняется движком)
- **Тестом** (содержит сценарии проверки)
- **Документацией** (принцип code=doc)
- **Источником объяснений** (для аудита и клиентов)

### 1.3. Ключевые принципы

| Принцип | Что означает |
|---------|-------------|
| **code = doc** | Код `.dar` сам является документацией. Отдельные документы не нужны |
| **file-first** | Файл на диске — источник истины. Базы данных, облака — вторичны |
| **русский синтаксис** | Ключевые слова на русском: `Правило`, `Если`, `Решение` (канон — `GRAMMAR.md`) |
| **объяснимость** | Каждое решение содержит причину, правило, условие, факт |
| **версионируемость** | Каждое правило имеет semver-версию, публикуется в git |
| **не заменяет, а дополняет** | Пользователь всегда может открыть файл в любом редакторе |

### 2.2. Роли компонентов

| Компонент | Роль | Тип | Где работает |
|-----------|------|-----|-------------|
| **dar-core** | Ядро языка: парсер, интерпретатор, диагностика, автодополнение, объяснитель | Библиотека (Rust) | Везде |
| **dar-notebook** | UI: редактор, исполнение, git, агент | Приложение (Tauri 2) | Локально у сотрудника |
| **lsp-dar** | Language Server Protocol для любых клиентов | Бинарник (Rust) | Локально (sidecar / IDE) |
| **credo-server** | MCP-сервер + REST API + git-публикация | Сервис (Rust) | На сервере |

### 2.3. Протоколы взаимодействия

```
┌──────────────────┐         ┌──────────────────┐

     │                      │                    │  POST /evaluate  │
     │                      │                    │◄─────────────────│
     │                      │                    │  ❌ Отказ +      │
     │                      │                    │  объяснение      │
     │                      │                    │─────────────────►│
```

Черновик — производное состояние (Q12): он создаётся из `rules/*.dar` или
агентом с нуля; источник истины — `.dar`-файл, при расхождении выигрывает
файл (черновик помечается `stale`). У каждого опубликованного артефакта есть
исходник: черновик без файла при публикации сначала сохраняется в
`rules/{name}.dar`.

Шаг слияния ветки в `main` — отдельный и явный (Q15): `credo merge {name} {version}`.
До слияния опубликованная версия не видна потребителям (`evaluate`, манифест, UI).
Ветка обязана быть потомком `main`; если нет — отказ без авто-ребейза с
предложением перепубликовать. Иначе `refs/heads/main` обновляется атомарно
(`git update-ref` с CAS-проверкой ожидаемого sha), после чего ветка
`publish/{name}-{version}` удаляется. Кнопка «Смержить» в UI и MCP-инструмент
`check.merge` — в планах; команда проектируется как их будущая реализация.

## 8. План реализации

> **Q1 (решено):** план реализуется как эволюция `credo2`, а не с нуля.
> Фазы 1 и 4 частично закрыты прототипом: ядро (`core.rs`) и сервер
> (`mcp.rs`/`rest.rs`) уже существуют в минимальном виде — их нужно
> перенести в целевые крейты и довести до требований фич (объём зависит от
> решений Q3/Q4). Остальные фазы — новые.
>
> **Q3 (решено 2026-09-24):** парсер MVP — regex-минимум (`core::parse_rule`),
> язык v0.1 канонизирован в `GRAMMAR.md`. Лексер+AST — Фаза 1.x после MVP
> (v0.2); LSP строится поверх публичного API `parse_rule` без ожидания AST
> (стратегия «толстый парсер, тонкий интерфейс», GRAMMAR.md §3).
>
> **Q4 (решено 2026-09-24):** `Приоритет` вне MVP — не входит в язык v0.1;
> вернётся в v0.2 вместе с конвейерами (Q36).
>
> **Q38 (решено 2026-09-24):** LSP — в MVP: diagnostics + completion +
> hover + symbols + semanticTokens (Фаза 2 обязательна для демо);
> formatting/definition/references — v0.2. Состав — §3.3.
>
> **Q40 (решено 2026-09-24):** `.feature` — документация, не исполняемая
> спецификация: cucumber-rs внедряется в v0.2 (для backend-сценариев) после
> стабилизации языка и API; DoD фазы — `cargo test` + ручной прогон UI (§9).

## 11. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Правило** | Атомарная проверка: условие → действие |
| **Конвейер** | Упорядоченный набор правил, скорингов, таблиц |
| **Черновик** | Непубликованная версия правила в песочнице |
| **Публикация** | Фиксация правила в git с semver-версией |
| **Объяснение** | Структура (Q42): `rule_name`, `condition`, `actual_value`, `matched`, `decision`, `reason`; ключи латиницей, тексты решений/причин русские |
| **Прогон** | Исполнение конвейера на исторических данных |
| **code=doc** | Принцип: код является документацией |
| **file-first** | Файл на диске — источник истины |
| **sidecar** | Побочный процесс, управляемый основным приложением |
| **LSP** | Language Server Protocol — протокол для IDE |
| **MCP** | Model Context Protocol — протокол для AI-агентов |
