## P1

### P1-1. `field_line` не срезает ведущий пробел — парность Q↔D ложная

`tests/docs_journal.rs:109-113` возвращает значение поля **вместе с ведущим
пробелом** (маркер `- **Статус:**`, значение ` resolved by …`).
`questions_have_decision_or_exception` (`:347-356`) сравнивает
`status.starts_with("resolved by")` по необработанной строке.

- Факт: `Q1` (`docs/questions/Q1.md:3`) = `- **Статус:** resolved by [D15](…)`
  → `status` = `" resolved by …"` (ведущий пробел) → `starts_with` = false.
- Ожидание (D64 п.2): `resolved by` с существующим `D` — валидная пара.
- Фактическое: паника `Q1: статус « resolved by …» не подкреплён` (`:353`).
- Следствие: проверка красная не из-за канона, а из-за разбора; красной была бы
  на **любом** Q с непустым статусом (`open` тоже начинается с пробела).
- Правка: триммить значение в `field_line` (или в потребителях) перед
  `starts_with`; канон не трогать.

### P1-2. `cell_task_statuses` не понимает ID `T-XX` (дефис) — полнота задач и жизненный цикл ложные

`tests/docs_journal.rs:206-234`: парсер ждёт `T` + цифры сразу (`if chars[i] == 'T'`,
затем `while is_ascii_digit()`), но ID задач в журнале — `T-XX` (дефис после `T`).
`T-16` в `:211-216` отбрасывается (`j = i+1`, `j > i+1` ложно).

- Факт: строка `TRACEABILITY` `[T-16](…) ⬜, [T-08](…) ⬜, [T-01](…) ✅`
  (`docs/TRACEABILITY.md:16`) → разбор даёт **пустое** множество задач.
- Ожидание: `T-01` = `✅`, `T-16`/`T-08` = `⬜`.
- Фактическое:
  - `traceability_tasks_exist_and_match_registry` — `T-01 (✅) не видна ни в
    одной строке TRACEABILITY (D77)` (`:581`);
  - `traceability_lifecycle_matches_task_openness` — `Q1: in work требует
    открытую задачу (⬜/🚧), а её нет` (`:535`).
- Следствие: проверки (5)/(6) не проверяют заявленное (D77), а падают на разборе.
- Правка: обрабатывать опциональный `-` после `T` (как в `find_refs:126-128`).
  Дополнительно: окно `.take(4)` (`:220`) меньше расстояния до статуса после
  markdown-ссылки — расширить/искать статус по всей ячейке.

### P1-3. `section()` ловит inline-упоминание `## Сверка с кодом` — вердикт D64 ложный

`tests/docs_journal.rs:146-152`: `text.find("## Сверка с кодом")` ищет подстроку
где угодно, не строку-заголовок. В `docs/decisions/D64-journal-integrity-test.md`
заголовок — `:88`, но `:83` (нота «Обновление 02.10.2026», добавленная T-18)
содержит **inline** `` `## Сверка с кодом` ``. `find` берёт `:83`, следующий
`\n## ` — уже `:88`, и секция обрезается до «хвоста» строки 83 без `Вердикт:`.

- Факт: `every_decision_has_code_review_verdict` (`:472`) —
  `D64: в «Сверке с кодом» нет строки «Вердикт:»`.
- Ожидание (D64 п.4): секция `## Сверка с кодом` D64 (`:88-111`) содержит
  `Вердикт: ⬜ **не реализовано**` (`:90`).
- Фактическое: паника на D64; остальные D прошли.
- Следствие: проверка (4) красная из-за разбора, а не канона.
- Правка: искать заголовок только в начале строки (`\n## Сверка с кодом`) —
  как уже сделано в `live_text:672`. Нота D64:83 — валидная (журнал допускает
  «Обновление»); канон не трогать.

### P1-4. `feature_tokens`/`feature_registry` не нормализуют префикс `features/` — полнота фич ложная

`tests/docs_journal.rs:237-249` (token) и `:285-297` (registry) берут токен
целиком. `features/README.md` перечисляет фичи **bare** (`testing.feature`,
`:198`), а `TRACEABILITY.md:44` называет её `features/testing.feature`.

- Факт: `features_are_named_in_traceability_and_exist` (`:613`) —
  `features/README: testing.feature не упомянута поимённо в TRACEABILITY (D80)`.
- Ожидание (D80): фича поимённо видна в колонке «Реализация».
- Фактическое: `named` = `features/testing.feature`, registry =
  `testing.feature` → встречная проверка `:622-626` также упала бы.
- Следствие: проверка (7) красная из-за несогласованной нормализации; при этом
  все прочие строки TRACEABILITY называют фичи bare (напр. `:16`).
- Правка: нормализовать обе стороны — срезать префикс `features/` (и/или
  `docs/features/`) перед сравнением; канон-строку можно не трогать.
