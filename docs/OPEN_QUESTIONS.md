# Открытые вопросы: `SPECIFICATION.md` ↔ `features/`

Документ фиксирует расхождения между `SPECIFICATION.md` (целевая архитектура)
и `features/*.feature` + `features/README.md` (требования), а также с текущим
кодом `credo2`. Цель — до начала разработки принять решения, чтобы каждая
формулировка жила в одном месте и в одном виде.

**Как пользоваться.** Для каждого вопроса впишите ответ в блок «Решение»
(кто и когда). После решения обновите документы из поля «Обновить».
Нумерация сквозная и не зависит от порядка разделов: Q42 добавлен позже
остальных.

> **Миграция (с 2026-09-26).** Архив разбирается на отдельные записи журнала:
> вопрос → `questions/Qn.md`, решение → `decisions/Dn-<слаг>.md` (правила —
> [`BRIEF.md`](BRIEF.md), прогресс — [`TRACEABILITY.md`](TRACEABILITY.md)).
> Перенесённый вопрос заменяется здесь коротким указателем; полный текст —
> только в файле журнала.

Легенда приоритета:

- 🔴 **Блокер** — без ответа нельзя начинать соответствующую разработку.
- 🟡 **Важно** — можно начать, но решение нужно до конца MVP.
- ⚪ **Оформление** — не влияет на код, чинит противоречие в документации.
- ✅ **Решено** — вопрос закрыт, решение зафиксировано в блоке «Решение»,
  документы из поля «Обновить» синхронизированы.

### Q37. ✅ Реестр полей и типов для автодополнения (решено 2026-09-26)

- **Расхождение:** `lsp.feature` требует подсказки `Клиент.Возраст`,
  `Клиент.Доход` с типом поля; откуда берутся схемы — ни SPEC, ни фичи не
  говорят. Каталог `tables/` упомянут, но формат не определён.
- **Вопрос:** источник схемы полей для completion/hover: файл `tables/`,
  контракт опубликованных проверок, конфиг workspace?
- **Рекомендация:** для MVP — не подсказывать поля (только ключевые
  слова), иначе вводить `tables/` с форматом.
- **Обновить:** `lsp.feature`, `SPECIFICATION.md` §4.3.
- **✅ Решение (2026-09-26):**
  1. **Архитектурный источник схемы полей и словарей — БД**
     (пользовательские и системные таблицы). В MVP БД = `HashMap`, явной
     схемы нет. Векторная БД — отложена (после MVP).
  2. **Каталог `tables/` — рудимент, полностью исключается:** данные
     приходят из БД, а не из `.dar`-файлов таблиц. Убран из
     `SPECIFICATION.md` §4.3, `notebook_ui.feature`, `lsp.feature`;
     синтаксис таблиц в `GRAMMAR.md` не вводится.
  3. **Автодополнение MVP — два источника:**
     - ключевые слова языка: `Правило`, `Если`, `Решение`, `Причина`
       (статический список из `GRAMMAR.md`);
     - эвристика по открытым файлам: все слова с точкой (например,
       `Клиент.Возраст`), встреченные в тексте.
  4. **Типы полей в MVP не подсказываются** (явной схемы нет). Целевая
     траектория — строгая статическая типизация; схема колонок будет
     браться из БД (Q9: в MVP типы проверяются на исполнении).
  5. **Словарь решений** для автодополнения `Решение = `:
     - источник — системная таблица решений банка в БД (пользователь
       расширяет свободно, набор не ограничен);
     - в MVP — демо-конфиг, имитирующий системную таблицу решений,
       заполненную пользователем банка (включая нестандартные решения из
       реальной практики, не только «Одобрить/Отказать»);
     - фиксированный набор в коде ядра не хардкодится.
  6. **Векторная БД — отложена (после MVP).** Абстракция источника данных
     (trait) не закладывается сейчас; `evaluate_rule` работает с
     `HashMap` напрямую. Переход на БД — отдельная задача.
  - **Следствие для кода:** правок не требуется (автодополнение — задача
    LSP/`lsp-dar`, Фаза 2; каталог `tables/` в коде не используется).
  - **Обновлено:** `features/lsp.feature` (источники автодополнения,
    без типов полей, словарь решений — демо-конфиг),
    `features/notebook_ui.feature` (без `tables/`),
    `features/README.md` (заметки, строки), `SPECIFICATION.md` §4.3 и §10
    (решение №33), `DECISIONS.md` (ADR-002: БД как источник данных).

  поверх API `parse_rule` (Фаза 2). Вне MVP → v0.2: formatting, definition,

  `lsp_notebook.feature`, `features/README.md` (строка и счётчики).
- **✅ Решение (2026-09-26):** принимается рекомендация с уточнениями.

  1. **«Нет fallback» — нет второго движка.** При недоступности
     sidecar функции LSP (диагностика, автодополнение, семантическая
     подсветка) недоступны; редактор работает как обычный текстовый.
     Встроенной в UI альтернативы нет: `dar-core` доступен только через
     LSP (согласуется с Q33 — локального исполнения в UI нет).
  2. **Восстанавливается серверная сессия, а не «состояние» файлов.**
     Буферы, курсор, скролл и undo — клиентские (CodeMirror), падение
     sidecar их не теряет. После перезапуска клиент выполняет
     `initialize` и повторный `didOpen` по всем открытым документам с
     текущим текстом (включая несохранённые правки); сервер заново
     публикует диагностику.
  3. **Ограничение автоперезапуска.** Автопопытки подряд ограничены
     (канон — три); после их исчерпания автоперезапуск прекращается,
     пользователь видит уведомление «Сервер языка недоступен» и может
     перезапустить сервер вручную. Бесконечный цикл падений исключён.
  4. **Деградация не блокирует работу.** Во время недоступности LSP
     редактирование и сохранение продолжаются, буферы и несохранённые
     правки сохраняются; выполнение правила (`check.test` через MCP,
     Q33) от LSP не зависит.

  - Следствие для кода: `lsp-dar` и Notebook не реализованы (Фаза 2–3,
    Q38), правок кода нет. Фича: сценарий «Перезапуск LSP при падении»
    уточнён, добавлены 2 поведенческих сценария (деградация без LSP;
    повторные падения → ручной перезапуск), 6 → 8 сценариев.
    `SPECIFICATION.md` §10 п. 6 переформулирован.
