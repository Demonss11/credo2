## Контекст

Три описания одного ответа не совпадали: `rest_api.feature` —
`count`/`service_hash`/`checks` (`ManifestEntry`:
`name`/`active`/`supported`/`deprecated`); `dashboard.feature` — «три записи
со статусами активна/deprecated»; `evaluate.feature` —
`name`/`kind`/`versions`/`latest`. Было неясно, какая схема нормативна и
нужно ли поле `kind`.

## Вопрос

Одна схема ответа `GET /checks` — какая? Входит ли `kind` в манифест?

## Варианты

- (а) манифест как есть — `{schema_version, count, service_hash, checks[]}`
  с `ManifestEntry = name/active/supported/deprecated` (как в коде);
- (б) добавить `kind` в `ManifestEntry`;
- (в) облегчённый список `name`/`kind`/`versions`/`latest` (как в раннем
  `evaluate.feature`).

## Рекомендация

Канон — `ManifestEntry` из кода; `kind` добавить, только если он нужен
публикации (сейчас есть только в фичах).

## Итог

**Решение (2026-09-25):** канон схемы `GET /checks` — манифест как есть,
ответ идентичен `manifest.json` в `main` (один источник истины):
`{ "schema_version": 1, "count", "service_hash", "checks": [ManifestEntry] }`.
`ManifestEntry` — `name: string`, `active: string` (максимальная
не-deprecated версия; пустая строка, если все версии deprecated — конвенция
«нет значения = пустая строка»; обращение к active-эндпоинту в этом
состоянии — 409), `supported: string[]` (все не-deprecated по убыванию,
включая `active`), `deprecated: string[]`. Поле `kind` в манифест **не**
вводится (YAGNI, v0.2); отдельный `GET /checks/{name}` в MVP не нужен.

Полный контекст решения, следствия, сверка с кодом и отклонённые
альтернативы — в [D23](../decisions/D23-get-checks-manifest.md); краткий
канон — `SPECIFICATION.md` §10, решение №23.
