## Контекст

При приёмке документных пакетов переноса журнала `validator` выполнял
cargo-прогоны (`cargo fmt --check`, `cargo test --test features_inventory`),
хотя `src/**`/`tests/**` не менялись. Это лишний расход шагов и токенов роли
(бюджет `steps` — [D44](../decisions/D44-run5-refinements.md)).

При этом действующие тексты канона расходятся:

- [`review.md`](../../.opencode/rules/review.md) §«Порог существенности»:
  механические docs-правки → **адресная** проверка изменённых файлов, cargo не
  упомянут;
- [`validator.md`](../../.opencode/agents/validator.md), чек-лист «Документы и
  агенты»: «счётчики `docs/features/README.md` согласованы **с тестом**
  `features_inventory`» — читается как требование cargo-прогона;
- `BRIEF.md` §5.7: «DoD прототипа зелёный: `cargo fmt --check`,
  `cargo clippy …`, `cargo test --all`» — без оговорки про docs-пакеты.

## Вопрос

Обязателен ли `cargo`-прогон у `validator` для пакетов без изменений
`src/**`/`tests/**`?

## Варианты

- (а) **оставить как есть** — cargo-прогоны на docs-пакетах; просто, но
  расходует бюджет роли без пользы (код не менялся, регрессий быть не может);
- (б) **полностью без cargo при отсутствии изменений `src/**`/`tests/**`** —
  адресная проверка документов; но при реальных правках счётчиков
  `docs/features/**` машинная сверка не выполнится, и рассинхрон с
  `tests/features_inventory.rs` не поймается;
- (в) **без cargo, исключение — правки счётчиков/состава сценариев
  `docs/features/**`** → адресный `cargo test --test features_inventory` —
  cargo запускается только там, где он действительно проверяет артефакт.

## Рекомендация

Вариант (в): убирает лишний прогон на «чистых» docs-пакетах, но сохраняет
машинную проверку там, где требования-сводка (`docs/features/README.md`)
реально меняется и её согласованность с тестом
[`tests/features_inventory.rs`](../../tests/features_inventory.rs) обязана быть
подтверждена.
