## Контекст

[`SPECIFICATION.md`](../SPECIFICATION.md) §9 формулировал критерий готовности:
«Все сценарии из соответствующих `.feature` файлов проходят». При этом не было
ни маппинга сценариев на тесты, ни раннера (Cucumber и т. п.), а
[`testing.feature`](../features/testing.feature) перечисляет только Rust-тесты.
Проверить такой DoD было невозможно — формулировка требовала исполнения
Gherkin-сценариев, которых никто не исполнял.

## Вопрос

Фичи — исполняемая спецификация (cucumber-rs) или документация, а DoD =
`cargo test`?

## Варианты

- (а) сделать `.feature` исполняемой спецификацией: подключить cucumber-rs и
  раннер уже в MVP;
- (б) считать `.feature` документацией (требования и чек-листы), а DoD привязать
  к конкретным Rust-тестам; cucumber ввести при переходе к целевому состоянию.

## Рекомендация

В MVP — документация, DoD привязать к конкретным Rust-тестам; ввести cucumber —
при переходе к целевому состоянию.

**Обновить:** [`SPECIFICATION.md`](../SPECIFICATION.md) §9,
[`testing.feature`](../features/testing.feature),
[`ci.yml`](../../.github/workflows/ci.yml).

## Итог

**Решение (2026-09-24):** в MVP `.feature` — **документация** (требования и
чек-листы), не исполняемая спецификация.

- **DoD SPEC §9:** `cargo fmt --check` + `cargo clippy -- -D warnings` +
  `cargo test --all` плюс ручной прогон UI-сценариев.
- **Проверяемость инвентаризации** даёт тест
  [`tests/features_inventory.rs`](../../tests/features_inventory.rs): структура
  фич, полнота перечня, счётчики и итоги README (согласуется с Q5/D19 —
  единственный канон чисел в `features/README.md`).
- **Cucumber-rs** — v0.2, после стабилизации языка и API, только для
  backend-сценариев; UI-сценарии остаются ручными.

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D20](../decisions/D20-features-docs-dod.md); краткий канон —
`SPECIFICATION.md` §10, решение №20.
