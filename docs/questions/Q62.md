## Контекст

Соседний проект применяет композит doc-проверок (`markdownlint-cli2`, лимит
строк, `cspell`, `markdown-link-check`; порядок «быстрые раньше») как единый
`npm run check`. У нас проверка ссылок — вручную
(`BRIEF.md` §7, историч.), а link-check запланирован в Rust-тесте
`tests/docs_journal.rs` ([T-18](../tasks/T-18-docs-journal-test/README.md),
[D64](../decisions/D64-journal-integrity-test.md)) — то есть один владелец уже
назначен. Node-инфраструктура в `.opencode/` есть (`npm ci`, `clean-logs.mjs`,
`agents-perms.mjs`). Опыт 29.09.2026: ссылочная гниль и ручное сжатие
документов (BRIEF 395→304 строки). Обзор-основание —
[`docs/research/doc-quality-checks-2026-09-29.md`](../research/doc-quality-checks-2026-09-29.md).

## Вопрос

Какие doc-проверки заводим, где они живут и как включаются?

## Варианты

- (а) `size` + `markdownlint` (узкий ruleset) — Node-скрипты в
  `.opencode/scripts/`; link-check — **единый владелец** [T-18](../tasks/T-18-docs-journal-test/README.md)
  (Rust, v0.2); композит «быстрые раньше»; гейт: сначала локально
  (роли/сервисная сессия), затем отдельный CI-job `docs`;
- (б) полный Node-набор, включая links (тогда link-check уходит из T-18);
- (в) только `size`;
- (г) не брать.

## Рекомендация

Вариант (а), поэтапно: пилот в temp → локально → CI (обзор, разделы
«Архитектура внедрения» и «Пилот»).
