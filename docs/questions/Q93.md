## Контекст

Целевая модель процесса (записка §7) требует, чтобы **метрики прогона
и очереди выводились из состояния**, а не собирались вручную. Сейчас это не так:

- метрики прогонов (dispatch по ролям, шаги и упоры по сессиям, re-plan по
  категориям, `outcome`) собирались **вручную** — таблицы меморандума W8 §3,
  §9–§11 (записка §2, §7); ручной труд упомянут как текущее состояние и в
  записке §7, и в фиче
  [`agents-metrics.feature`](../features/agents-metrics.feature);
- чек-лист готовности к MCP §8 («метрики прогона выводятся из состояния
  без ручного труда») — незакрытый пункт, без которого заморозка (фаза D) не
  формальна;
- есть скрипт `metrics-report.mjs` (B0-own P4) — но это **нативные** метрики
  сессий (`stats`/`export` OpenCode: стоимость/токены/цепочки), а не слой
  метрик **процесса** из `progress.yaml`/`receipts.yaml`/`state`;
- состояние уже структурировано: [D86](../decisions/D86-state-schema.md) закрепил схему
  (`session_index`, `replan_reason`, `owner_response`, `outcome` и др.),
  [D91](../decisions/D91-c2-validate-state.md) — валидатор; но **читателя** (query-слой) из
  состояния нет.

Требуется решение о **носителе** вывода метрик и очередей: новый скрипт,
расширение существующего `metrics-report.mjs` или сохранение ручной сборки.
Форма (CLI + `--json`) и место в каноне — часть того же решения.

## Вопрос

Каким носителем выводятся метрики прогона и очереди из состояния (новый скрипт
`state-metrics.mjs` · расширение `metrics-report.mjs` · ручная сборка), в каком
формате (CLI-вывод + `--json`) и как это отражается в каноне, без дублирования
таблиц?

## Варианты

- **(A) Новый скрипт `state-metrics.mjs`; CLI + `--json`.** Отдельный query-слой
  из состояния (`progress.yaml`, `receipts.yaml`, `current_state.yaml`,
  `next_action.yaml`): секции прогона, dispatch, re-plan/конвергенции, очередей,
  квитанций. В каноне (`dispatch-loop.md`, `AGENTS.md`) — ссылка «метрики —
  скриптом», без таблиц. Нативные метрики сессий остаются у `metrics-report.mjs`.
- **(B) Расширить `metrics-report.mjs`.** Добавить в него чтение состояния и
  процессные секции рядом с нативными `stats`/`export`.
- **(C) Оставить ручную сборку.** Таблицы собираются вручную по текстам
  меморандума; пункт §8 остаётся незакрытым.

## Рекомендация

Вариант **(A)** — принят владельцем 03.10.2026 (сервисная операция r18):
**новый скрипт** `.opencode/scripts/state-metrics.mjs` — метрики и очереди из
**состояния**; формат — **CLI-вывод + `--json`**; в каноне
(`dispatch-loop.md`/`AGENTS.md`) — **ссылка** «метрики выводятся скриптом», без
дублирования таблиц. Отклонены: (B) — смешивает два слоя (нативные сессионные
метрики `stats`/`export` и метрики процесса из состояния), разные источники и
потребители; (C) — не закрывает чек-лист §8 и сохраняет ручной труд.
Оформлено [D96](../decisions/D96-state-metrics.md).
