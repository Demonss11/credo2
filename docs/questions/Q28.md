## Контекст

`draft.feature` описывала вход `check.create` как `name`, `text`,
`expected_kind`; ответ `check.list_drafts` — с размером в байтах и форматом
`"text"`. Код ([`src/mcp.rs`](../../src/mcp.rs)) принимал только `source`, хранил
распарсенное правило и отдавал `sandbox_file`. Фича
`agent_minimal.feature` полагалась на результат («Черновик создан»), но
параметров не показывала. Контракт входа главного инструмента агента был не
зафиксирован.

## Вопрос

Каков канонический контракт `check.create` для MVP?

## Варианты

- (а) один вызов — `source: string` (как в коде), `expected_kind`/`name` убрать
  из MVP; переписать `draft.feature`;
- (б) оставить архивную форму `{name, text, expected_kind}`;
- (в) `{name, source}` — имя передаётся явно и сверяется с заголовком
  `Правило {name}`.

## Рекомендация

Один вызов — `source: string` (как в коде), `expected_kind`/`name` убрать из
MVP; переписать `draft.feature`.

## Итог

**Решение (2026-09-26):** контракт `check.create` для MVP — `{name, source}`
(оба обязательны); имя — из заголовка `Правило {name}` (`GRAMMAR.md`);
повторный вызов перезаписывает черновик; ответ `{status: "ok", name}`;
`expected_kind`/`contract` не используются.

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D31](../decisions/D31-check-create-contract.md); краткий канон —
[`SPECIFICATION.md`](../SPECIFICATION.md) §10, решение №31, схемы — §4.5.
