## Контекст

SPEC §1.3/§4.3 объявляет «файл на диске — источник истины» (`rules/*.dar`), но
жизненный цикл §7 начинается с MCP-черновика в `.credo/sandbox.json`, а
публикация пишет `rule.json`/`contract.json`/`meta.json` в bare-репозиторий;
`.dar`-файлы в этом цикле не участвуют вовсе. Три представления одного правила
(файл workspace, черновик, опубликованный артефакт) не имели единого потока и
правила разрешения расхождений.

## Вопрос

Как связаны файлы workspace, черновики и опубликованные артефакты? Что
происходит при расхождении?

## Варианты

- (а) `.dar` — истина, черновик/публикация — производные;
- (б) песочница — истина для черновиков, `.dar` — только UI-представление;
- (в) два независимых контура в MVP.

## Рекомендация

Определить один направленный поток (`файл → черновик → публикация`) и запретить
обход.

## Итог

**Решение (2026-09-25):** источник истины — `.dar`-файл рабочего контура
(`rules/`, под git). `.credo/sandbox.json` — только черновик: производный
от файла или созданный агентом с нуля; временное состояние, которое можно
удалить/пересоздать без потери данных; черновики не участвуют в REST
`evaluate`. Поток строго направленный:
`rules/*.dar → черновик → артефакт публикации`.

- Обход потока запрещён: нельзя опубликовать то, чего нет в песочнице/файле;
  `evaluate` читает только опубликованное.
- При расхождении (файл изменён вручную, черновик устарел) выигрывает файл;
  черновик помечается `stale` при первой операции над ним (сверка
  `source_hash` исходного `.dar`).
- Черновик без привязанного `.dar`-файла при публикации обязан сначала
  сохранить текст в `rules/{name}.dar` — сохраняется инвариант «у каждого
  опубликованного артефакта есть исходник».
- Точное хранение опубликованных правил для `evaluate` в MVP —
  `HashMap`/`Vec` в памяти; будущая векторная БД — только производный
  поисковый индекс, не источник истины для исполнения.
