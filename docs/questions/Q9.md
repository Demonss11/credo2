## Контекст

`errors.feature` требует ошибку «Несовместимые типы» при
`Клиент.Возраст < "двадцать"`; `evaluate_rule` молча возвращал
`matched = false`. `SPECIFICATION.md` §10 п. 13: `f64` в MVP, `Decimal` в v0.2;
`rust_decimal` указан в §3.1 как зависимость.

## Вопрос

Проверяем типы на этапе парсинга или исполнения? Что с `==` для `f64` — точное
равенство или эпсилон?

## Варианты

- (а) проверка типов на этапе парсинга (статическая типизация) — плановая v0.2;
- (б) проверка типов на исполнении, при несовпадении — ошибка.

## Рекомендация

Ошибка типов — в MVP; для `==` зафиксировать допуск либо запретить `==` для
чисел вне целых.

**Обновить:** `core.rs`, `errors.feature`, `SPECIFICATION.md` §10.

## Итог

**Решение (2026-09-24):** строгая статическая типизация — плановая (v0.2), это
не вопрос MVP. В MVP принято «как в рекомендации»: проверка типов **на
исполнении**.

- `core.rs`: сравнение значений разных типов → `EvalError::TypeMismatch`
  («Несовместимые типы: поле … имеет тип …, ожидался …»); строки поддерживают
  только `==`/`!=`, `<`/`>` для строк — та же ошибка типов.
- Равенство `f64` (`==`/`!=`) остаётся точным; эпсилон не вводится (риски ложных
  срабатываний выше). Переход на `Decimal` снимет вопрос в v0.2
  (SPEC §10 п. 13).
- Замечание: `errors.feature` ожидает ошибку типов на этапе парсера — это
  целевое поведение лексера/AST ([Q3](Q3.md): regex-минимум в MVP ловит ошибку
  на исполнении); сценарий остаётся целевым состоянием v0.2.
- Тест: `core::tests::type_mismatch_is_error_q9`.

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D21](../decisions/D21-core-semantics-v01.md); краткий канон —
`SPECIFICATION.md` §10, решение №21.
