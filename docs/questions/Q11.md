## Контекст

Фичи ожидали русские тексты ошибок («ожидалась }», «Файл пуст», «Неизвестное
поле», «черновик не найден»), а код частично отвечал английским (`not found`,
`missing or invalid x-api-key`, `unknown tool`). При этом машиночитаемые
идентификаторы (имена проверок `name`, коды ошибок, ключи JSON, сегменты путей)
должны оставаться латиницей ради стабильного машинного контракта. Без единого
правила «что по-русски, что латиницей» документы, REST, MCP и клиенты
расходились в языке сообщений.

## Вопрос

Что и на каком языке писать в человекочитаемых сообщениях об ошибках и что —
латиницей; какие именно канонические тексты у статусов REST?

## Варианты

- (а) латиница для всего (англоязычный API) — привычно инструментам, но
  человекочитаемый слой для риск-технолога теряется;
- (б) **машина / человек**: человекочитаемый текст (`message`) — русский,
  машиночитаемое (идентификаторы, коды, ключи JSON, сегменты путей) — латиница;
- (в) русский текст вперемешку с латиницей по месту — кодам и ключам грозит
  дрейф, машинная обработка ломается.

## Рекомендация

(б): русский текст `message` + стабильный `code` в JSON ошибки. Канонические
тексты и статусы зафиксировать в `SPECIFICATION.md` §4.4, пути и ресурсы — по
решению Q20.

## Итог

**Решение (2026-09-25):** принцип «машина / человек» (сквозной для Q11, Q13,
Q42):

- человекочитаемый текст ошибки (`message`) — **русский**;
- машиночитаемое (идентификаторы проверок `name`, коды ошибок, ключи JSON,
  сегменты путей) — **латиница**.

Это согласуется с Q13 (идентификаторы — латиница) и [Q42](Q42.md) (ключи
объяснения — латиница, тексты `decision`/`reason` — русские).

Канонические тексты и статусы (пути и ресурсы — по решению Q20):

```
404  проверка не найдена: {name}
404  версия не найдена: {name}@{version}
     — POST /checks/{name}/versions/{version}/evaluate
410  версия выведена из эксплуатации: {name}@{version}
     — обращение к deprecated-версии
409  активация недоступна: {name}
     — active-эндпоинт при пустом active (все версии deprecated, Q21)
401  ошибка аутентификации: неверный или отсутствующий x-api-key
     — фиксировано решением Q22 (заголовок x-api-key)
```

Статусы 410 (Gone) и 409 (Conflict) зафиксированы 2026-09-25.

Граница с соседними вопросами (чтобы не дублировать решения):

- Q11 = **язык** и сами тексты человекочитаемых сообщений;
- Q23 = **формат/конверт** ошибки в JSON (структура `code`/`message`) — решён
  2026-09-25: `{"error": {"code", "message"}}`;
- Q22 = аутентификация: заголовок и тексты 401.

Ядро (`core.rs`: парсер, semver, `EvalError`), публикация (`lib.rs`) и MCP
(«неизвестный инструмент: {name}») уже соответствуют канону — приведены при
Q8/Q9. Транспорт REST приведён к канону: «проверка не найдена: {name}» (было
«проверка '{name}' не найдена» с кавычками). Исключения канона: служебные и
диагностические сообщения (ошибки git в `lib.rs`, описания в OpenAPI-документе)
остаются техническими.

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D53](../decisions/D53-error-messages-language.md); краткий канон —
`SPECIFICATION.md` §10, решение №53.
