## Контекст

SPEC §7 показывал «git commit+branch» и сразу `POST /evaluate`, без шага merge.
MCP-ответ предлагал ручную команду `git update-ref refs/heads/main ...`.
`deferred.feature` откладывает настоящий PR через GitHub API. UI
(`git_integration.feature`) содержит кнопку «Опубликовать» и «Commit», но
непонятно, к какому репозиторию они применяются.

## Вопрос

Минимальный цикл публикации в MVP: кто переводит ветку в `main` — человек
командой, Notebook или сервер?

## Варианты

- (а) человек командой (`credo merge {name} {version}`) — полуручной цикл;
- (б) Notebook/UI кнопкой «Смержить»;
- (в) сервер автоматически мержит ветку в `main` после `check.publish`.

## Рекомендация

Для MVP — полуручной цикл с одной документированной командой и кнопкой
«Смержить» в UI.

## Итог

**Решение (2026-09-25):** минимальный цикл публикации — двухшаговый:

1. `check.publish` создаёт ветку `publish/{name}-{version}` от `main`;
2. отдельный явный шаг слияния в `main` — команда
   `credo merge {name} {version}`.

Правило становится видимым для `evaluate`, MCP и UI **только после слияния
в `main`**; до этого ветка — заготовка, не доступная потребителям.

- Канон MVP — «человек командой». Кнопка «Смержить» в UI и MCP-инструмент
  `check.merge` — в планах; команда `credo merge` проектируется так, чтобы
  позже её мог вызывать MCP-инструмент без изменения семантики.
- Механика мержа в bare-репозитории: ветка обязана быть потомком `main`
  (`git merge-base --is-ancestor`); если нет — отказ **без авто-ребейза**
  с предложением перепубликовать. Иначе атомарное обновление `main` через
  `git update-ref refs/heads/main <sha-ветки> <ожидаемый-sha-main>`
  (CAS-проверка против параллельных мержей). После успеха ветка
  `publish/{name}-{version}` удаляется; артефакт неизменяемо живёт в `main`.
- Принцип «четырёх глаз» (публикует один, мержит другой) в MVP не
  требуется, но закладывается архитектурно: шаг мержа отделён от шага
  публикации и допускает другого исполнителя.
- Настоящий PR через GitHub API остаётся отложенным (`deferred.feature`).

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D56](../decisions/D56-merge-step.md); краткий канон —
