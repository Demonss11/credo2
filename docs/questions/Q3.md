## Контекст

`credo2::core::parse_rule` — регулярные выражения: одно сравнение, нет
`Приоритет`, нет типизированных ошибок, нет позиций. При этом фичи
`lexer.feature`, `parser.feature`, `execution.feature`, `errors.feature`,
`explain.feature` описывают токены, AST, `Приоритет`, ошибки «Файл пуст» /
«Несовместимые типы» / «ожидалась }», а `features/README.md` называет языковые
фичи «целевым состоянием DAR». Нужно определить, какой парсер обязателен для
MVP.

## Вопрос

Какой парсер обязателен для MVP — regex-минимум или лексер+AST?

## Варианты

- (а) **regex-минимум** (текущий `core::parse_rule`) — парсер MVP без
  отдельного лексера и публичного AST;
- (б) **полноценный лексер + AST** уже в MVP — токены, дерево, типизированные
  ошибки с позициями.

## Рекомендация

Для MVP — regex-минимум, но с явным списком «язык v0.1» в `GRAMMAR.md`;
языковые фичи перевести в раздел «целевое состояние».

## Итог

Принят вариант (а): **regex-минимум** (текущий `core::parse_rule`) — парсер MVP
без отдельного лексера и публичного AST. Язык v0.1 формально зафиксирован в
[`GRAMMAR.md`](../GRAMMAR.md) (EBNF + ограничения). Конфликта с планируемым LSP
нет: принята стратегия «толстый парсер, тонкий интерфейс» — весь доступ к `.dar`
только через `parse_rule()`, внутренние типы (`Rule`/`Condition`/`Action`)
в v0.2 обогащаются позициями и типизированными ошибками без смены публичного
контракта (`GRAMMAR.md` §3). Файлы `lexer.feature`/`parser.feature` остаются
целевым состоянием (v0.2).

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D16](../decisions/D16-dsl-canon-regex-mvp.md); краткий канон —
`SPECIFICATION.md` §10, решение №16.
