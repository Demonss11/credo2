## Контекст

`publish.feature` утверждал, что «в ветке содержится файл „Правило
МинимальныйВозраст 1.0.0“»; `storage_paths.feature` — `checks/{name}/{version}/`
с `rule.json`, `contract.json`, `meta.json`; `publish_rules.feature` — путь
`checks/CreditAgeMin/2.0.0/`; SPEC §10 п. 14 — «одно правило = один файл».
Код писал JSON-тройку. Все формулировки расходились между собой.

## Вопрос

Канонический артефакт публикации — JSON или `.dar`-текст? Если JSON — то где
лежит исходный `.dar`?

## Варианты

- (а) оставить JSON-тройку (как в коде) и переписать `publish.feature`;
  «один файл» уточнить как «один check = один каталог версии»;
- (б) публиковать `.dar`-текст (сохранить «один файл» буквально);
- (в) JSON-тройка + исходный `source.dar` в каталоге версии — отложено в v0.2.

## Рекомендация

(а): оставить JSON-тройку (как в коде), переписать `publish.feature`, «один
файл» уточнить как «один check = один каталог версии».

## Итог

**Решение (2026-09-25):** публикация — неизменяемый скомпилированный
артефакт, а не исходный DSL-текст. Каталог `checks/{name}/{version}/`
содержит три файла:

- `rule.json` — исполняемое представление правила (AST или иной
  машинно-читаемый формат);
- `contract.json` — контракт проверки: входные поля с типами и формат
  результата;
- `meta.json` — метаданные издания: `name`, `version`, `display_name`,
  `published_at`, `published_by`, `checksum`, `source_hash`,
  `compiler_version`.

- Исходный `.dar` остаётся источником истины в рабочем контуре; в v0.1 в
  реестр публикаций не попадает. Добавление `source.dar` в каталог версии —
  v0.2; связь артефакта с исходником обеспечивает `source_hash`.
- `name` — машиночитаемый латинский идентификатор (например, `CreditAgeMin`);
  человекочитаемое имя — `display_name` в `meta.json`.
- Каталог версии неизменяем: изменение правила требует новой версии.
  Формулировка «одно правило = один файл» устарела; канон — «один check =
  один каталог версии».
