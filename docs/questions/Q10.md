## Контекст

`contract_from_rule` добавлял решение `"Pass"`; `lsp.feature` предлагает
«Отказ», «Одобрено», «РучноеРассмотрение»; `client_explanation.feature` —
«Заявка одобрена»; фичи используют «пусто» (`test_draft.feature`), «решение не
установлено» (`execution.feature`), пустую строку (код).

## Вопрос

Каков канонический набор решений и каким должно быть представление результата
«правило не сработало»?

## Варианты

- (а) зафиксировать enum решений в грамматике + одно представление «нет решения»;
- (б) оставить решения свободными идентификаторами, словарь — на стороне банка.

## Рекомендация

Зафиксировать enum решений в грамматике + одно представление «нет решения»
(`null` в JSON, пустая строка в ядре — как сейчас), убрать `"Pass"` из контракта
или объяснить его.

**Обновить:** `core.rs`, `lsp.feature`, `client_explanation.feature`,
`GRAMMAR.md`.

## Итог

**Решение (2026-09-24):** жёсткого перечня решений в ядре **нет** — словарь
решений определяет банк, в каждом банке он свой. Ядро оперирует решениями как
свободными идентификаторами (`Решение = <Имя>` в
[`GRAMMAR.md`](../GRAMMAR.md) уже так и определено).

- Форму для заполнения словаря заложим при разработке БД/справочников
  (per-bank таблица/HashMap) — вне текущего кода, не блок MVP-ядра.
- `contract_from_rule` больше **не** добавляет `"Pass"`: в контракт попадают
  только решения, реально используемые в правиле.
- «Правило не сработало»: единое представление — пустая строка `decision`/`reason`
  в ядре, `""` в JSON объяснения (сценарии «пусто»/«решение не установлено» в
  фичах трактуются как «пустое значение», код менять не нужно).
- Подсказки LSP (`lsp.feature`) смогут брать словарь из конфигурации банка —
  учтено в плане Q36–Q39 (ожидают переноса).
- Тесты: `contract_decisions_follow_rule_vocabulary_q10`,
  `unmatched_rule_has_empty_decision_q10`.

Полный контекст решения, следствия, сверка с кодом и отклонённые альтернативы —
в [D21](../decisions/D21-core-semantics-v01.md); краткий канон —
`SPECIFICATION.md` §10, решение №21.
