## Контекст

`SPECIFICATION.md` §4.2 фиксировал порт 8080, тогда как код (`src/main.rs`)
использовал `127.0.0.1:8080` по умолчанию и **не поднимал REST**, если не передан
`--rest`/`--addr`. Фичи запуск не описывали. Нужно было снять расхождение
формулировки SPEC и зафиксировать канон запуска.

## Вопрос

Какой канон запуска и адреса REST считать нормативным: поведение кода или
прежнюю формулировку SPEC?

## Варианты

- (а) зафиксировать поведение кода (`src/main.rs`): адрес по умолчанию —
  `127.0.0.1:8080`; REST поднимается только по явному флагу; без флагов —
  «только MCP (stdio)»; приоритет `--no-rest` > `--addr` > `--rest`;
- (б) сохранить прежнюю формулировку SPEC (порт 8080 сам по себе) — она
  расходится с кодом и не описывает флаги и режим «только MCP».

## Рекомендация

Канон — поведение кода; расхождение было только в формулировке SPEC. Порт 8080
зафиксирован вместе с хостом `127.0.0.1` (loopback — безопасное значение по
умолчанию).

## Итог

**Решение (2026-09-25):** канон — поведение кода (`src/main.rs`); расхождение
было только в формулировке SPEC:

- адрес по умолчанию — **`127.0.0.1:8080`**;
- REST поднимается **только по явному флагу**: `--rest` (адрес по умолчанию) или
  `--addr <ADDR>` (включает REST на указанном адресе); без флагов — штатный
  режим «только MCP (stdio)»; приоритет `--no-rest` > `--addr` > `--rest`;
- наружное развёртывание — через `--addr` (например, `--addr 0.0.0.0:8080`);
  отдельного конфига/переменной порта в MVP нет;
- режим «только MCP» согласуется с планируемыми Notebook-сценариями
  ([Q30](Q30.md): локальный stdio-процесс) и является режимом демо по умолчанию;
- следствие для кода: **правок не требуется** — реализация совпадает с принятым
  решением.
