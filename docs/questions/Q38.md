## Контекст

`lsp.feature` требовал formatting, semanticTokens, definition, references,
documentSymbol, hover; `SPECIFICATION.md` §3.3/§5 перечислял только
диагностику, автодополнение и символы, а модули `dar-core` —
`completion.rs`/`explain.rs` без `format`/`tokens`. Неясно было, какое
подмножество LSP обязательно для MVP и где оно реализуется.

## Вопрос

Какое подмножество LSP обязательно для MVP и где оно реализуется?

## Варианты

- (а) MVP — минимальный набор (diagnostics + completion + semantic tokens),
  остальное — в целевом состоянии;
- (б) полный набор LSP в MVP.

## Рекомендация

MVP — diagnostics + completion + semantic tokens; остальное — в целевом
состоянии.

## Итог

**Решение (2026-09-24):** LSP входит в MVP (пользователь подтвердил).
Обязательный состав: initialize/handshake, синхронизация документов
(didOpen/didChange), diagnostics, completion (ключевые слова + значения
решений), hover по правилу, documentSymbol/workspaceSymbols (по одному правилу
в файле — см. [Q36](Q36.md)), semanticTokens. Реализация — крейт `lsp-dar`
поверх API `parse_rule` (Фаза 2). Вне MVP → v0.2: formatting, definition,
references, completion полям из реестра ([Q37](Q37.md)). Сценарии `lsp.feature`
с `Приоритет`, полями и конвейером помечаются как целевое состояние.

- **Следствие для кода:** правок не требуется — LSP-сервер (`lsp-dar`) — Фаза 2,
  вне кода прототипа `credo2`.
- **Обновлено (зона `docs-writer`):** `features/lsp.feature` (пометки целевого
  состояния), `features/README.md` (нота Q36/Q38); `SPECIFICATION.md` §3.3/§5/§8
  и §10 (решение №18 — D-ссылка, 2026-09-29).
