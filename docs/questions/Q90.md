## Контекст

[D89](../decisions/D89-branch-topology-freeze-session-commit.md) P3 принял
**первый инкремент C3** — session-commit: на границе сессии процесс-слой (ленты,
память, `state/**`) фиксируется отдельным коммитом **в текущую рабочую ветку**
(для задачи — `feature/T-XX-<слаг>`; для сервисной операции — `develop`) ролью
`git` по «постоянному» пакету с подтверждением один раз на прогон. Правило
внесено в [`git-workflow.md`](../../.opencode/rules/git-workflow.md)
§«Session-commit».

**Остаток C3** прямо отложен «отдельным решением»
([`git-workflow.md`](../../.opencode/rules/git-workflow.md): остаток
`process/runN`, теги `session/runN-sM`, фасад `/git/checkpoint`): нужен носитель
по-сессионных снапшотов состояния, теги сессий и фасад владельца. Записка
[`mcp-ready-process.md`](../tasks/T-15-mcp-ready-process/mcp-ready-process.md) §6
и фича
[`agents-session-checkpoint.feature`](../features/agents-session-checkpoint.feature)
(4 сценария: чекпойнт в конце сессии, правило останова, восстановление по
снапшоту, идемпотентность) задают предмет. Строки `C3` (остаток) и `C4` (фасады
`/git/checkpoint`, `/git/status`; `.opencode/commands/**` — в область аудита
`auditor`) в карточке [T-15](../tasks/T-15-mcp-ready-process/README.md) — 🚧.

Контекст коллизии: накопительная ветка `process/<прогон>` на общем рабочем
дереве конфликтует с незакоммиченными файлами (`git switch` перезаписал бы
M-файлы); данные F80–F82 (T-16/T-25) — грязное дерево на `branch_start`
([F82](../analysis/findings-registry.md)). Обсуждение ролей 03.10.2026
(сервисная операция r15, лента) вынесло владельцу две развилки: имя прогона и
исполнитель снапшота.

## Вопрос

Как замкнуть C3-остаток и C4: (1) имя прогона для ветки/тега (идентификатор
задачи `T-XX` или глобальный номер `runN`); (2) нужна ли отдельная process-ветка
и какая топология; (3) кто создаёт снапшот состояния; (4) состав фасада
`/git/checkpoint`?

## Варианты

- **(A) process-ветка по имени прогона + теги + снапшот + фасад** — прогон =
  идентификатор задачи (`T-XX`); ветка сессии `process/<прогон>-s<M>` от текущего
  HEAD; тег `session/<прогон>-s<M>`; снапшот
  `.opencode/state/snapshots/<прогон>-s<M>/` создаёт скрипт по вызову фасада;
  `/git/checkpoint` по «постоянному» пакету.
- **(B) Глобальный номер прогона (`runN`)** — сквозная нумерация прогонов вместо
  идентификатора задачи; ветка `process/runN`.
- **(C) Без process-ветки (инкремент 1 + теги)** — оставить session-commit в
  текущей ветке, добавить только теги и фасад, без отдельного носителя
  снапшотов.

## Рекомендация

Вариант **(A)** — принят владельцем 03.10.2026 (сервисная операция r15):
**A + идентификатор задачи**; снапшот — **скрипт по вызову фасада**. Отклонены:
`runN` (вариант B — имя прогона теряет связь с задачей; накопительная ветка
конфликтует с M-файлами) и «без process-ветки» (вариант C — нет носителя
по-сессионных снапшотов/resume, противоречит сценарию «Восстановление по
снапшоту» фичи). Оформлено
[D93](../decisions/D93-session-commit-process-branch.md).
