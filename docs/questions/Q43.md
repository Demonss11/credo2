## Контекст

Пилот T-01 прошёл маршрутом `coder → rust-expert → tester → validator →
docs-writer` и показал, что маршрут работоспособен, но выстроен **водопадом**:
каждая кодовая роль прогоняла полный `cargo test` (4+ прогона на задачу),
тестирование дублировалось, а обрывы сессий теряли работу и отчёты (сессия
`coder` прервана — состояние восстанавливали по `git diff`; push роли `git`
прерван — потребовался повтор). Отдельно выяснилось, что условные подтверждения
(`ask`) в суб-сессиях не срабатывают, а «инструкция ↔ права» ролей расходятся.

Владелец сформулировал целевой цикл (v2) с учётом итогов пилота; ниже — вопрос,
на который этот цикл отвечает, и отклонённые варианты.

## Вопрос

Каким должен быть цикл работы команды агентов: остаётся ли он водопадом, кто
ведёт задачу, сколько ролей запускают тесты и как цикл переживает обрыв сессии?

## Варианты

- (а) **водопад (как в пилоте):** `coder → rust-expert → tester → validator →
  docs-writer → git`; тестовые прогоны у нескольких ролей; `validator` —
  последний шаг, лидером не является;
- (б) **петля с `validator`-лидером:** `validator` одновременно лидер команды,
  единственный тестировщик и приёмщик;
- (в) **петля с отдельным лидером:** задачу ведёт переработанный `lead`,
  тестирует и принимает только `validator` (независимо от лидера), роли
  `coder`/`rust-expert`/`tester` дают компиляционную обратную связь без запуска
  тестов.

## Рекомендация

Вариант (в): Agile-петля с отдельной ролью лидера и независимым `validator`.
Он убирает дублирование тестов, сохраняет независимость приёмки и даёт точку
восстановления после обрыва (память роли, лента задачи, чекпойнты).

## Итог

Принят вариант (в). Ниже — суть; полный контекст решения, следствия,
отклонённые альтернативы и сверка — в [D38](../decisions/D38-agent-cycle.md);
краткий канон — `SPECIFICATION.md` §10, решение №38:

- Agile-петля `coder → rust-expert → tester → validator → docs-writer → git`;
  возврат на доработку — `validator → lead → coder` (повторная проверка `-rN`);
- `tester` добавляет тесты, но не запускает; полный `cargo test --all` и DoD —
  только у `validator`; `cargo check`/`clippy`/`fmt` — у ролей, работающих с
  кодом;
- лидер — переработанный `lead`, маршрут по размеру задачи (S/M/L);
- память роли `.opencode/memory/<роль>.md` и лента задачи
  `.opencode/mail/T-XX.md` — рабочие данные в git, не канон; чекпойнт до/после
  тяжёлых операций; продолжение по `sessionID`;
- правки канона агентов (`AGENTS.md`, `.opencode/**`) вносит сервисная сессия
  владельца по протоколу (журнал → правки → независимый аудит → приёмка →
  коммит); `auditor` (`mode: all`) — независимая приёмка, канон не правит
  *(уточнено 2026-09-26: схема A)*;
- git — пакетное подтверждение (один раз) и идемпотентность, push ≥ 5 минут.
