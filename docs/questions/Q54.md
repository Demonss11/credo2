## Контекст

При приёмке service-t11-closeout (28.09.2026) проверялось утверждение «коммиты
`0a5832f`/`5019c45` влиты в `develop`». Прямой вопрос «входит ли коммит в
ветку» отвечает `git branch --contains <коммит>`, но команда была отклонена
движком прав:
у роли `validator` нет ни одного паттерна `git branch` (`review.md`,
«Доступные команды» — `git status|diff|log|show|grep`). Проверка заменена
косвенной — `git log develop -50` (коммиты видны в истории, но это не
машинное подтверждение вхождения именно в ветку).

Разграничение (уточнение владельца 28.09.2026): смежный отказ у той же роли —
`git diff -- .opencode/...` — **не** пробел прав: право `git diff *` есть,
отказ вызван известным квиком движка для аргумента, начинающегося с точки,
**после** `--` (`review.md` §«Доступные команды»); канон уже предписывает
форму `./…`.
Роль применила правило «сузь и повтори» (префикс `./`) — это норма, отдельного
решения не требует.

## Вопрос

Чем `validator` подтверждает вхождение коммита в историю ветки при приёмке
утверждений о влитых коммитах, если прямой команды в allowlist нет?

## Варианты

- (а) **не менять, обходиться `git log`** — прямой вопрос «входит ли коммит в
  ветку» не проверяется; `git log` подтверждает лишь присутствие коммита в
  показанном диапазоне, не членство в ветке;
- (б) **точечно `git branch --contains *`** — read-only, ровно одна доказанная
  команда под конкретную потребность приёмки (принцип D44 «одна доказанная
  команда», отказ массового расширения allow-листов);
- (в) **расширить весь read-only набор `git branch`** (`-l`, `-a`, `-vv`,
  `--show-current`) — массовое расширение без подтверждённой потребности
  (отклонено в духе D44).

## Рекомендация

Вариант (б): минимальное право закрывает пробел «инструкция ↔ права» —
у приёмки появляется машинный ответ на вопрос о вхождении коммита в ветку,
без расширения остального набора `git branch`.
