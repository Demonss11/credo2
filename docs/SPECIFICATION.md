## 1. Цель проекта

**DAR {}** — декларативный предметно-ориентированный язык описания кредитных конвейеров с русским синтаксисом, предназначенный для риск-технологов, бизнес-аналитиков и разработчиков банковского сектора.

### 1.1. Решаемая проблема

В кредитном конвейере три стороны (бизнес, риск, разработка) работают с
правилами в разных форматах: при переводе между форматами смысл теряется,
объяснение отказа требует ручного разбора, тестирование отделено от описания
правил.

### 1.2. Решение

Один декларативный файл `.dar` одновременно — **требование** (читается
бизнесом), **исполняемый код** (движок), **документация** (принцип code=doc) и
**источник объяснений** (аудит, клиенты). Тесты в `.dar` — целевое состояние,
вне MVP (v0.2): «быстрые прогоны» живут в локальном кэше
`.dar-notebook/results-cache.json` (вне git, `.dar-notebook/` в `.gitignore`) —
[`D32`](decisions/D32-test-gate-mvp.md).

### 1.3. Ключевые принципы

| Принцип | Что означает |
|---------|-------------|
| **code = doc** | Код `.dar` сам является документацией. Отдельные документы не нужны |
| **file-first** | Файл на диске — источник истины. Базы данных, облака — вторичны |
| **русский синтаксис** | Ключевые слова на русском: `Правило`, `Если`, `Решение` (канон — `GRAMMAR.md`) |
| **объяснимость** | Каждое решение содержит причину, правило, условие, факт |
| **версионируемость** | Каждое правило имеет semver-версию, публикуется в git |
| **не заменяет, а дополняет** | Пользователь всегда может открыть файл в любом редакторе |
| **атомарная композиция** («принцип Макдоналдса») | Полный прогон собирается из атомов: `(правило, данные) → Explanation`; сведение решений — слой конвейера (v0.2). См. §1.3.1 |

### 1.3.1. Принцип «Макдоналдс»: композиция из атомов

Зафиксирован решением [`D22`](decisions/D22-rest-paths-canon.md) (вопрос
[`Q20`](questions/Q20.md)); сквозное обоснование — корневой `DECISIONS.md`
(ADR-001).

**Атом** — чистая функция без состояния: одна проверка на одних данных → одно
`Explanation`; атом не знает о других атомах и не сводит решения.
**Конвейер** — набор атомов и правил сборки (порядок, условия, сведение
решений), отдельный ресурс (`/pipelines/{name}/versions/{v}/evaluate`, v0.2),
а не модификация атома. «Конвейер» и pipeline — одно понятие: русский термин —
в документации, латиница — в машинных идентификаторах.

**Критерий принятия решений:** если фича требует «запечь что-то внутрь атома»
(свести решения, узнать о других правилах) — это нарушение принципа; такое
почти всегда относится к слою конвейера.

### 2.2. Роли компонентов

## 4. Модель развёртывания

### 4.1. Локальный компьютер сотрудника

Notebook (Tauri 2): React UI, Rust backend (Tauri IPC, управляет
sidecar-процессами), `lsp-dar` (stdio), git CLI (workspace-репозиторий) и
MCP-клиент, спавнящий `credo-server` (состав — §2.1, §2.2).

MCP-транспорт в MVP: Notebook спавнит `credo-server` как локальный sidecar по
stdio (JSON-RPC 2.0) и запускает автоматически при старте; сервер работает в
режиме «только MCP» (без REST); HTTP+SSE и внешний сервер — вне MVP (v0.2+,
multi-user) — [`D29`](decisions/D29-notebook-mcp-transport.md).

**Исполнение правил из редактора** — единый механизм: кнопка «Выполнить» и
агент вызывают MCP `check.test` на черновике; локального исполнения через Tauri
`dar-core` нет. Кнопка активна только при наличии черновика; сохранение
правила создаёт черновик из буфера (`check.create`, draft-first), файл
`rules/{name}.dar` материализуется при публикации; опубликованная версия
исполняется через `check.run` —
[`D30`](decisions/D30-execution-mechanism.md).

### 4.2. Сервер (общий для команды)

`credo-server`: MCP-сервер (`rmcp`), REST API (`axum`, по умолчанию
`127.0.0.1:8080`), git-публикации, кэш манифеста (`RwLock` + watcher),
`dar-core`. Данные — `.credo/sandbox.json` (черновики) и
`.credo/published-repo/` (bare-git).

**Тест-гейт.** Успешный `check.test` обновляет метки черновика
`last_test_checksum`/`tested_at`; публикация без успешного теста или после
изменения черновика отклоняется — [`D32`](decisions/D32-test-gate-mvp.md).

**Запуск и адрес REST.** Канон — `127.0.0.1:8080`; REST поднимается только по
явному флагу, без флагов сервер работает в режиме «только MCP (stdio)»
(штатный режим Notebook-демо); приоритет `--no-rest` > `--addr` > `--rest`;
для наружного развёртывания адрес задаётся через `--addr` —
[`D27`](decisions/D27-rest-launch-address.md).

**Два git-контура.** Workspace-репозиторий (истина для `rules/*.dar`,
git-панель Notebook) и published-repo (bare, внутренняя деталь `credo-server`,
read-only панель «Версии»); мультиверсионность — ветвление от линии и
bumped-номер — [`D28`](decisions/D28-two-git-contours.md); поток
буфер → файл → опубликованное — §7,
[`D54`](decisions/D54-source-of-truth-flow.md).

### 4.3. Файловая структура

```
consumer-credit/                ← git-репозиторий (workspace)
├── rules/                      ← исходники правил (источник истины)
│   ├── Пример.dar              ← канонический пример (создаётся с workspace)
│   ├── МинимальныйВозраст.dar
│   └── ...
├── README.md                   ← инструкции workspace
├── .credo/                     ← данные credo-server (вне git)
│   ├── sandbox.json            ← черновики
│   └── published-repo/         ← bare-git публикаций
├── .dar-notebook/              ← метаданные Notebook (вне git)
│   ├── layout.json
│   ├── results-cache.json      ← «быстрые прогоны»
│   └── agent-history.json
└── .gitignore                  ← игнорирует .credo/ и .dar-notebook/
```

| Каталог | Владелец | Содержимое | В git? |
|---|---|---|---|
| `rules/*.dar` | пользователь / workspace | исходники правил — источник истины | да |
| `.credo/` | `credo-server` | `sandbox.json` (черновики); `published-repo/` (bare-git публикаций) | нет |
| `.dar-notebook/` | DAR Notebook | `layout.json`; `results-cache.json` («быстрые прогоны»); `agent-history.json` | нет |

Оба служебных каталога живут в корне workspace и не попадают в git; владельцы
разные — серверный (`.credo/`) и клиентский (`.dar-notebook/`) домены; имя
`.credo/` оставлено прототипным, переименование в `.dar/` — пост-MVP —
[`D58`](decisions/D58-workspace-data-dirs.md).

Новый workspace создаёт `rules/`, канонический `Пример.dar` (из `GRAMMAR.md`),
`README.md` (структура, пример, шаги «создать → выполнить → опубликовать») и
`.gitignore`; «Создать правило» создаёт файл с парсящимся шаблоном, имя правила
= имя файла, черновик появляется при сохранении —
[`D59`](decisions/D59-workspace-templates.md).

Каталог `tests/` (`*.тест`, принцип code=doc) и синтаксис таблиц — вне MVP
(v0.2); в MVP тесты — только локальный кэш, готовность к публикации — успешный
`check.test`, а не файл теста ([`D32`](decisions/D32-test-gate-mvp.md)); схема
полей и словари — из БД ([`D33`](decisions/D33-fields-registry-source.md)).

### 4.4. REST API v0.1: состав и схема

Канонические пути — [`D22`](decisions/D22-rest-paths-canon.md); схема
манифеста — [`D23`](decisions/D23-get-checks-manifest.md). MVP-минимум
(YAGNI):

| Метод и путь | Назначение | Статус |
|---|---|---|
| `POST /checks/{name}/versions/{version}/evaluate` | Атомарное исполнение опубликованной версии из `main` | MVP |
| `GET /checks` | Манифест (`manifest.json` из `main` + `count`) | MVP |
| `GET /health`, `GET /version`, `GET /openapi.json` | Инфраструктура (без ключа) | MVP |
| `POST /checks/{name}/evaluate` | Исполнение active-версии | вне MVP-минимума (в прототипе) |
| `GET /checks/{name}/versions`, `.../versions/{version}` | История/детали версий | вне MVP-минимума (в прототипе) |
| batch (Q24), export/import (Q26), `/pipelines/...` (v0.2) | — | отложено |

Эндпоинты вне MVP-минимума не удаляются и не развиваются: их судьба —
решение пост-MVP.

`name` и `version` — параметры пути, не тела; `evaluate` читает только версии,
влитые в `main` (черновики не участвуют); серверной агрегации нет —
оркестрация полного прогона на клиенте (манифест → цикл по `active`-версиям →
цикл атомарных `evaluate`).

**Ошибки.** Все ответы с ненулевым статусом — единый конверт
`{"error": {"code": "<стабильный код>", "message": "<русский текст>"}}`
(`code` — `snake_case`, латиница, стабилен в пределах major-версии API;
`message` — канонический текст; поле `details` в v0.1 не вводится) —
[`D25`](decisions/D25-rest-error-envelope.md),
[`D53`](decisions/D53-error-messages-language.md). Коды: `check_not_found`
(404, нет в манифесте), `version_not_found` (404, нет в `main`),
`version_deprecated` (410), `activation_unavailable` (409, active-эндпоинт при
пустом `active`), `evaluation_failed` (422, ошибка ядра —
[`D21`](decisions/D21-core-semantics-v01.md)), `unauthorized` (401).

**Аутентификация.** Заголовок `x-api-key`; единственный серверный ключ
(`CREDO_API_KEY` или флаг `--api-key`, флаг выше переменной); открытые пути
`/health`, `/docs`, `/openapi.json`; без ключа API открыт (режим демо) —
[`D26`](decisions/D26-rest-auth-x-api-key.md).

### 4.5. Контракты MCP-инструментов v0.1

JSON-контракты MCP — единственный источник истины по взаимодействию агента с
сервером; полные схемы, стабильные коды ошибок и инварианты —
[`D34`](decisions/D34-mcp-tool-contracts.md) (Q29); контракт `check.create` —
[`D31`](decisions/D31-check-create-contract.md).

**Общие правила.** Успех — `isError = false`, `content[0].text` с JSON-объектом
и полем `status` (`"ok"` или доменный: `"published"`, `"deprecated"`); ошибка —
`isError = true` с конвертом `{"error": {"code": "...", "message": "..."}}`
(`code` — стабильный `snake_case` латиницей, `message` — русский). Ключи
ответов — `snake_case`, латиница; текстовые значения `decision`, `reason`,
`deprecation_reason`, `message` — русские. Каноническое имя входных данных для
исполнения — `input` (варианты `data`, `params`, `payload` не используются).

**Инварианты.** Любой черновик в песочнице всегда парсится (`check.create`
валидирует `source` до записи). Ответы возвращают только рендеренные строки
(`source`, `condition`, `decision`, `reason`); внутренние
`Rule`/`Condition`/`Action` приватны и не публикуются. `stale` черновика: файла
`rules/{name}.dar` нет или хэши совпадают → `false`, хэши различаются → `true`;
`stale` не блокирует `check.test`.
`test_valid = (last_test_checksum != null && last_test_checksum == source_hash)`.
Поля `size` и `format` не вводятся.

**Инструменты MVP** (полные схемы — [`D34`](decisions/D34-mcp-tool-contracts.md)):

| Инструмент | Вход | Успех (`status`) |
|---|---|---|
| `check.create` | `{name, source}` | `ok` |
| `check.list_drafts` | `{}` | `ok` |
| `check.get_draft` | `{name}` | `ok` |
| `check.test` | `{name, input}` | `ok` |
| `check.delete_draft` | `{name}` | `ok` (`deleted: bool`) |
| `check.publish` | `{name, version, published_by?}` | `published` |
| `check.deprecate` | `{name, version, reason}` | `deprecated` |
| `check.list_published` | `{}` | `ok` |
| `check.rebuild_manifest` | `{}` | `ok` |
| `check.run` | `{name, version, input}` | `ok` |

**Вне MVP:** `check.merge` ([`D56`](decisions/D56-merge-step.md), команда
`credo merge` и будущая кнопка UI); `check.explain_client` (Q25, отложен, v0.2).

## 7. Жизненный цикл правила

```
rules/*.dar → черновик (check.create → check.test) → publish/{name}-{version}
            → credo merge → main → evaluate
```

Черновик — производное состояние, не источник истины: он создаётся из
`rules/*.dar` или агентом с нуля; при расхождении выигрывает файл (черновик
помечается `stale`), черновик без файла при публикации сначала сохраняется в
`rules/{name}.dar` — [`D54`](decisions/D54-source-of-truth-flow.md).

Три представления правила: грязный буфер редактора — локальные прогоны
(`check.test` на черновике); файл на диске (`rules/*.dar`) — git-операции
(`commit`, `publish`); опубликованная версия из `main` — исполнение «как в
проде» (явный выбор версии). Git-панель Notebook работает только с
workspace-репозиторием; репозиторий публикаций — внутренняя деталь сервера
(read-only панель «Версии»); хотфикс старой линии — ветвление и bumped-номер
(`1.0.x → 1.0.1`) — [`D28`](decisions/D28-two-git-contours.md).

`check.create` (`{name, source}`, оба обязательны) парсит и валидирует весь
текст `.dar`; имя черновика — из заголовка правила; повторный вызов
перезаписывает черновик («сохранить = обновить»); ответ — `{status: "ok", name}`
([`D31`](decisions/D31-check-create-contract.md), полные схемы — §4.5).

Шаг слияния ветки в `main` — отдельный и явный: `credo merge {name} {version}`;
до слияния версия не видна потребителям. Ветка обязана быть потомком `main`
(иначе отказ без авто-ребейза); `refs/heads/main` обновляется атомарно
(`git update-ref` с CAS), затем ветка `publish/{name}-{version}` удаляется.
Кнопка «Смержить» и `check.merge` — в планах —
[`D56`](decisions/D56-merge-step.md) (см. также [`D55`](decisions/D55-publish-branch-name.md)).

## 11. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Правило** | Атомарная проверка: условие → действие |
| **Атом** | Единица исполнения v0.1: `(правило, данные) → Explanation`, чистая функция без сведения решений (принцип «Макдоналдс», Q20) |
| **Конвейер (pipeline)** | Слой композиции атомов: упорядоченный набор правил, скорингов, таблиц (порядок, условия, сведение решений). «Конвейер» и pipeline — одно понятие: русский термин — в документации, латиница — в машинных идентификаторах (ресурс `/pipelines/...`, v0.2 — Q20) |
| **Черновик** | Непубликованная версия правила в песочнице; производное состояние, не источник истины (Q12). Вычисляемые метки: `stale` — файл `rules/{name}.dar` расходится с черновиком; `test_valid` — успешный тест при текущем `source_hash` (Q29) |
| **Публикация** | Фиксация версии в git: ветка `publish/{name}-{version}` (Q14), слияние в `main` — отдельный явный шаг `credo merge` (Q15); потребителям версия видна только после слияния |
| **check (проверка)** | Версионируемая запись реестра: `name` + версии; один check = один каталог версии `checks/{name}/{X}/{Y}/{Z}/` (`rule.json`, `contract.json`, `meta.json`); в v0.1 check — это правило (Q13/Q32) |
| **`name`** | Машиночитаемый латинский идентификатор проверки (например, `CreditAgeMin`, Q13); человекочитаемое имя — `display_name` в `meta.json`. Термин `rule_id` не используется (Q17) |
| **Контракт (`CheckContract`)** | Машиночитаемое описание проверки: `name`, `version`, `description`, входные поля (`inputs` с типами), словарь решений (`decisions`); публикуется как `contract.json` (Q13) |
| **Метаданные версии (`CheckMeta`)** | `meta.json` каталога версии: `name`, `version`, `display_name`, `published_at`, `published_by`, `checksum`, `source_hash`, `compiler_version`; при депрекации — `deprecated_at`, `deprecation_reason` (Q13) |
| **Песочница (sandbox)** | `.credo/sandbox.json` — хранилище черновиков; производное состояние, не источник истины (Q12); хранит метки тестирования `last_test_checksum`/`tested_at` (Q16) |
| **published-repo** | Bare-git репозиторий публикаций `.credo/published-repo/`: `main` — источник истины для исполнения; внутренняя деталь `credo-server` (Q15/Q32) |
| **Манифест (`manifest.json`)** | Машинное описание всех проверок в `main`: `schema_version`, `service_hash`, `checks[]`; `GET /checks` возвращает его же плюс `count` (Q21) |
| **`ManifestEntry`** | Элемент манифеста: `name`, `active`, `supported[]`, `deprecated[]` (Q21) |
| **`active`** | Максимальная supported-версия проверки; пустая строка, если все версии deprecated (Q10/Q21) |
| **`supported`** | Все не-deprecated версии проверки по убыванию, включая `active` (Q21) |
| **`deprecated`** | Версии, выведенные из эксплуатации: не исполняются (REST 410), данные сохраняются (Q21) |
| **`kind`** | Вид проверки (правило/скоринг/таблица/конвейер); в v0.1 не вводится — единственный вид — правило; вернётся в v0.2 (Q21/Q36) |
| **`service_hash`** | SHA-256 от содержимого манифеста (`name|version|status|checksum` всех версий); меняется при публикации/депрекации; используется для инвалидации кэша (Q21) |
| **Объяснение** | Структура (Q42): `rule_name`, `condition`, `actual_value`, `matched`, `decision`, `reason`; ключи латиницей, тексты решений/причин русские |
| **Прогон** | Исполнение конвейера на исторических данных |
| **Workspace** | Каталог пользователя: `rules/` (источник истины), `.credo/` (данные `credo-server`), `.dar-notebook/` (данные Notebook); оба служебных каталога — вне git (Q19) |
| **code=doc** | Принцип: код является документацией |
| **file-first** | Файл на диске — источник истины |
| **sidecar** | Побочный процесс, управляемый основным приложением |
| **LSP** | Language Server Protocol — протокол для IDE |
| **MCP** | Model Context Protocol — протокол для AI-агентов |
