## 1. Цель проекта

**DAR {}** — декларативный предметно-ориентированный язык описания кредитных конвейеров с русским синтаксисом, предназначенный для риск-технологов, бизнес-аналитиков и разработчиков банковского сектора.

### 1.1. Решаемая проблема

В кредитном конвейере три стороны (бизнес, риск, разработка) работают с правилами в разных форматах. При каждом изменении смысл теряется при переводе между форматами, объяснение отказа требует ручного разбора, тестирование отделено от описания правил.

### 1.2. Решение

Один декларативный файл `.dar`, который одновременно является:
- **Требованием** (читается бизнесом)
- **Исполняемым кодом** (выполняется движком)
- **Тестом** (целевое состояние: сценарии проверки в файле; в MVP — вне
  объёма, см. Q34)
- **Документацией** (принцип code=doc)
- **Источником объяснений** (для аудита и клиентов)

> **Q34 (решено 2026-09-26):** в MVP `.dar` не содержит тестов: «быстрые
> прогоны» живут в локальном кэше `.dar-notebook/results-cache.json`
> (вне git, `.dar-notebook/` в `.gitignore`). Канонические тест-файлы
> (`tests/*.тест`, принцип code=doc) — вне MVP, v0.2.

### 1.3. Ключевые принципы

| Принцип | Что означает |
|---------|-------------|
| **code = doc** | Код `.dar` сам является документацией. Отдельные документы не нужны |
| **file-first** | Файл на диске — источник истины. Базы данных, облака — вторичны |
| **русский синтаксис** | Ключевые слова на русском: `Правило`, `Если`, `Решение` (канон — `GRAMMAR.md`) |
| **объяснимость** | Каждое решение содержит причину, правило, условие, факт |
| **версионируемость** | Каждое правило имеет semver-версию, публикуется в git |
| **не заменяет, а дополняет** | Пользователь всегда может открыть файл в любом редакторе |
| **атомарная композиция** («принцип Макдоналдса») | Полный прогон собирается из атомов: `(правило, данные) → Explanation`; сведение решений — слой конвейера (v0.2). См. §1.3.1 |

### 1.3.1. Принцип «Макдоналдс»: композиция из атомов

> Зафиксирован решением Q20 (`OPEN_QUESTIONS.md`); краткая ссылка —
> `DECISIONS.md` (ADR-001).
>
> **Терминология:** «конвейер» и pipeline — одно понятие: русский термин —
> в документации, латиница — в машинных идентификаторах (URL
> `/pipelines/...`, имена в коде).

**Метафора:** как в Макдоналдсе «Биг Мак» собирается из ингредиентов (булка,
котлета, соус), а не жарится как единое блюдо, так и полный прогон («вся
картина») собирается из атомарных проверок, а не исполняется как монолит.

**Что это значит:**

- **Атом** (ингредиент) = одна проверка на одних данных → одно
  `Explanation`. Чистая функция без состояния, без сведения с другими
  атомами.
- **Конвейер** (комбо) = набор атомов + правила сборки (порядок, условия) +
  сведение решений.
- **Конфигурация** (опции) = данные о составе конвейера (какие атомы, какие
  исключить).

**Следствия для архитектуры:**

1. Атом не знает о существовании других атомов и не сводит решения (это
   забота конвейера).
2. Конвейер — новый ресурс (`/pipelines/{name}/versions/{v}/evaluate` —
   машинный идентификатор понятия «конвейер»), а не модификация атома.
3. «Опции» (состав конвейера) — данные конфигурации, версионируются
   отдельно.
4. Атом проектируется как компонуемый элемент:
   `(правило, данные) → Explanation`.

**Критерий принятия решений:** если новая фича требует «запечь что-то внутрь
атома» (например, свести решения или знать о других правилах) — это
нарушение принципа. Скорее всего, это слой конвейера.

**Как применять на практике:**

| Вопрос | «Макдоналдс» говорит | Решение |
|---|---|---|
| «Может, атом сам агрегирует результаты всех правил?» | ❌ Котлета не знает, что её положат в Биг Мак. Сведение — слой сборки. | Агрегация в конвейере (v0.2). |
| «Нужен ли `priority` внутри атома?» | ❌ У котлеты нет приоритета — он есть у меню. | `Приоритет` — в метаданных конвейера, не в атоме. |
| «Можно ли вызвать атом напрямую?» | ✅ Да, как заказать просто котлету. | `POST /checks/{name}/versions/{v}/evaluate` остаётся. |
| «Где хранить историю вызовов?» | ✅ В кассе (конвейер), не в котлете. | Конвейер логирует свои прогоны. |

## 4. Модель развёртывания

### 4.1. Локальный компьютер сотрудника

```
┌─────────────────────────────────────────────────────┐
│  DAR Notebook (Tauri 2)                              │
│  ├── React UI (CodeMirror, файловое дерево, чат)     │
│  ├── Rust backend (Tauri IPC)                        │
│  │   └── управляет sidecar-процессами               │
│  ├── lsp-dar (sidecar, stdio)                        │
│  ├── git CLI (workspace-репозиторий)                 │
│  └── MCP-клиент (stdio, спавн credo-server)          │
└─────────────────────────────────────────────────────┘
```

**MCP-транспорт в MVP (Q30, решено 2026-09-26).** Notebook спавнит
`credo-server` как локальный sidecar через stdio (JSON-RPC 2.0) и запускает
его автоматически при старте — пользователь видит только UI. Сервер
работает в режиме «только MCP» (без REST) согласно Q27; `published-repo`
локален (Q32). HTTP+SSE и внешний сервер — вне MVP (v0.2+, multi-user).

**Исполнение правил из редактора (Q33, решено 2026-09-26).** Кнопка
«Выполнить» и агент используют единый механизм — MCP `check.test` на
черновике (через `credo-server`); локального исполнения через Tauri
`dar-core` нет. Кнопка активна только при наличии черновика; сохранение
правила создаёт черновик из буфера (`check.create`, draft-first), файл
`rules/{name}.dar` материализуется при публикации (Q12). Опубликованная
версия исполняется через `check.run` (не через черновик).

### 4.2. Сервер (общий для команды)

```
┌─────────────────────────────────────────────────────┐
│  credo-server                                        │
│  ├── MCP-сервер (rmcp, stdio/HTTP)                   │
│  ├── REST API (axum, по умолчанию 127.0.0.1:8080)    │
│  ├── Git bare-репозиторий (публикации)               │
│  ├── Кэш манифеста (RwLock + watcher)               │
│  └── dar-core (нативный)                             │
│                                                      │
│  Данные:                                             │
│  ├── .credo/sandbox.json (черновики)                 │
│  └── .credo/published-repo/ (git bare)              │
└─────────────────────────────────────────────────────┘
```

Черновики в `.credo/sandbox.json` хранят метки тестирования
`last_test_checksum` и `tested_at`: успешный `check.test` обновляет их;
публикация без успешного теста или после изменения черновика отклоняется
(Q16/Q34, решено 2026-09-26).

**Запуск и адрес REST (Q27, решено 2026-09-25).** Канон адреса —
`127.0.0.1:8080` (порт 8080 из прежней формулировки зафиксирован вместе с
хостом). REST поднимается **только по явному флагу**; без флагов сервер
работает в режиме «только MCP (stdio)» — это штатный режим Notebook-демо
(см. Q30):

| Запуск | Результат |
|---|---|
| `credo2` | только MCP (stdio), REST выключен |
| `credo2 --rest` | MCP + REST на `127.0.0.1:8080` |
| `credo2 --addr <ADDR>` | MCP + REST на `<ADDR>` (включает REST) |
| `credo2 --no-rest` | только MCP; перекрывает `--rest` и `--addr` |

Приоритет флагов: `--no-rest` > `--addr` > `--rest`. Для наружного
развёртывания адрес задаётся через `--addr` (например, `--addr
0.0.0.0:8080`). Текущий код (`src/main.rs`) реализует эту схему — правок в
коде не требуется.

**Два git-репозитория и мультиверсионность (Q32, решено 2026-09-26).**
У системы два независимых git-контура:

- **workspace-репозиторий** (локальный, у пользователя) — источник истины
  `rules/*.dar`; с ним работает git-панель Notebook (статус, diff, commit,
  ветки); операции `commit`/`publish` выполняются от файлов на диске;
- **published-repo** (bare, `.credo/published-repo/`) — внутренняя деталь
  `credo-server`; `check.publish` пишет в него артефакт
  `checks/{name}/{X}/{Y}/{Z}/`, слияние в `main` выполняет `credo merge`.
  Пользователь видит опубликованное через панель «Версии» (read-only;
  источник — манифест / `check.list_published`).

**Три уровня источника правды (Q32):** грязный буфер редактора — для
локальных прогонов (`check.create` из буфера → `check.test` на черновике; Q33); файл на
диске (`rules/*.dar`) — для git-операций (`commit`, `publish`), при
расхождении выигрывает файл (Q12); опубликованная версия из `main` — для
исполнения «как в проде» с явным выбором версии. Переключение версий — в
тулбаре редактора с группировкой по major.minor; workspace при переключении
не затирается.

> **Q19 (решено 2026-09-26):** оба служебных каталога живут в корне
> workspace и не попадают в git; владельцы разные — серверный (`.credo/`)
> и клиентский (`.dar-notebook/`) домены. Имя `.credo/` оставлено

|---|---|---|---|

| `.credo/` | `credo-server` | `sandbox.json` (черновики, Q12); `published-repo/` (bare-git публикаций, Q15/Q32) | нет (`.gitignore`) |
| `.dar-notebook/` | DAR Notebook | `layout.json`; `results-cache.json` («быстрые прогоны», Q34); `agent-history.json` (Q31) | нет (`.gitignore`) |

> **Q35 (решено 2026-09-26):** новый workspace создаёт `rules/`,
> `rules/Пример.dar` (канонический пример из `GRAMMAR.md` §1), `README.md`
> (структура, пример, шаги «создать → выполнить → опубликовать») и
> `.gitignore` (Q19). «Создать правило» создаёт файл `rules/{Имя}.dar` с
> парсящимся шаблоном; имя правила = имя файла; черновик появляется при
> сохранении (Q33), не при создании файла.

Канонический шаблон нового правила (`{Имя}` подставляется из диалога):

```dar
// Новое правило: отредактируйте условие и решение
Правило {Имя} {
  Если (Клиент.Возраст < 21) {
    Решение = Отказ;
    Причина = "Причина отказа";
  }
}
```

> **Q34 (решено 2026-09-26):** каталог `tests/` (`*.тест`, принцип
> code=doc) — вне MVP, возвращается в v0.2. В MVP тесты — только локальный
> кэш `.dar-notebook/results-cache.json`; готовность к публикации — успешный
> `check.test` (`last_test_checksum`/`tested_at`, Q16), а не файл теста.

> **Q37 (решено 2026-09-26):** каталог `tables/` исключён: схема полей и

> (строгая типизация, схема из БД).

### 4.4. REST API v0.1: состав и схема

> **Q20/Q21 (решено 2026-09-25):** MVP-минимум, канонический путь и схема
> манифеста. Полный контекст — `OPEN_QUESTIONS.md` Q20/Q21.

**MVP-минимум (YAGNI):**

| Метод и путь | Назначение | Статус |
|---|---|---|
| `POST /checks/{name}/versions/{version}/evaluate` | Атомарное исполнение опубликованной версии из `main` | MVP |
| `GET /checks` | Манифест (схема ниже) | MVP |
| `GET /health`, `GET /version`, `GET /openapi.json` | Инфраструктура (без ключа) | MVP |
| `POST /checks/{name}/evaluate` | Исполнение active-версии | вне MVP-минимума (в прототипе; судьба — пост-MVP) |
| `GET /checks/{name}/versions`, `GET /checks/{name}/versions/{version}` | История/детали версий | вне MVP-минимума (в прототипе; судьба — пост-MVP) |
| batch (Q24), export/import (Q26), `/pipelines/...` (v0.2) | — | отложено |

Эндпоинты вне MVP-минимума в рамках MVP **не удаляются и не развиваются**;
их сохранение или удаление — решение пост-MVP, не задача MVP.

`name` и `version` — параметры пути, а не тела: один шаблон пути, без
алиасов. `evaluate` читает только версии, влитые в `main` (Q12/Q15);
черновики в REST-исполнении не участвуют. Серверной агрегации нет —
оркестрация полного прогона на стороне клиента (манифест → цикл по
`active`-версиям → цикл атомарных `evaluate`, Q20).

**Схема `GET /checks`** — манифест как есть (один источник истины —
`manifest.json` в `main`) плюс `count`:

```json
{
  "schema_version": 1,
  "count": 2,
  "service_hash": "<sha256>",
  "checks": [
    {
      "name": "CreditAgeMin",
      "active": "1.0.1",
      "supported": ["1.0.1", "1.0.0"],
      "deprecated": ["1.1.0"]
    }
  ]
}
```

`ManifestEntry`: `name` (латиница, Q13); `active` — максимальная
supported-версия, `""` если все версии deprecated; `supported` — все
не-deprecated версии по убыванию, включая active; `deprecated` — выведенные
из эксплуатации. Инварианты: каждая версия ровно в одном из списков; при
непустом `supported` `active == supported[0]`. Поле `kind` не вводится
(YAGNI, Q21); `generated_at` остаётся в `GET /version`.

**Ошибки (язык — Q11; статусы зафиксированы 2026-09-25; конверт и коды —
Q23, решено 2026-09-25):**

Все ответы с ненулевым статусом имеют единый конверт:

```json
{"error": {"code": "<стабильный код>", "message": "<русский текст>"}}
```

`code` — `snake_case`, латиница, стабилен в пределах major-версии API;
`message` — канонический текст по Q11. Поле `details` в v0.1 не вводится
(YAGNI).

| Статус | `code` | Текст (`message`) | Когда |
|---|---|---|---|
| 404 | `check_not_found` | `проверка не найдена: {name}` | проверки нет в манифесте |
| 404 | `version_not_found` | `версия не найдена: {name}@{version}` | версии нет в `main` (versioned evaluate) |
| 410 | `version_deprecated` | `версия выведена из эксплуатации: {name}@{version}` | обращение к deprecated-версии |
| 409 | `activation_unavailable` | `активация недоступна: {name}` | active-эндпоинт при пустом `active` (все версии deprecated) |
| 422 | `evaluation_failed` | текст ошибки ядра (`EvalError`) | отсутствующее поле / несовместимый тип (Q8/Q9) |
| 401 | `unauthorized` | `ошибка аутентификации: неверный или отсутствующий x-api-key` (Q22) | неверный/отсутствующий ключ |

Аутентификация — Q22 (решено 2026-09-25): заголовок `x-api-key`,
единственный серверный ключ (`CREDO_API_KEY` или флаг `--api-key`, флаг
выше переменной), открытые пути `/health`,
`/docs`, `/openapi.json`; без переменной API открыт (режим демо). Тело 401
— общий конверт Q23 (`code = unauthorized`).

### 4.5. Контракты MCP-инструментов v0.1

> **Q29 (решено 2026-09-26):** JSON-контракты MCP-инструментов —
> единственный источник истины по взаимодействию агента с сервером.
> Согласовано с Q11 (язык ошибок), Q16/Q34 (тест-гейт), Q23 (конверт
> ошибки REST), Q28 (контракт `check.create`), Q32 (пути реестра),
> Q33 (draft-first), Q42 (схема объяснения).

**Общие правила:**

1. Успешный ответ: `isError = false`; `content[0].text` содержит
   JSON-объект; объект содержит поле `status`; `status` — общий
   `"ok"` или доменный (`"published"`, `"deprecated"`).
2. Ошибочный ответ: `isError = true`; `content[0].text` содержит
   `{"error": {"code": "...", "message": "..."}}`; `code` — стабильный
   `snake_case` латиницей; `message` — русский текст (Q11).
3. Ключи ответов — `snake_case`, латиница. Текстовые значения
   `decision`, `reason`, `deprecation_reason`, `message` — русские.
4. Каноническое имя входных данных для исполнения — `input`.
   Альтернативы `data`, `params`, `payload` не используются.

**Стабильные коды ошибок** — см. таблицу в Q29
(`OPEN_QUESTIONS.md`): `validation_failed`, `draft_not_found`,
`evaluation_failed`, `publish_failed`, `version_not_found`,
`version_deprecated`, `deprecation_conflict`, `manifest_error`,
`unknown_tool`, `internal_error`.

**Инварианты:**

1. Любой черновик в песочнице всегда парсится: `check.create`
   валидирует `source` до записи.
2. MCP-ответы возвращают только рендеренные строки (`source`,
   `condition`, `decision`, `reason`); внутренние `Rule / Condition /
   Action` приватны (Q3, GRAMMAR.md §3) и не публикуются.
3. `stale` черновика: файл `rules/{name}.dar` отсутствует → `false`;
   хэши совпадают → `false`; хэши различаются → `true`.
   `stale` не блокирует `check.test`.
4. `test_valid = (last_test_checksum != null && last_test_checksum == source_hash)`.
5. Поля `size` и `format` черновика не вводятся.

**Инструменты MVP** (таблица; полные схемы — Q29):

| Инструмент | Вход | Успех (`status`) |
|---|---|---|
| `check.create` | `{name, source}` | `ok` |
| `check.list_drafts` | `{}` | `ok` |
| `check.get_draft` | `{name}` | `ok` |
| `check.test` | `{name, input}` | `ok` |
| `check.delete_draft` | `{name}` | `ok` (`deleted: bool`) |
| `check.publish` | `{name, version, published_by?}` | `published` |
| `check.deprecate` | `{name, version, reason}` | `deprecated` |
| `check.list_published` | `{}` | `ok` |
| `check.rebuild_manifest` | `{}` | `ok` |
| `check.run` | `{name, version, input}` | `ok` |

**Вне MVP:** `check.merge` (Q15, план — команда `credo merge` и будущая
кнопка UI); `check.explain_client` (Q25 — отложен, v0.2).

Черновик — производное состояние (Q12): он создаётся из `rules/*.dar` или
агентом с нуля; источник истины — `.dar`-файл, при расхождении выигрывает
файл (черновик помечается `stale`). У каждого опубликованного артефакта есть
исходник: черновик без файла при публикации сначала сохраняется в
`rules/{name}.dar`.

Три уровня источника правды (Q32): грязный буфер редактора — локальные
прогоны (`check.create` из буфера → `check.test` на черновике; Q33); файл на диске
(`rules/*.dar`) — git-операции (`commit`, `publish`); опубликованная версия
из `main` — исполнение «как в проде» (явный выбор версии). Git-панель
Notebook работает только с workspace-репозиторием; репозиторий публикаций —
внутренняя деталь сервера (read-only панель «Версии»). Мультиверсионное
сопровождение: хотфикс старой линии создаётся ветвлением от неё и
публикацией с bumped-номером (1.0.x → 1.0.1).

**Контракт `check.create` (Q28, решено 2026-09-26).** Параметры:
`{ "name": string, "source": string }` — оба обязательны. `source` — весь
текст `.dar`-файла; сервер парсит и валидирует его, ошибки парсинга
возвращаются как `error`. Имя черновика — из заголовка правила (первая
строка `Правило {name}`, `GRAMMAR.md`); заголовок отсутствует или
невалиден — ошибка валидации. Повторный `check.create` с тем же `name`
перезаписывает черновик («сохранить = обновить»), отдельного флага
перезаписи нет. Ответ: `{ "status": "ok", "name": "..." }`;
метаинформация (список полей) — вне MVP (задача LSP). `expected_kind` и
`contract` не используются: типы выводятся из `source`.
Полные контракты всех MCP-инструментов (включая `check.create`) — §4.5
(Q29).

Шаг слияния ветки в `main` — отдельный и явный (Q15): `credo merge {name} {version}`.
До слияния опубликованная версия не видна потребителям (`evaluate`, манифест, UI).
Ветка обязана быть потомком `main`; если нет — отказ без авто-ребейза с
предложением перепубликовать. Иначе `refs/heads/main` обновляется атомарно
(`git update-ref` с CAS-проверкой ожидаемого sha), после чего ветка
`publish/{name}-{version}` удаляется. Кнопка «Смержить» в UI и MCP-инструмент
`check.merge` — в планах; команда проектируется как их будущая реализация.

## 11. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Правило** | Атомарная проверка: условие → действие |
| **Атом** | Единица исполнения v0.1: `(правило, данные) → Explanation`, чистая функция без сведения решений (принцип «Макдоналдс», Q20) |
| **Конвейер (pipeline)** | Слой композиции атомов: упорядоченный набор правил, скорингов, таблиц (порядок, условия, сведение решений). «Конвейер» и pipeline — одно понятие: русский термин — в документации, латиница — в машинных идентификаторах (ресурс `/pipelines/...`, v0.2 — Q20) |
| **Черновик** | Непубликованная версия правила в песочнице; производное состояние, не источник истины (Q12). Вычисляемые метки: `stale` — файл `rules/{name}.dar` расходится с черновиком; `test_valid` — успешный тест при текущем `source_hash` (Q29) |
| **Публикация** | Фиксация версии в git: ветка `publish/{name}-{version}` (Q14), слияние в `main` — отдельный явный шаг `credo merge` (Q15); потребителям версия видна только после слияния |
| **check (проверка)** | Версионируемая запись реестра: `name` + версии; один check = один каталог версии `checks/{name}/{X}/{Y}/{Z}/` (`rule.json`, `contract.json`, `meta.json`); в v0.1 check — это правило (Q13/Q32) |
| **`name`** | Машиночитаемый латинский идентификатор проверки (например, `CreditAgeMin`, Q13); человекочитаемое имя — `display_name` в `meta.json`. Термин `rule_id` не используется (Q17) |
| **Контракт (`CheckContract`)** | Машиночитаемое описание проверки: `name`, `version`, `description`, входные поля (`inputs` с типами), словарь решений (`decisions`); публикуется как `contract.json` (Q13) |
| **Метаданные версии (`CheckMeta`)** | `meta.json` каталога версии: `name`, `version`, `display_name`, `published_at`, `published_by`, `checksum`, `source_hash`, `compiler_version`; при депрекации — `deprecated_at`, `deprecation_reason` (Q13) |
| **Песочница (sandbox)** | `.credo/sandbox.json` — хранилище черновиков; производное состояние, не источник истины (Q12); хранит метки тестирования `last_test_checksum`/`tested_at` (Q16) |
| **published-repo** | Bare-git репозиторий публикаций `.credo/published-repo/`: `main` — источник истины для исполнения; внутренняя деталь `credo-server` (Q15/Q32) |
| **Манифест (`manifest.json`)** | Машинное описание всех проверок в `main`: `schema_version`, `service_hash`, `checks[]`; `GET /checks` возвращает его же плюс `count` (Q21) |
| **`ManifestEntry`** | Элемент манифеста: `name`, `active`, `supported[]`, `deprecated[]` (Q21) |
| **`active`** | Максимальная supported-версия проверки; пустая строка, если все версии deprecated (Q10/Q21) |
| **`supported`** | Все не-deprecated версии проверки по убыванию, включая `active` (Q21) |
| **`deprecated`** | Версии, выведенные из эксплуатации: не исполняются (REST 410), данные сохраняются (Q21) |
| **`kind`** | Вид проверки (правило/скоринг/таблица/конвейер); в v0.1 не вводится — единственный вид — правило; вернётся в v0.2 (Q21/Q36) |
| **`service_hash`** | SHA-256 от содержимого манифеста (`name|version|status|checksum` всех версий); меняется при публикации/депрекации; используется для инвалидации кэша (Q21) |
| **Объяснение** | Структура (Q42): `rule_name`, `condition`, `actual_value`, `matched`, `decision`, `reason`; ключи латиницей, тексты решений/причин русские |
| **Прогон** | Исполнение конвейера на исторических данных |
| **Workspace** | Каталог пользователя: `rules/` (источник истины), `.credo/` (данные `credo-server`), `.dar-notebook/` (данные Notebook); оба служебных каталога — вне git (Q19) |
