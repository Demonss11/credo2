# T-17. `credo merge` — явный шаг слияния ветки публикации в `main`

- **Статус:** ⬜ открыта
- **Приоритет:** P2 (цикл публикации; до демо — если успеем; **приоритет — на
  подтверждение владельца**)
- **Зависит от:** —
- **Источник:** D56 (Q15).

## Контекст

Решение Q15/D56 задаёт двухшаговый цикл: `check.publish` создаёт ветку
`publish/{name}-{version}`, а отдельный явный шаг (`credo merge {name}
{version}`) переводит её в `main`. В коде шага слияния нет: нет команды, нет
ancestor-проверки, нет CAS-обновления `main`, нет удаления ветки; `next_step`
ответа `check.publish` (`src/mcp.rs:335-340`) предлагает ручной
`git update-ref` без CAS. Сценарий `git_integration.feature` (42–48) ожидает
`credo merge` с атомарным обновлением `main` и удалением ветки.

## Что сделать

- Добавить команду `credo merge {name} {version}` (MVP-канон — «человек
  командой»; позже та же семантика — для MCP-инструмента `check.merge`).
- Перед обновлением `main`: проверить, что ветка `publish/{name}-{version}` —
  потомок `main` (`git merge-base --is-ancestor`); если нет — отказ **без
  авто-ребейза** с предложением перепубликовать.
- Атомарно обновить `main`:
  `git update-ref refs/heads/main <sha-ветки> <ожидаемый-sha-main>`
  (**CAS против параллельных мержей**).
- После успеха удалить ветку `publish/{name}-{version}`.
- Заменить `next_step` в `src/mcp.rs` (335–340) подсказкой про `credo merge`
  (без ручного un-CAS `git update-ref`).

## Критерий готовности

Сценарий `../../features/git_integration.feature` «Слияние ветки публикации в
main» (строки 42–48): `credo merge CreditAgeMin 1.0.0` атомарно обновляет
`refs/heads/main`, удаляет ветку, версия становится видимой для `evaluate` и
манифеста; DoD задачи.
