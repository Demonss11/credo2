## 2. Разбор находок

### F1. Маршрут M без `rust-expert`

**Наблюдение.** `analyst` при плане T-03 (класс M) исключил `rust-expert` с обоснованием «не идиоматическая правка, clippy у `validator`». Обоснование в досье и ленте есть.

**Оценка.** Канон D38 для M предписывает полный маршрут; сокращение разрешено только для S. Формально — отклонение. Содержательно — оправданное: clippy + validator закрывают идиоматическую проверку. Оставить как отклонение — любой M с работающим clippy будет формально нарушать канон. Запретить — потеряем экономию.

**Решение.** Расширить канон.

- **`AGENTS.md` §Цикл задачи:** «`analyst` вправе исключить роль из маршрута: для S — штатно; для M — с письменным обоснованием в досье (`route_exclusions`: какая роль исключена и какие риски закрыты другими). Для L — маршрут полный, исключения не допускаются.»
- **`dispatch-loop.md`:** при `dispatch` с пропущенной ролью `analyst` обязан включить в досье пункт `route_exclusions`.

### F2. Scope T-03↔T-04 не в Q/D

**Наблюдение.** `analyst` в досье: «Scope-решений нет: вытекает из Q28 + Q29». Оба предыдущих анализа (T-11, T-03) фиксировали эту границу как долг C1.

**Оценка.** Формально рассуждение верно — граница выводится из Q28 и Q29. Практически — это граница со смежной задачей, где решено «в T-03 общий конверт не делать». Третий прогон подряд: решения такого класса в журнал не попадают.

**Решение.** Ввести порог + записать задним числом.

- **`dispatch-loop.md`:** «Scope-решение — любой выбор границы со смежной задачей, требованием или контрактом, где `analyst` решил, что **не** входит в T-XX. Идёт в Q/D через `migrator` **до** исполнения; при обнаружении после — задним числом, со ссылкой на текущую задачу.»
- Драфт Q45/D40 — §5.1.

### F3. Дрейф `docs/GRAMMAR.md` §7

**Наблюдение.** GRAMMAR §7 цитирует старое «Не найдено имя правила»; Run 3 изменил сообщение парсера, чтобы удовлетворить substring-требование сценария.

**Оценка.** Run 2 шёл через маппинг в `create`; Run 3 — через правку парсера. Оба рабочих; Run 3 — единственный источник сообщения, меньше скрытой логики. Дрейф — следствие, не дефект. Закрытие — `docs-writer` в хвосте задачи.

**Решение.** Канонизировать Run 3-подход.

- **`dispatch-loop.md` (hard rules, `coder`):** «Если сценарий требует substring в сообщении парсера — правится само сообщение парсера (единственный источник); `GRAMMAR` синхронизируется `docs-writer` в закрытии задачи.»

### F4. Права `git` у `lead`

**Наблюдение.** `git ls-remote` и `git diff --stat` отклонены движком прав, при том что `git diff *` в allow-листе `lead`. Класс А (платформенное) из анализа T-11.

**Оценка.** Блокером не является (обход найден). Но паттерн `git diff *` ведёт себя не как prefix-матч — нужна проверка семантики. `git ls-remote` — read-only; в текущем контуре `lead` не критична.

**Решение.** Два действия.

1. **Research-шаг в W6:** эксперимент в песочнице — какие строки матчатся `git diff *`, `git diff **`, точные формы.
2. **По результату:** либо расширить паттерны (`git diff --stat *`, `git ls-remote *`), либо зафиксировать «сужение команды» как штатный приём.
3. **`dispatch-loop.md`:** «Если команда отклонена правом — сузить до ближайшего allow-паттерна; если сужение невозможно — `surface_to_user` с описанием.»

### F5. `current_state.yaml` отстаёт

**Наблюдение.** Фаза `implementation`, `acceptance: pending`, хотя приёмка прошла. Ground truth — `receipts.yaml`.

**Оценка.** Сводка обновляется на re-plan; у пользователя картина отстаёт на фазу. Вторая точка записи (`validator` → `current_state`) — лишний писатель и лишний риск.

**Решение.** Зафиксировать авторитет и семантику.

- **`dispatch-loop.md`:** «Авторитетное состояние задачи — `receipts.yaml`. `current_state.yaml` — снимок на момент последнего re-plan, снабжается полем `as_of`. Ответ на статусный запрос владельца формируется по `receipts.yaml`, а не по `current_state.yaml`.»

### F6. `rework=0`

**Оценка.** Фабриковать нельзя. Механизм есть (`next_action.yaml` содержит ветку rework), задача оказалась чистой.

**Решение.** Не считать провалом; запланировать отдельный пилот на T-05 (после T-02) — прицельно на ветку rework.

### F7. P3-ссылка карточки T-03

**Наблюдение.** `../GRAMMAR.md` вместо `../../GRAMMAR.md`.

**Оценка.** Одна строка; во время Run 3 менять нельзя — сбивает сравнение с Run 2.

**Решение.** Починить в первой пост-Run 3 правке документации.

### F8. Вопросы владельцу — текстом, не через `question` tool

**Наблюдение (доп. от владельца).** Подтверждение git-пакета на Run 3 запрашивалось текстом, а не через `question` tool.

**Оценка.** Класс — процесс/UX. `question` даёт структурированные варианты (рекомендуемый, альтернативы), фиксируется инструментальным способом, снижает риск неверной интерпретации и потери решения. Текстовый запрос не оставляет машиночитаемого следа и оставляет выбор формата ответа на усмотрение модели.

**Решение.** Канонизировать: `surface_to_user` — **всегда** `question`, не текст.

- **`dispatch-loop.md`:** «Действие `surface_to_user` — **всегда** вызов `question` tool, не текст. Формат: 1–3 вопроса, у каждого 2–4 варианта, один помечен `(Recommended)`. После ответа — запись в ленту и обновление state. Текстовые уточнения допустимы как сопровождение, но решение — через `question`.»
- **`lead.md` (тело):** аналогичное правило в раздел «Цикл» или «Hard rules».
- **Метрика сравнения (для будущих прогонов):** «Вопросы владельцу — через `question` tool: да/нет; число пакетов».
