# Шаблон меморандума по итогам прогона (W-акт)

**Назначение:** зафиксировать решения по находкам после пилота/прогона — с готовыми текстами правок канона и драфтами Q/D, чтобы `migrator`, сервисная сессия и `docs-writer` исполняли без домысливания.
**Вход:** отчёт анализа прогона + наблюдения владельца + состояние репозитория (`git log`, state-файлы, лента).
**Выход:** один markdown-файл меморандума по скелету из части II.

---

## Часть I. Инструкция (до заполнения)

1. **Когда заводить.** После завершённого прогона (или серии на одной задаче), когда есть ≥2 находки, требующих решения уровня канона/журнала. Разовые однострочные правки — без меморандума.
2. **Кто пишет.** Сервисная сессия (владелец делегирует) либо `analyst` при повторяющихся прогонах.
3. **Порядок работы.**
   1. Прочитай отчёт анализа и наблюдения владельца целиком.
   2. Выпиши находки в черновик с черновыми ID (`F1…Fn`).
   3. Классифицируй по таксономии (А/Б/В) и присвой приоритет (P1/P2/P3).
   4. По каждой — «Наблюдение / Оценка / Решение». Решение без правки канона или журнальной записи — не решение, а пожелание.
   5. Собери сводную таблицу решений — она первая в документе.
   6. Подготовь **готовые тексты** правок (§4) и **драфты Q/D** (§5) — без «сделать лучше».
   7. Опиши последовательность внедрения (§6) и явно перечисли, что **не** решаем сейчас (§7).
4. **Правила честности.**
   - Факт без ссылки на лог/state — гипотеза, помечай.
   - Не фабрикуй сработавшие механизмы (нет rework — так и пиши).
   - Различай: наблюдение / вывод агента / твой вывод.
   - Если решение откладывается — зафиксируй условие пересмотра, а не «позже».
5. **Что обязательно приложить.** Сравнительную таблицу по прогонам (если их ≥2), драфты Q/D, тексты правок канона, последовательность внедрения.

## Часть III. Чек-лист перед сдачей

- [ ] Сводная таблица §1 согласована с разбором §2: ни одной находки не потеряно, ни одной не добавлено молча.
- [ ] Каждая находка имеет класс и приоритет; решения либо ведут к правке канона/журнала, либо явно «оставить как есть» с причиной.
- [ ] §4 содержит только готовые тексты (буквальная вставка), без «улучшить/уточнить».
- [ ] §5 — реальные Q/D с полями Resolves/Affects/Tasks; ID проверены по живому журналу.
- [ ] §6 имеет исполнителя на каждом шаге, порядок — от завершения прогона к канону и журналу.
- [ ] §7 не пуст: если решать нечего — так и написано, но условие пересмотра есть.
- [ ] Каждый факт со ссылкой на источник (лог/state/отчёт/коммит).
- [ ] Ничего не выдумано: отсутствующие механизмы названы отсутствующими.
- [ ] Объём: 150–300 строк; преобладают таблицы и готовые тексты.
- [ ] Терминология — канон проекта (роли в обратных кавычках, ID как в журнале).

## Часть IV. Типовые ошибки

1. **Меморандум-пересказ.** Повторение отчёта анализа без новых решений. Здесь решения, а не хроника.
2. **Решение-пожелание.** «Улучшить обработку ошибок» вместо «добавить `route_exclusions` в досье `analyst`».
3. **Раздел §4 с недоформулированным текстом.** Исполнитель начнёт домысливать — меморандум потеряет смысл.
4. **Q/D-драфт без Affects/Tasks.** `migrator` не сможет записать; запись откладывается и превращается в долг.
5. **§7 пустой.** Всегда есть отложенные решения. Пустой §7 = недоработанный документ.
6. **Тихая правка метрик §3.** Сравнение прогонов теряет валидность.
7. **Смешение уровней.** Платформенный баг записан в процессные — лечится не там.
8. **Меморандум вместо записи.** Решение, живущее только в меморандуме, со временем становится «решением без журнала». Ссылки на Q/D — обязательны.
