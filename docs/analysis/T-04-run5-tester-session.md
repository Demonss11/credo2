## 6. Выводы (факт → оценка → предложение)

1. **Лимит 28 исчерпан дважды подряд, задача закрыта третьим прогоном
   (61 шаг).** Факт: оба рабочих сегмента — ровно 28 шагов; в третьем — 5
   шагов «записей». Оценка: `28→36` с высокой вероятностью укладывает задачу в
   **два** прогона — во втором до полного закрытия не хватало ~3–4 шагов
   (лента + память + отчёт), резерв даёт +8. Предложение: подтвердить `36`
   (F18/§4.4) — данные за.
2. **Wrap-up на лимите — не гарантирован.** Факт: у `tester` оба останова дали
   содержательный итог в сессии; у `coder` — пустой финальный ход без отчёта.
   Оценка: след останова зависит от характера обрыва; полагаться на него
   нельзя. Предложение: закрепить resume-паттерн лида «**сначала
   отчёт/чекпойнт, потом работа**» (применён в [30]; короткий финальный вызов
   «только записи» [60] — как эталон) в `dispatch-loop`/F18-уточнении.
3. **Права `git -C`: расхождение с каноном T-13.** Факт: `git -C … diff`
   прошла дважды, `git -C … status` — `permission.rejected`, `git -C … show | …`
   — отклонена (труба). Оценка: поведение матчинга не однородно, канон говорит
   «`-C` не использовать». Предложение: сервисной сессии перепроверить и либо
   уточнить `review.md`/правила, либо зафиксировать паттерн в памяти роли;
   кандидат F-записи (см. §8).
4. **F20-эпизод подтверждает дрейф форматтеров.** Факт: два одинаковых diff
   `cargo fmt --check` (`{json, Value}` → `{Value, json}`), обход перезаписью
   файла. Оценка: уже учтено в §4.6 меморандума (draft), данных достаточно.
   Предложение: учесть при приёмке конфиг-пакета; память роли уже фиксирует
   паттерн.
5. **Гранулярность правок.** Факт: 26 `edit` (18 на `mcp_draft.rs`), 3 `write`.
   Оценка: на фоне лимита мелкие правки дороже цельных перезаписей; роль сама
   применила `write` для новых файлов и `common` (после F20-инцидента).
   Предложение: не требует правок; при `36` запас покрывает.

## 7. Ответы на вопросы разбора

- **Достаточно ли 36 шагов для `tester`?** С высокой вероятностью да (для двух
  прогонов): второй прогон остановился в ~3–4 шагах от полного закрытия
  (лента + память + отчёт), +8 шагов перекрывают это; первый прогон (28) в
  любом случае не мог завершить объём (рефактор — в середине). Экономия —
  один resume-цикл лида.
- **Воспроизводима ли потеря отчёта при обрыве?** Для `tester` — **нет**: оба
  останова сопровождались структурным wrap-up'ом, записи велись по протоколу;
  «потерянным» был только финальный статус записей. Контраст с `coder` (пустой
  финальный ход) показывает: потеря не детерминирована, поэтому правило
  «отчёт/записи до тяжёлой работы» и resume-паттерн лида остаются нужными —
  они делают исход предсказуемым.
