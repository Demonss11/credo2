## 2. Разбор находок

### F9. Пакет ↔ дерево (микро re-plan)

**Наблюдение.** `analyst` при сверке `package.add_paths` со `git status
--porcelain` нашёл пропуск `.opencode/memory/docs-writer.md` (чекпойнт 🚧 → ✅)
и добавил его; итог — 14 путей (лента: «re-plan (микро: расхождение add_paths
перед гейтом)»; `progress` — запись от 27.09).

**Оценка.** Механизм сработал (расхождение поймано до `surface_to_user`), но
перечень пакета составляется вручную → класс риска «тихий неполный коммит»
(при пропуске после гейта файл остался бы незакоммиченным, `expect` git не
выполнился бы).

**Решение.** Канонизировать сверку как штатный шаг (§4.1); микро re-plan
считать штатным приёмом, не отклонением.

### F10. Частичный пакет / owner override

**Наблюдение.** Владелец подтвердил пакет завершения, затем отменил его на
шаге push в develop (запись `cancelled_by_owner`); по прямому указанию выполнен
только push feature; на вопрос о судьбе merge ответил «вернуться к пакету
позже» (запись `deferred`). `develop` не тронут, ветка сохранена.

**Оценка.** Канон описывает пакет как атомарный и идемпотентный; частичное
исполнение и отложенный остаток не описаны, хотя отработали штатно. Без
правила «остаток = новый пакет с новым подтверждением» следующий resume может
выполнить незаподтверждённое.

**Решение.** Канонизировать (§4.2); `complete` запрещён до полного closeout
(зафиксировано в `wait_for_user`-плане).

### F11. GRAMMAR §7 — отдельная docs-задача

**Наблюдение.** `analyst` (re-plan pass) решил **не включать** правку GRAMMAR
в T-03: «GRAMMAR — канон языка (правка канона → L + auditor), T-03 принят как
M»; `docs-writer` подтвердил: GRAMMAR не тронут, follow-up отдельной
docs-задачей. Memo-1 (F3, §4.2) предполагал синк **в закрытии задачи**.

**Оценка.** Аргументы итерации 2 сильнее: (а) границы досье — только
`src/**`/`tests/**`; (б) правка канона языка — не M; (в) Run 3 не должен менять
канон посреди сравнения. Дрейф кода и GRAMMAR остаётся долгом — закрывается
задачей (AGENTS.md: «расхождение канона и кода → задача»).

**Решение.** Принять подход итерации 2; обновить memo-1 (§4.3) и драфт D41;
завести docs-задачу (§6, шаг 3).

### F12. Канал `surface_to_user` не фиксируется

**Наблюдение.** Записи `progress`/ленты о трёх `surface_to_user` не содержат
указания, задавался ли вопрос через `question` tool или текстом. Memo-1 F8
(«всегда `question`») по state не проверить.

**Оценка.** Без поля нельзя ни верифицировать F8, ни собрать метрику 9.

**Решение.** §4.4.

### F13. Шаги, сессии и хвост

**Наблюдение.** Две сессии по 16 шагов; 1 resume; `analyst` — 5 вызовов;
`progress` — 12 записей; финальный re-plan не оставил записи `progress`
(state/лента обновлены) — сессия завершилась на лимите шагов; closeout
(merge/push/delete) не пройден.

**Оценка.** Данные для решения memo-1 §7 (steps 16 → 24) появились, но решение

**Решение.** Зафиксировать данные; решение по `steps` — после closeout (§7);

## 4. Пакет правок канона (готовые тексты)

### 4.1 `dispatch-loop.md` — сверка git-пакета

> **Git-пакет: сверка перед гейтом.** Перед `surface_to_user` с git-пакетом
> `analyst` сверяет `package.add_paths` со снимком `git status --porcelain`
> (все пути задачи, включая память/почту; `.opencode/state/**` — вне git).
> Расхождение — re-plan **до** гейта; `lead` пакет не расширяет.

### 4.2 `dispatch-loop.md` + `git-workflow.md` — частичный пакет и override

> **Частичное исполнение.** Владелец может отменить/сузить подтверждённый
> пакет в любой момент: выполненная часть фиксируется (`progress.yaml`:
> `cancelled_by_owner`/`deferred`), остаток сохраняется в `next_action`
> (`package` + `resume_hint`); возобновление — **новым** подтверждением.
> `complete` — только после полного завершения задачи. `git` идемпотентен:
> повторный add/commit не выполняется, если коммит уже создан.

### 4.3 Правка memo-1 (§4.2 и §5.2, пункт про GRAMMAR)

> Заменить «`GRAMMAR` синхронизируется `docs-writer` в закрытии задачи» на:
> «`GRAMMAR` синхронизируется **отдельной docs-задачей после завершения
> прогона** (GRAMMAR — канон языка; правка канона — вне границ M)».

### 4.4 `dispatch-loop.md` — фиксация канала

> **Канал решения владельца.** Каждая запись `surface_to_user` в
> `progress.yaml` содержит `channel: question|text` и `result`; `question` —
> норма, текст — только сопровождение.

### 4.5 `dispatch-loop.md` — финализация записи действия

> Действие считается завершённым только после записи в `progress.yaml`;
> при приближении к лимиту шагов — сначала запись, затем остановка.
