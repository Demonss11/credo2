## 2. Разбор находок

### F15. `iteration` — чистая проверка (том 1, перенесено)

**Наблюдение.** Run 5: старт `iteration: 1`, rework не было, приёмка с первого
раунда → `iteration` остался `1` на всех участках; номера участков шли через
`progress_marker` (`run5_t04_plan` → … → `run5_t04_finalize`), не через
`iteration`.

**Оценка.** Дрейфа нет — норма W8 §4.2 соблюдена. Механика инкремента при
`rework` **не проверялась** (условие не возникло) — честная пометка для
чек-листа.

**Решение (драфт).** Внести F15 в реестр; чистую проверку инкремента выполнить
на первом `rework`.

### F16. `auditor` не может дописать отчёт в ленту (P2 аудита)

**Наблюдение.** `auditor` при аудите T-04 получил `permission.rejected` на
`edit .opencode/mail/T-04.md`; его фронтматтер разрешает `edit` только
`.opencode/memory/auditor.md`. Отчёт внесён релеем `lead`; по канону
(`AGENTS.md` §«Память и почта») роли дописывают отчёт в ленту сами.

**Оценка.** Расхождение «инструкция ↔ права» (класс Б). Решение владельца
28.09.2026: выдать право `edit .opencode/mail/**`.

**Решение (драфт).** §4.1 (права и тело роли) + §4.2 (`AGENTS.md`, «Пишет в»)
+ драфт §5.1. До внесения релей `lead` остаётся допустимым. Примечание: первый
аудит канон-пакета, которым вносится это право, снова пройдёт релеем.

### F17. Бриф плана противоречил канону

**Наблюдение.** Бриф `coder` (участок №2) требовал: `check.delete_draft` по
отсутствующему черновику → ошибка `draft_not_found` (со ссылкой «канон
`draft.feature` стр.49/68»). `coder` вернул scope-вопрос: канон требует
идемпотентного успеха (`draft.feature` стр.51–55; SPEC §4.5; Q29 §5;
`tests/mcp_draft.rs::delete_is_idempotent`). Re-plan участка №3 снял требование
как ошибочное чтение канона (восстановление канона, не scope-решение).

**Оценка.** Класс Б: ошибка планирования, пойманная исполнителем — механизм
сработал (тихой правки не было). Правило «что делать при расхождении брифа с
каноном» в каноне явно не записано. Первопричина — F32 (цитаты не сверены).

**Решение (драфт).** §4.3 — правило в `dispatch-loop.md` §«Hard rules».

### F18. Упоры в лимит `steps`

**Наблюдение.** `tester` (28 шагов) упёрся в лимит дважды: на середине
рефакторинга `tests/mcp_draft.rs` (файл в некомпилируемом состоянии, без
отчёта) и на завершении; оба продолжены тем же `sessionID`. `coder` (44 шага)
завершил правки, но не оставил текстового отчёта — отчёт и чекпойнт получены

**Оценка.** Класс Б: потери не было (resume сработал 3×), но два обрыва у
`tester` на одной задаче — сигнал малого запаса.

**Решение (драфт).** §4.4 — `tester` 36, `coder` 52; resume тем же
`sessionID` — норма (уже в `AGENTS.md` §«Лимиты шагов»).

### F19. `git branch -vv` вне allowlist

**Наблюдение.** При `branch_start` проверка upstream командой `git branch -vv`

**Решение (драфт).** §4.5; драфт §5.2.

### F20. Форматтер харнесса ≠ `cargo fmt` (style edition)

**Наблюдение.** `tester`: автоформаттер при сохранении сортирует импорты иначе,
чем `cargo fmt` (style edition); пришлось избегать mixed-case списков импортов.
`Cargo.toml`: `edition = "2024"`; `rustfmt.toml` в репозитории нет.

**Оценка.** Класс А/конфиг: standalone-`rustfmt` без `rustfmt.toml` не знает
edition 2024 → расхождение с `cargo fmt`; риск fmt-петель. Проверка 28.09.2026
подтвердила: `rustfmt --check tests/mcp_draft.rs` без edition даёт дифф, с
`--edition 2024` — чисто; `rustfmt --check src/mcp.rs` без edition **падает**
(«`async fn` is not permitted in Rust 2015»).

**Решение (драфт).** §4.6 — `edition = "2024"` + принятый стиль (80);
smoke-сверка.

**Оценка.** Класс В/дрейф: конфиг — источник поведения, канон обязан совпасть.
Связь: T-15 фаза C (session-commit), F30.

**Решение (драфт).** §4.7 — синхронизировать тексты; состояние включать в
процессные пакеты прогона.

### F22. Процессные файлы внутри продуктового коммита

**Наблюдение.** Коммит `3545afa` «`code(T-04)`» (19 файлов) содержит
служебные: 7 файлов `.opencode/memory/**` (analyst, auditor, coder,
docs-writer, git, tester, validator) и 2 файла `.opencode/mail/**` (T-04.md —
336 строк; service-mcp-ready-r2 — +20 строк) вместе с кодом `src/**` и
`tests/**`. Остаток записей ушёл в `a7eac82` (процессный коммит). В Run 4
процессные записи шли отдельным коммитом (`8d9c9dc`). Канон это допускал:
`git-workflow.md` §«Ограничения» — «память и почта ролей … входят в коммит
задачи по решению `lead`».

**Оценка.** Класс Б: история смешивает продукт и процесс; продуктовый коммит
непрозрачен по составу; для session-commit (T-15 фаза C) и review-практик это
прямое препятствие. Факт не был отклонением от канона — канон требует правки.

**Решение (драфт).** §4.8 — правило разделения коммитов (продукт/процесс);
процессный префикс `chore(process): …`.

### F23. EOL-шум (LF/CRLF), нет `.gitattributes`

**Наблюдение.** Предупреждения `LF will be replaced by CRLF` — при каждом
пакете (`git add`) в волне 0, T-03, T-04, `run5_records`; `coder`: «остаточный
diff форматтера — только CRLF-нормализация (файл LF)». Системный
`core.autocrlf=true`; индекс и рабочее дерево сейчас LF
(`git ls-files --eol`: `i/lf w/lf`), но без атрибутов любая запись/checkout
может внести EOL-шум в диффы.

**Оценка.** Класс В/конфиг: ложные диффы, шум в отчётах, риск fmt-петель.

**Решение (драфт).** §4.6 — `.gitattributes` (`* text=auto eol=lf`)
подготовлен; правило — форматтеры пишут LF, EOL в диффах не «чинить» вручную.

### F24. Срезанный вывод: нет протокола для ролей (B1 → норма)

**Наблюдение.** `coder` анализировал срезанный `git diff src/mcp.rs`
(21 КБ → «опущено ~8080 Б»); `tester`/`validator` работали с выводами ниже
порога. Маркер среза в выводе есть (`…[token-guard] срез: опущено ~N байт`),
но инструкций ролям, что с маркером делать, нет — только митигация в плане
волны 0 («пере-запуск команды с фильтром»).

**Оценка.** Класс Б: B1 переведён в норму решением владельца → протокол
обязан быть в каноне, иначе роли могут делать выводы по неполному выводу.

**Решение (драфт).** §4.9 — правило в `AGENTS.md` §«Гигиена и чтение».
