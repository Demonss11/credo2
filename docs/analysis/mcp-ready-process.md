## 0. Назначение

Цель — довести процесс агентного контура до состояния, в котором он
«сериализуется» в MCP-сервер (по образцу Kupu): **storage + validation +
query** над состоянием прогона. MCP не принимает решений: policy (`analyst`)
и orchestration (`lead`) остаются у ролей; MCP исполняет уже принятое решение.

Последовательность (владелец): **сначала процесс — потом MCP**. Эта записка —
шаг A плана: фиксирует целевую модель, схему состояния, каталог операций и
критерии готовности; реализация — задача
[T-15](../tasks/T-15-mcp-ready-process/README.md).

**Не входит:** разработка MCP-сервера (после заморозки — отдельная задача);
продуктовые фичи CREDO; правки канона (этот документ — проект, не канон).

## 1. Термины

| Термин | Значение |
|---|---|
| прогон (Run N) | цикл работ по одной задаче/пилоту (несколько сессий `lead`) |
| сессия (session) | один запуск `lead`; шаги ограничены `steps` |
| участок | отрезок плана между re-plan; кодируется `progress_marker` |
| `iteration` | rework-цикл задачи; не номер участка (W8 §4.2; F15) |
| re-plan / re-raise | пересмотр плана `analyst`; структурируется как объект (§5.5) |
| product / process | продукт (`src/**`, `tests/**`, `docs/**`) / операционные данные прогона (`state`, `mail`, `memory`) |
| session-commit | фиксация process-слоя на границе сессии (§6) |
| операция (op) | именованное изменение состояния: `append_progress(entry)` и др. (§5.4) |

| Запрашиваемость | ✖ метрики собираются вручную (W8 §3, §9–§11) | §7: метрики из состояния |

## 3. Слои и границы

| Слой | Ответственность | Кто (сегодня) |
|---|---|---|
| **Policy** | решает, *что* делать: план, re-plan, классификация | `analyst` |
| **Orchestration** | решает, *когда* и *кем*: dispatch, resume, остановка | `lead` |
| **Storage** | обеспечивает *как записать*: state, квитанции, лента | файлы (завтра — MCP) |

**Правило границы:** если операция требует **суждения** — она не в MCP.
MCP берёт storage, validation и query; не берёт решения, планирование,
формулировки брифов и git.

## 5. Схема состояния (проект, к утверждению)

### 5.1. Общие правила

- один писатель на файл; `progress` и `receipts` — только append;
- расширение схемы — записью в журнал и обновлением схемы; неизвестные поля
  до обновления — **предупреждение**, не ошибка (эволюция без жёсткости);
- источник истины при расхождении записей — `receipts.yaml` (как сейчас).

### 5.2. Поля артефактов

- `next_action.yaml`: `task`, `iteration`, `status` (`in_progress`/`blocked`/
  `idle`), `progress_marker`, `as_of`, `next[]` (`kind`, `role`, `brief`,
  `expect`, `package`), `resume_hint`, `re_raise` (при re-plan, §5.5).
- `current_state.yaml`: `as_of`, `task`, `iteration`, `rework`, `phase`,
  `acceptance`, `branch`, `base_commit`, `package`, `gate`, `deferred*`,
  `session_index`.
- `progress.yaml` (запись): `at`, `task`, `iteration`, `session_index`,
  `action` (`dispatch`/`surface_to_user`/`re-plan`/`complete`), `role`,
  `package`, `result`, `expect_match` (`true`/`partial`/`false`), `pre_gate`,
  `replan_reason`, `owner_response` (дословно, при `surface_to_user`), `next`.
- `receipts.yaml` (запись): `task`, `iteration`, `verdict`
  (`rework`/`accepted`), `report`, `date`.

### 5.3. Инварианты

- `iteration ≥ 1`; `rework = iteration − 1`; единое значение `iteration`
  в плане, состоянии, `progress` и квитанциях;
- `session_index` — сквозная нумерация сессий прогона (лечит дрейф
  «сессия №X» в текстах);
- `expect_match` — только из перечисленных значений;
- при `action: surface_to_user` обязательны `channel` и `owner_response`.

### 5.4. Каталог операций (≤ 10)

| # | Операция | Кто | Идемпотентность |
|---|---|---|---|
| 1 | `append_progress(entry)` | `lead` | ключ: (`task`, `session_index`, `action`, `role`) |
| 2 | `set_next_action(action)` | `analyst` | перезапись плана |
| 3 | `set_current_state(snapshot)` | `analyst` | снимок на re-plan |
| 4 | `register_receipt(receipt)` | `validator` | ключ: (`task`, `iteration`, `verdict`/`report`) |
| 5 | `register_re_raise(obj)` / `resolve_re_raise(id, fix)` | `analyst` | ключ: (`task`, `id`) |
| 6 | `record_dispatch_metrics(entry)` | `lead` | производная от `progress`; возможно слияние с №1 |
| 7 | `add_deferred(item)` / `resolve_deferred(id, reason)` | `lead` | ключ: (`task`, `id`) |
| 8 | `checkpoint_session(run, session)` | `lead` (диспатч `git` по «постоянному» пакету; Прил. A) | повтор пропускается (§6) |

### 5.5. Re-raise (объект)

Поля: `id`, `category`, `origin`, `failed_clause` (`expectation`,
`observation`), `fix`, `blocking`, `resolved`.

| Категория | Что значит | В метрике конвергенции |
|---|---|---|
| `expect_mismatch` | расхождение ожидания с отчётом | ✅ (кандидат в находку F) |
| `owner_override` | директива владельца (пакет/класс/лимит) | ✖ |
| `plan_gap` | неполнота плана | ✅ |
| `role_failure` | роль не справилась | ✅ |

Повтор `owner_override` на одном участке — сигнал к разбору плана, не норма.

## 6. Финализация и остановка

- **Правило останова.** Если остатка шагов не хватает на dispatch +
  журнальную запись + session-commit — не диспатчить: сначала финализировать
  состояние, затем остановиться.
- **Session-commit.** На границе сессии (штатной или вынужденной) `lead`
  инициирует фиксацию process-слоя отдельным коммитом в ветку `process/runN`:
  лента, память, снапшот состояния (`.opencode/state/snapshots/runN-sM/`).
  Коммит выполняется ролью `git` по «постоянному» пакету, подтверждённому
  один раз на прогон; продуктовые изменения в него не входят.
- **Идемпотентность.** Повторный append/commit не создаёт дублей: запись
  распознаётся по ключу (§5.4), уже сделанные шаги пропускаются.
- **Восстановление.** Resume — по снапшоту и квитанциям; ручная реконструкция
  записи (F13) — исключение, а не норма.

**Выбор механизма (решение владельца, 2026-09-27).** Process-commit исполняет
существующая роль `git` по «постоянному» пакету — подтверждение один раз на
прогон; права не расширяются, микро-роль `checkpoint` не вводится (в
перспективе её заменяет узкий инструмент после git-MCP — Приложение A). Фасад
владельца — команды OpenCode (`.opencode/commands/git/…`, инициируются из TUI;
работают и после упора `lead` в лимит): `/git/status` — уже; `/git/checkpoint` —
в объёме T-15 (фаза C), когда появятся `process/runN` и «постоянный» пакет.
Команда только триггерит исполнение подтверждённого пакета; подтверждение —
запись `lead` в ленте («нет записи — нет подтверждения»). В git-командах не
использовать shell-блоки (`!`-вставки) — они идут вне permission-потока
агента.

## 7. Метрики и запросы (целевые)

- метрики прогона: dispatch по ролям, шаги и упоры по сессиям, re-plan по
  категориям, `outcome`;
- очереди: `deferred_by_owner`, `blocked` — машиночитаемые выборки;
- метрика конвергенции: число re-plan без `owner_override` (сравнимо между
  прогонами);
- источник: `progress` + `receipts` + состояние; ручные таблицы меморандума
  (W8 §3, §9–§11) уходят.

## 8. Чек-лист готовности к MCP (заморозка)

- [ ] схема состояния в каноне и не менялась ≥ 2 прогона;
- [ ] список операций зафиксирован (≤ 10);
- [ ] идемпотентность проверена имитацией обрыва (resume);
- [ ] re-raise используется ≥ 2 прогона;
- [ ] метрики прогона выводятся из состояния без ручного труда;
- [ ] слои policy / orchestration / storage различимы в логах;
- [ ] прогон на ≥ 2 классах задач (M и S) прошёл успешно.

Формально: отклонение от чек-листа — преждевременная заморозка.

## 11. Риски

| Риск | Митигация |
|---|---|
| Схема окажется жёсткой | старт с минимума; неизвестные поля — warning; расширение по журналу |
| Список операций разрастётся | лимит 10; новые — только при повторяющейся потребности |
| Re-raise станет бюрократией | 4 категории; поля — только нужные; owner_override вне метрики |
| Соблазн начать MCP раньше | чек-лист §8 формален; обход = преждевременная заморозка |
| Session-commit тратит шаги | правило останова (§6); «постоянный» пакет без лишних гейтов |
| Процесс-ветка усложняет git | минимальная политика: отдельный коммит, теги, без merge в `develop` |
| S-пилот «назначен», а не естественен | класс фиксирует `analyst`; при отсутствии S — честный M, S — позже |

## Приложение A. git-MCP (следующий горизонт, после отладки файлового MCP)

Владелец планирует реализовать git-MCP под проект. Эскиз, согласованный с
решением по process-commit:

- **операции** (идемпотентные; они же — будущие инструменты): `git.status`
  (read-only), `git.checkpoint(run, session)`, `git.commit(product_package)`,
  `git.merge_to_develop(task)`, `git.push`, `git.branch_create` /
  `git.branch_delete`, `git.tag`;
- **права по инструментам** (вместо ролей): `lead` — `status` + `checkpoint`;
  `git` — полный набор (или тонкая policy-роль поверх MCP); сервисная сессия —
  пакеты канона; пакеты исполняются по подтверждению из ленты;
- **отношение к process-MCP (§5–§8)**: другой слой — git-MCP исполняет
  действия, process-MCP хранит состояние; общий принцип — MCP исполняет
  принятое решение и не принимает его сам;
- команды `/git/*` остаются фасадом TUI и после внедрения git-MCP; scope и
  дизайн — отдельной задачей после отладки файлового MCP.
