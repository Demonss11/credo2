# BRIEF: журнал вопросов и решений (Q/D)

**Статус:** канон процесса · **Ревизия:** 2026-09-29 · **Область:** `prototypes/credo2/docs/`

Журнал фиксирует **почему** система устроена именно так: от открытого вопроса (Q)
до принятого решения (D), требования к поведению (feature) и задачи по коду (T-XX).
Карта документации — [`README.md`](README.md), сводная таблица связей —
[`TRACEABILITY.md`](TRACEABILITY.md).

## Зачем журнал

Журнал разбит на отдельные записи: **один вопрос — один файл, одно решение — один
файл**. Так diff читаемый, ссылки стабильные, каждую запись можно найти и обсудить
отдельно.

Принципы:

1. **Один факт — один канон** ([D60](decisions/D60-docs-ownership-sync.md), политика
   Q41): полный текст вопроса или решения — только в его файле, остальные документы
   ссылаются, а не копируют. Роли документов определены
   [D60](decisions/D60-docs-ownership-sync.md) и §10
   [`SPECIFICATION.md`](SPECIFICATION.md) — здесь только ссылка.
2. **Ссылка, не копия; время жизни адреса** ([D65](decisions/D65-reference-policy.md)):
   ссылка из канона допустима только на артефакт, который штатно не удаляется.
3. **ID стабильны.** `Qn`, `Dn` и `T-XX` не переиспользуются и не меняются; ссылка
   ведёт на ID и путь файла, а не на номер строки.
4. **Записи не удаляются.** `dropped` и `superseded` — это статусы, а не удаление:
   история нужна аудиту.
5. **Решение не обязано менять продукт.** Инфраструктурные, процессные и «отказные»
   решения фиксируются так же, как функциональные, — с вердиктом сверки с кодом.

## 1. Структура

| Путь | Тип | Канон чего |
|---|---|---|
| `questions/Qn.md` | Q | формулировка вопроса: контекст, варианты, рекомендация |
| `decisions/Dn-<слаг>.md` | D | полный контекст решения: выбор, следствия, сверка с кодом, альтернативы |
| [`TRACEABILITY.md`](TRACEABILITY.md) | сводка | связи Q → D → задача → реализация и жизненный цикл ([D63](decisions/D63-journal-index-lifecycle.md)) |
| [`SPECIFICATION.md`](SPECIFICATION.md) §10 | таблица | краткая формулировка решения (номер, обоснование, ссылка на D) |
| [`features/README.md`](features/README.md) | сводка | статусы, приоритеты и счётчики требований |
| [`tasks/`](tasks/README.md) | реестр | задачи по коду — следствия решений (поле «Источник» — `Dn`/`Qn`) |

[`questions/README.md`](questions/README.md) и
[`decisions/README.md`](decisions/README.md) — рабочие сводки, **не канон**
([D63](decisions/D63-journal-index-lifecycle.md)).

## 2. Идентификаторы

**Q — вопрос.** Сквозной номер в порядке появления: `Q1`, `Q2`, … Файл —
`questions/Qn.md`, без слага.

**D — решение.** Номер `Dn` **равен номеру строки решения в
[`SPECIFICATION.md`](SPECIFICATION.md) §10**: решение по Q1 зафиксировано в §10 под
№15 → файл `decisions/D15-evolution-credo2.md`. `D15` и «решение №15» в документах и
коде — одно и то же; второй нумерации нет. §10 — **краткий канон** (номер,
формулировка, обоснование, ссылка на D-файл), D-файл — **полным контекстом**.

Слаг — короткий, латиница, `kebab-case` (`D15-evolution-credo2`). Выбранный слаг
не переименовывается: переименование файла ломает ссылки.

**Ссылки.** Только ID + относительный markdown-путь, как в примерах выше:
`` `[Q1](../questions/Q1.md)` `` из файла вопроса и
`` `[`D15`](../decisions/D15-evolution-credo2.md)` `` из документа-потребителя.
Не ссылайтесь на номер строки и не дублируйте чужой текст — вместо копии ставьте
ссылку ([D65](decisions/D65-reference-policy.md)).

## 3. Жизненный цикл

```
Q (open) ──► D (accepted) ──► feature (added/updated) ──► задача T-XX (tasks/)
   │
   └─────► Q (dropped) — снят без решения

D (accepted) ──► D (superseded by Dm) — заменён новым решением
             └─► D (rejected) — рассмотрен и отклонён

T-XX: ⬜ открыта ──► 🚧 в работе ──► ✅ сделана
```

Статусы: **Q** — `open` · `resolved by Dm` · `dropped`; **D** — `accepted` ·
`superseded by Dm` · `rejected`; **T** — ⬜ открыта · 🚧 в работе · ✅ сделана.
Приоритет Q: 🔴 блокер · 🟡 важно · ⚪ оформление; приоритет задачи — P1–P3
([`tasks/README.md`](tasks/README.md)). Решение без изменения поведения
(процесс, инфраструктура, отказ) — `Affects: —`; при смене поведения требование
и обратная ссылка — по §5.6. Задачи порождает сверка с кодом (§5.3): расхождение
в периметре MVP — задача `T-XX`, иначе фиксируется «задач не требуется».
Пошаговый порядок — рецепты §5.

Жизненный цикл в `TRACEABILITY.md` ([D63](decisions/D63-journal-index-lifecycle.md)):
`open` · `resolved` · `in work` · `done` · `dropped`.

## 4. Шаблоны

### Вопрос

```markdown
# Q7: Краткая формулировка вопроса

- **Статус:** open
- **Дата:** YYYY-MM-DD
- **Приоритет:** 🔴 блокер | 🟡 важно | ⚪ оформление
- **Связано:** Q3, D15, `SPECIFICATION.md` §5, `features/README.md`

## Контекст

Что не сходится или чего не хватает; почему это важно.

## Вопрос

Что именно нужно решить.

## Варианты

- (а) …; (б) …; (в) …

## Рекомендация

Что предлагается и почему (может отсутствовать).
```

### Решение

```markdown
# D7: Краткая формулировка решения

- **Статус:** accepted
- **Дата:** YYYY-MM-DD
- **Resolves:** [Q7](../questions/Q7.md)
- **Спека:** `SPECIFICATION.md` §10, решение №7
- **Affects:** [`features/README.md`](../features/README.md) (шапка) | —
- **Tasks:** T-XX, T-YY | — (см. «Сверка с кодом»)

## Контекст

В чём была проблема (кратко, без пересказа вопроса).

## Решение

Что решили и как это устроено.

## Следствия

Что меняется: документы, код, ограничения; что делать дальше.

## Сверка с кодом

Вердикт: ✅ соответствует · 🟡 расхождение · ⬜ не реализовано · ⚪ не применимо
(процесс/документы). Что проверено, где в коде, какие тесты прогнаны. Если
расхождение в периметре MVP — ссылки на задачи `T-XX`; иначе — триггер возврата.

## Альтернативы

Что отклонили и почему.
```

## 5. Рецепты

### 5.1 Завести вопрос

1. Возьмите следующий свободный `Qn` (проверьте `questions/` и `TRACEABILITY.md`).
2. Создайте `questions/Qn.md` по шаблону; статус — `open`; добавьте строку в
   [`questions/README.md`](questions/README.md).
3. Занесите строку в `TRACEABILITY.md` (D, feature и задачи пусты).
4. Если вопрос — расхождение документа с кодом: понизьте статус затронутого
   требования до 🟡 в `features/README.md`.

### 5.2 Принять решение

1. Возьмите следующий свободный номер §10 → это `Dn`.
2. Создайте `decisions/Dn-<слаг>.md`; заполните `Resolves`, `Affects`, следствия
   и альтернативы.
3. Сверьте решение с кодом (§5.3) и зафиксируйте вердикт.
4. В `SPECIFICATION.md` §10 добавьте строку решения со ссылкой на D-файл.
5. В `questions/Qn.md` смените статус на `resolved by Dn`.
6. Если `Affects` не пуст — обновите требования и оставьте в них обратную ссылку.
7. Добавьте строку в [`decisions/README.md`](decisions/README.md) (краткая тема —
   без копии формулировки) и обновите `TRACEABILITY.md` (жизненный цикл, «Задачи»,
   «Реализация»).

### 5.3 Сверка решения с кодом

Цель — не оставлять решение «висеть»: проверить, соответствует ли код принятому
решению, и решить, нужна ли задача на доработку. Обязательный шаг для каждого D.

1. Возьмите карту зон ответственности из `features/README.md` →
   «Соответствие коду» (`src/core.rs`, `src/lib.rs`, `src/mcp.rs`, `src/rest.rs`,
   тесты).
2. Определите, что именно сверяется: контракт (имена, поля, коды, схемы),
   поведение (кейсы сценариев), артефакты (пути, файлы), API.
3. Соберите доказательства: чтение кода и тестов; адресный прогон
   (`cargo test <тест>`), если он нужен, выполняет `validator` (запрос — через
   `lead`) — `migrator` сам `cargo` не запускает; для MCP/REST — ручной прогон
   по сценарию из `features/`.
4. Зафиксируйте вердикт в D-файле (раздел «Сверка с кодом»):

   | Вердикт | Что значит | Действия |
   |---|---|---|
   | ✅ соответствует | код уже реализует решение | ничего; требование может быть ✅ |
   | 🟡 расхождение | реализовано иначе или частично | статус 🟡 требованию + задача, если в периметре MVP |
   | ⬜ не реализовано | кода нет | ⬜/⏸ требованию; задача — только для MVP (P1–P3) |
   | ⚪ не применимо | решение о процессе, документах или отказе | задач не порождает |

5. Нужна задача → создайте `T-XX-<слаг>/README.md` по шаблону `tasks/`
   (Источник — `Dn (Qn)`), занесите в сводку `tasks/README.md`, в D-файле укажите
   `Tasks: T-XX`, в `TRACEABILITY.md` — в колонку «Задачи».
6. Не нужна → напишите это явно в D-файле: «Задач не требуется: …», чтобы вердикт
   не потерялся.

### 5.4 Снять вопрос (`dropped`)

1. Статус Qn → `dropped`, в тексте — причина (устарел, потерял актуальность,
   поглощён другим вопросом).
2. Если вопрос поглощён другим — укажите в `Связано` основной Q.
3. Обновите `TRACEABILITY.md` (D, feature и задачи — `—`, жизненный цикл `dropped`).

### 5.5 Заменить решение (`superseded`)

1. Новое решение оформляется обычным порядком (новый `Dm`, включая сверку с кодом).
2. В старом Dn статус → `superseded by Dm`; запись остаётся в журнале.
3. Обновите ссылки: требования и код должны вести на актуальное решение;
   открытые задачи `T-XX` — перевесить на `Dm` или закрыть.

### 5.6 Решение меняет поведение (feature)

1. Создайте или обновите требование в `features/`; сценарии — по-русски
   (`# language: ru`), инвентаризацию проверяет
   [`tests/features_inventory.rs`](../tests/features_inventory.rs).
2. В шапке требования — комментарий со ссылкой на решение:
   `# Dn (Qx): краткая формулировка`; отдельного блока `Decisions:` в фичах нет.
3. В D-файле укажите точный путь в `Affects`.
4. Если требование пока не реализовано — статус ⬜/🟡 в `features/README.md`,
   а задачу заводите по вердикту сверки (§5.3): расхождение или отсутствие кода
   в периметре MVP.

### 5.7 Чек-лист перед коммитом

- [ ] ID уникальны, файлы названы по правилам (§2), слаг не менялся.
- [ ] Статусы согласованы: Q ↔ D ↔ `TRACEABILITY.md`.
- [ ] В SPEC §10 есть строка решения со ссылкой на D-файл.
- [ ] У D есть вердикт «Сверка с кодом»; задачи созданы или зафиксировано
      «задач не требуется».
- [ ] Дубликатов текста нет: вместо копии — ссылка
      ([D65](decisions/D65-reference-policy.md)).
- [ ] Относительные ссылки живые (см. §7).
- [ ] DoD прототипа зелёный; порог по составу пакета — [`AGENTS.md`](../AGENTS.md)
      §Сборка и `.opencode/rules/review.md` §«Порог существенности»
      ([D50](decisions/D50-dod-by-package-scope.md)).
- [ ] Сообщение коммита: `docs(Qn): <что>` или `docs(Dn): <что>` (одна запись —
      один коммит).

## 6. TRACEABILITY

Связи журнала централизованы в [`TRACEABILITY.md`](TRACEABILITY.md) — единая
таблица ([D63](decisions/D63-journal-index-lifecycle.md)):

| Q | D | Жизненный цикл | Задачи | Реализация |
|---|---|---|---|---|

- Q и D — ссылки на файлы; «Задачи» — `T-XX` со статусами из
  [`tasks/README.md`](tasks/README.md); «Реализация» — требования ссылкой на
  [`features/README.md`](features/README.md).
- Жизненный цикл: `open` · `resolved` · `in work` · `done` · `dropped` (при
  нескольких задачах — статус по совокупности).
- Таблица — **представление**, а не канон статусов: статусы задач и требований
  берутся из своих канонов, согласованность проверяет тест целостности (§7).
- Строки не удаляются: снятые и заменённые записи остаются с историческим статусом.

## 7. Целостность журнала

Основной механизм — тест `tests/docs_journal.rs`
([D64](decisions/D64-journal-integrity-test.md); задача
[T-18](tasks/T-18-docs-journal-test/README.md)): уникальность и парность ID Q↔D,
строки-представления (каталоги, §10, `TRACEABILITY`), вердикт «Сверка с кодом»,
согласованность `TRACEABILITY`, запреты (ссылки на номера строк, миграционные
маркеры, адреса рабочих данных). Тест входит в DoD `cargo test --all`
([`AGENTS.md`](../AGENTS.md) §Сборка).

Вспомогательный ручной мини-чек (битые относительные ссылки):

```sh
# из корня репозитория credo2
git grep -n -E '\]\(\.\.?/' -- docs
```

Сверки, которые нельзя терять: каждый D имеет вердикт «Сверка с кодом», каждая
задача — источник `Dn`/`Qn`; `TRACEABILITY.md` согласован с файлами и карточками
задач.

## 8. Антипаттерны

- Копировать формулировку решения в SPEC или requirements вместо ссылки.
- Ставить ссылку из канона на удаляемые/сессионные рабочие данные
  (`.opencode/mail/**` — чистит `clean-logs.mjs --mail-only`; `.opencode/state/**`
  — сессионное состояние) — нарушение «времени жизни адреса»
  ([D65](decisions/D65-reference-policy.md)). `docs/analysis/**` — провенанс
  («улики, не канон»), допустим; whitelist —
  [`analysis/findings-registry.md`](analysis/findings-registry.md)
  ([D48](decisions/D48-findings-registry-owner.md)).
- Ссылаться на номер строки (или «строка N» любого файла).
- Переиспользовать номера, переименовывать файлы записей, «чистить историю».
- Закрывать Q без D-файла или заводить D без §10-строки.
- Заводить D без сверки с кодом: решение «висит», расхождение всплывает позже.
- Заводить задачу без источника `Dn`/`Qn` или «на будущее», в отрыве от решения.
- Молча править канон при расхождении с кодом: расхождение — это Q или задача.

Роли процесса и рабочая группа агентов — канон [`AGENTS.md`](../AGENTS.md)
(§Рабочая группа агентов).
