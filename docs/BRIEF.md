# BRIEF: журнал вопросов и решений (Q/D)

**Статус:** канон процесса · **Ревизия:** 2026-09-26 · **Область:** `prototypes/credo2/docs/`

Журнал фиксирует **почему** система устроена именно так: от открытого вопроса (Q)
до принятого решения (D), требования к поведению (feature) и задачи по коду (T-XX).
Карта документации — [`README.md`](README.md), сводная таблица связей —
[`TRACEABILITY.md`](TRACEABILITY.md).

## Зачем журнал

Раньше вопросы и решения жили одним файлом `OPEN_QUESTIONS.md` (42 записи, ~190 КБ):
точечно читать нельзя, diff теряется, ссылка ведёт «в середину текста». Журнал
разбивает его на отдельные записи: **один вопрос — один файл, одно решение — один
файл**. Так diff читаемый, ссылки стабильные, каждую запись можно найти и обсудить
отдельно.

Принципы:

1. **Один факт — один канон** (политика Q41). Полный текст вопроса или решения —
   только в его файле; остальные документы ссылаются, а не копируют.
2. **ID стабильны.** `Qn`, `Dn` и `T-XX` не переиспользуются и не меняются; ссылка
   ведёт на ID и путь файла, а не на номер строки.
3. **Записи не удаляются.** `dropped` и `superseded` — это статусы, а не удаление:
   история нужна аудиту.
4. **Решение не обязано менять продукт.** Инфраструктурные, процессные и «отказные»
   решения фиксируются так же, как функциональные, — с вердиктом сверки с кодом.

## 1. Структура

| Путь | Тип | Канон чего |
|---|---|---|
| `questions/Qn.md` | Q | формулировка вопроса: контекст, варианты, рекомендация |
| `decisions/Dn-<слаг>.md` | D | полный контекст решения: выбор, следствия, сверка с кодом, альтернативы |
| `TRACEABILITY.md` | сводка | связи Q → D → feature → задача и статусы |
| `SPECIFICATION.md` §10 | таблица | краткая формулировка решения (номер, обоснование, ссылка на D) |
| `features/README.md` | сводка | статусы, приоритеты и счётчики требований |
| `tasks/` | реестр | задачи по коду — следствия решений (поле «Источник» — `Dn`/`Qn`) |
| `OPEN_QUESTIONS.md` | архив | исходный текст до конца миграции: очередь и указатели |

## 2. Идентификаторы

**Q — вопрос.** Сквозной номер в порядке появления: `Q1`, `Q2`, … `Q42` (до миграции),
далее `Q43` и т. д. Файл — `questions/Qn.md`, без слага.

**D — решение.** Номер `Dn` **равен номеру строки решения в `SPECIFICATION.md` §10**:

- решение по Q1 зафиксировано в §10 под №15 → файл
  `decisions/D15-evolution-credo2.md`;
- `D15` и «решение №15» в документах и коде — одно и то же; второй нумерации нет;
- §10 остаётся **кратким каноном** (номер, формулировка, обоснование, ссылка на
  D-файл), D-файл — **полным контекстом**.

**Новое решение:**

1. добавьте строку в `SPECIFICATION.md` §10 (следующий свободный номер);
2. создайте `decisions/D<номер>-<слаг>.md` по шаблону §4;
3. свяжите с вопросом (`Resolves`), сверьте с кодом (§5.3), обновите
   `TRACEABILITY.md`.

Слаг — короткий, латиница, `kebab-case` (`D15-evolution-credo2`). Выбранный слаг
не переименовывается: переименование файла ломает ссылки.

**Ссылки.** Только ID + относительный markdown-путь, как в примерах выше:
`` `[Q1](../questions/Q1.md)` `` из файла вопроса и `` `[`D15`](../decisions/D15-evolution-credo2.md)` ``
из документа-потребителя. Не ссылайтесь на номер строки и не
дублируйте чужой текст — вместо копии ставьте ссылку.

## 3. Жизненный цикл

```
Q (open) ──► D (accepted) ──► feature (added/updated) ──► задача T-XX (tasks/)
   │
   └─────► Q (dropped) — снят без решения

D (accepted) ──► D (superseded by Dm) — заменён новым решением
             └─► D (rejected) — рассмотрен и отклонён

T-XX: ⬜ открыта ──► 🚧 в работе ──► ✅ сделана
```

Порядок действий при решении вопроса:

1. Появился вопрос → `questions/Qn.md`, статус `open`.
2. Вопрос решён → `decisions/Dm-<слаг>.md`, поле `Resolves`; в Qn — статус
   `resolved by Dm`.
3. Решение меняет поведение системы → обновляется или создаётся требование в
   `features/`; в D — `Affects`, в требовании — обратная ссылка `Decisions`.
4. Решение без изменения поведения (процесс, инфраструктура, отказ) → `Affects: —`.
5. **Сверка с кодом** (§5.3): вердикт «соответствует / расхождение / не
   реализовано / не применимо»; при расхождении в периметре MVP заводится задача
   `T-XX` (или фиксируется «задач не требуется»).
6. Обновляется `TRACEABILITY.md` (включая колонку «Задачи»).

Статусы: **Q** — `open` · `resolved by Dm` · `dropped`; **D** — `accepted` ·
`superseded by Dm` · `rejected`; **T** — ⬜ открыта · 🚧 в работе · ✅ сделана.
Приоритет Q (наследие `OPEN_QUESTIONS.md`): 🔴 блокер · 🟡 важно · ⚪ оформление.
Приоритет задачи: P1–P3 (`tasks/README.md`).

## 4. Шаблоны

### Вопрос

```markdown
# Q7: Краткая формулировка вопроса

- **Статус:** open
- **Дата:** YYYY-MM-DD
- **Приоритет:** 🔴 блокер | 🟡 важно | ⚪ оформление
- **Связано:** Q3, D15, `SPECIFICATION.md` §5, `features/README.md`
- **Перенос:** YYYY-MM-DD, из `OPEN_QUESTIONS.md` (для мигрированных записей)

## Контекст

Что не сходится или чего не хватает; почему это важно.

## Вопрос

Что именно нужно решить.

## Варианты

- (а) …; (б) …; (в) …

## Рекомендация

Что предлагается и почему (может отсутствовать).
```

### Решение

```markdown
# D7: Краткая формулировка решения

- **Статус:** accepted
- **Дата:** YYYY-MM-DD
- **Resolves:** [Q7](../questions/Q7.md)
- **Спека:** `SPECIFICATION.md` §10, решение №7
- **Affects:** [`features/README.md`](../features/README.md) (шапка) | —
- **Tasks:** T-XX, T-YY | — (см. «Сверка с кодом»)

## Контекст

В чём была проблема (кратко, без пересказа вопроса).

## Решение

Что решили и как это устроено.

## Следствия

Что меняется: документы, код, ограничения; что делать дальше.

## Сверка с кодом

Вердикт: ✅ соответствует · 🟡 расхождение · ⬜ не реализовано · ⚪ не применимо
(процесс/документы). Что проверено, где в коде, какие тесты прогнаны. Если
расхождение в периметре MVP — ссылки на задачи `T-XX`; иначе — триггер возврата.

## Альтернативы

Что отклонили и почему.
```

## 5. Рецепты

### 5.1 Завести вопрос

1. Возьмите следующий свободный `Qn` (проверьте `questions/` и `TRACEABILITY.md`).
2. Создайте `questions/Qn.md` по шаблону; статус — `open`.
3. Занесите строку в `TRACEABILITY.md` (D, feature и задачи пусты).
4. Если вопрос — расхождение документа с кодом: понизьте статус затронутого
   требования до 🟡 в `features/README.md`.

### 5.2 Принять решение

1. Возьмите следующий свободный номер §10 → это `Dn`.
2. Создайте `decisions/Dn-<слаг>.md`; заполните `Resolves`, `Affects`, следствия
   и альтернативы.
3. Сверьте решение с кодом (§5.3) и зафиксируйте вердикт.
4. В `SPECIFICATION.md` §10 добавьте строку решения со ссылкой на D-файл.
5. В `questions/Qn.md` смените статус на `resolved by Dn`.
6. Если `Affects` не пуст — обновите требования и оставьте в них обратную ссылку.
7. Обновите `TRACEABILITY.md`.

### 5.3 Сверка решения с кодом

Цель — не оставлять решение «висеть»: проверить, соответствует ли код принятому
решению, и решить, нужна ли задача на доработку. Обязательный шаг для каждого D,
в том числе переносимого (§7).

1. Возьмите карту зон ответственности из `features/README.md` →
   «Соответствие коду» (`src/core.rs`, `src/lib.rs`, `src/mcp.rs`, `src/rest.rs`,
   тесты).
2. Определите, что именно сверяется: контракт (имена, поля, коды, схемы),
   поведение (кейсы сценариев), артефакты (пути, файлы), API.
3. Соберите доказательства: чтение кода и тестов; адресный прогон
   (`cargo test <тест>`), если он нужен, выполняет `validator` (запрос — через
   `lead`) — `migrator` сам `cargo` не запускает; для MCP/REST — ручной прогон
   по сценарию из `features/`.
4. Зафиксируйте вердикт в D-файле (раздел «Сверка с кодом»):

   | Вердикт | Что значит | Действия |
   |---|---|---|
   | ✅ соответствует | код уже реализует решение | ничего; требование может быть ✅ |
   | 🟡 расхождение | реализовано иначе или частично | статус 🟡 требованию + задача, если в периметре MVP |
   | ⬜ не реализовано | кода нет | ⬜/⏸ требованию; задача — только для MVP (P1–P3) |
   | ⚪ не применимо | решение о процессе, документах или отказе | задач не порождает |

5. Нужна задача → создайте `T-XX-<слаг>/README.md` по шаблону `tasks/`
   (Источник — `Dn (Qn)`), занесите в сводку `tasks/README.md`, в D-файле укажите
   `Tasks: T-XX`, в `TRACEABILITY.md` — в колонку «Задачи».
6. Не нужна → напишите это явно в D-файле: «Задач не требуется: …», чтобы вердикт
   не потерялся.

### 5.4 Снять вопрос (`dropped`)

1. Статус Qn → `dropped`, в тексте — причина (устарел, потерял актуальность,
   поглощён другим вопросом).
2. Если вопрос поглощён другим — укажите в `Связано` основной Q.
3. Обновите `TRACEABILITY.md` (D, feature и задачи — `—`, статус `dropped`).

### 5.5 Заменить решение (`superseded`)

1. Новое решение оформляется обычным порядком (новый `Dm`, включая сверку с кодом).
2. В старом Dn статус → `superseded by Dm`; запись остаётся в журнале.
3. Обновите ссылки: требования и код должны вести на актуальное решение;
   открытые задачи `T-XX` — перевесить на `Dm` или закрыть.

### 5.6 Решение меняет поведение (feature)

1. Создайте или обновите требование в `features/`; сценарии — по-русски
   (`# language: ru`), инвентаризацию проверяет `tests/features_inventory.rs`.
2. В шапке требования — комментарий со ссылкой на решение:
   `# Dn (Qx): краткая формулировка`; отдельного блока `Decisions:` в фичах нет.
3. В D-файле укажите точный путь в `Affects`.
4. Если требование пока не реализовано — статус ⬜/🟡 в `features/README.md`,
   а задачу заводите по вердикту сверки (§5.3): расхождение или отсутствие кода
   в периметре MVP.

### 5.7 Чек-лист перед коммитом

- [ ] ID уникальны, файлы названы по правилам (§2), слаг не менялся.
- [ ] Статусы согласованы: Q ↔ D ↔ `TRACEABILITY.md`.
- [ ] В SPEC §10 есть строка решения со ссылкой на D-файл.
- [ ] У D есть вердикт «Сверка с кодом»; задачи созданы или зафиксировано
      «задач не требуется».
- [ ] Дубликатов текста нет: вместо копии — ссылка.
- [ ] Относительные ссылки живые (см. §9).
- [ ] DoD прототипа зелёный: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
      `cargo test --all` (полный прогон выполняет только `validator`; роли,
      работающие с кодом, ограничиваются компиляцией `fmt`/`check`/`clippy`).
- [ ] Сообщение коммита: `docs(Qn): <что>` или `docs(Dn): <что>` (одна запись — один коммит).

## 6. TRACEABILITY.md

Формат строки: `| Q | D | Feature | Задачи | Статус |`, где Q и D — ссылки на файлы,
Feature — требование или `—`, Задачи — `T-XX` (или `—`), статус — статус вопроса
(`open` / `resolved by Dn` / `dropped`). Таблица:

- заполняется при каждой записи или смене статуса;
- не удаляет строки: снятые и заменённые записи остаются с историческим статусом;
- охватывает только перенесённые записи; до конца миграции остальные Q — в
  `OPEN_QUESTIONS.md`.

В перспективе таблица может собираться скриптом из полей `Resolves`, `Affects`
и `Tasks`; до этого — вручную и без «пропусков по невнимательности» (см. §5.7).

## 7. Миграция `OPEN_QUESTIONS.md`

Цели: разобрать архив на записи, сохранив ID и историю; не иметь двух канонов
одного текста в один момент; по ходу — сверить каждое решение с кодом и
пополнить/закрыть реестр задач; после завершения удалить архив.

Правила:

- **Перенос — это вырезание.** Полный текст уходит в `questions/Qn.md` и
  `decisions/Dn-<слаг>.md`; в архиве остаётся короткий указатель на файлы.
  Копии не остаётся — иначе нарушается «один факт — один канон».
- **ID и даты сохраняются.** `Qn` — как в архиве; `Dn` — номер решения в §10
  (если решения в §10 ещё нет, сначала добавьте строку).
- **Сверка с кодом — часть переноса** (§5.3): у каждого перенесённого D есть
  вердикт; расхождение в периметре MVP порождает задачу, отсутствие расхождений
  фиксируется явно.
- **Порядок:** разделы 0 → 7, внутри — по возрастанию Q; сначала решённые, потом
  открытые. Порядок согласован с приоритетом кодинга: разделы 2–5 закрывают
  решения, на которых стоят P1-задачи. Оформление идёт блоками по 2–5 записей
  за сессию, по одному вопросу на коммит.
- **Архив больше не пополняется.** После старта миграции новые вопросы заводятся
  только в `questions/Qn.md` (§5.1); `OPEN_QUESTIONS.md` — источник переноса.
- **Вопрос, закрытый «попутно»** (например, Q6 при Q5): отдельного D нет —
  запись ссылается на решение основного вопроса и помечается «закрыт попутно».
- **Вопрос без архитектурного решения** (процесс, документация): решение
  оформляется D-файлом (сверка — ⚪); сквозное — дополнительно ADR в корневом
  `DECISIONS.md`, и D-файл ссылается на ADR.

Шаги переноса одного вопроса:

1. Создайте `questions/Qn.md`: контекст, вопрос, варианты, рекомендация, статус.
2. Создайте `decisions/Dn-<слаг>.md`: полное решение, следствия, альтернативы.
3. Сверьте решение с кодом и решите судьбу задач (§5.3): создать `T-XX`,
   обновить существующую или зафиксировать «задач не требуется».
4. В `OPEN_QUESTIONS.md` замените блок вопроса указателем:
   `### Qn. → перенесён` + ссылки на оба файла.
5. Обновите `TRACEABILITY.md` (включая колонку «Задачи»).
6. Обновите обратные ссылки: `SPECIFICATION.md` §10 (строка решения),
   `features/README.md` и требования, `tasks/README.md` и карточки,
   корневой `DECISIONS.md`, `AGENTS.md`.
7. Прогоните чек-лист §5.7 и DoD прототипа.

Критерий завершения миграции:

- все Q оформлены файлами, в архиве не осталось полных текстов;
- у каждого перенесённого D есть вердикт сверки с кодом; задачи из сверок заведены;
- в проекте не осталось ссылок на `OPEN_QUESTIONS.md` (кроме исторических
  записей `CHANGELOG.md`);
- архив удалён;
- шапка `SPECIFICATION.md` §10 и `AGENTS.md` переведены на журнал;
- тест целостности журнала (§9) добавлен.

## 8. Стратегия: миграция и кодинг

**Вопрос:** переносить сначала все Q, а потом возвращаться к коду — или совмещать?

**Ответ: совмещать, полная миграция не является гейтом кодинга.** Все 42 решения
уже приняты — журнал не создаёт новых решений, а приводит документацию к
структуре, удобной для чтения и ссылок. Кодинг обеспечен задачами (P1: T-01…T-05)
и может идти параллельно.

Интерфейс между двумя потоками — реестр задач `tasks/`:

- **миграция** разбирает Q → D, сверяет D с кодом (§5.3) и **порождает или
  закрывает** задачи;
- **кодинг** берёт из реестра задачи P1–P3 и закрывает их;
- связь двусторонняя: D → `Tasks: T-XX`, задача → `Источник: Dn (Qn)`,
  `TRACEABILITY.md` показывает обе стороны.

Рекомендуемый режим:

1. **Блоками по разделам архива**, 2–5 записей за сессию: маленькие diff, свежий
   контекст, быстрый прогресс. Не «всё сразу» и не по одной записи.
2. **Одна сессия — одно занятие:** либо блок миграции (docs-коммиты), либо задачи
   кода (code-коммиты). Смешивать занятия в одном коммите нельзя.
3. **Кодинг не ждёт:** P1-задачи можно брать в любой момент; миграция продолжается
   следующим блоком, а не «когда-нибудь потом».
4. **Stop-состояние без дедлайна:** для демо достаточно, чтобы новые Q шли в
   журнал, у задач были источники, а архив не пополнялся. Полное удаление архива —
   по критерию §7, в своём темпе.

Допустимое исключение: если нужно быстро закрыть архив — можно выделить
2–3 сессии только под миграцию (документационный спринт). Правило «одно занятие —
один коммит» сохраняется и там.

## 9. Проверка целостности

Сейчас — вручную, чек-листом §5.7. Быстрая проверка ссылок:

```sh
# из корня репозитория credo2: показать все относительные ссылки документации
git grep -n -E '\]\(\.\.?/' -- docs
```

Сверки, которые нельзя терять:

- каждый D имеет вердикт «Сверка с кодом», а каждая задача — источник `Dn`/`Qn`;
- `TRACEABILITY.md` согласован с файлами и карточками задач.

План (v0.x): тест `tests/docs_journal.rs`, который проверяет уникальность ID,
парность Q ↔ D, наличие вердикта сверки и согласованность `TRACEABILITY.md`
с файлами и задачами. До его появления расхождениями считаются только те, что
видны по чек-листу; «тихих» исключений нет.

## 10. Роли

- **Владелец** — принимает решения, утверждает приоритеты задач, мержит, отвечает
  за канон; правки журнала без принятого решения не допускаются.
- **Агент** — оформляет записи по этому BRIEF, выполняет сверку с кодом, готовит
  задачи и коммиты, поднимает замеченные расхождения новым Q или задачей;
  не переписывает принятые решения «задним числом».
- **Читатель** — идёт по цепочке `TRACEABILITY.md` → D → Q → feature → задача.

## 11. Антипаттерны

- Копировать формулировку решения в SPEC или requirements вместо ссылки.
- Ссылаться на «`OPEN_QUESTIONS.md`, строка N» или на любой номер строки.
- Переиспользовать номера, переименовывать файлы записей, «чистить историю».
- Закрывать Q без D-файла или заводить D без §10-строки.
- Переносить D без сверки с кодом: решение «висит», расхождение всплывает позже.
- Заводить задачу без источника `Dn`/`Qn` или «на будущее», в отрыве от решения.
- Пополнять `OPEN_QUESTIONS.md` после старта миграции.
- Молча править канон при расхождении с кодом: расхождение — это Q или задача.
