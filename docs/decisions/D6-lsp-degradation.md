## Контекст

[`SPECIFICATION.md`](../SPECIFICATION.md) §10 п. 6 фиксировал «Нет fallback
при падении LSP; перезапуск sidecar», тогда как
[`lsp_notebook.feature`](../features/lsp_notebook.feature) обещал
автоперезапуск + уведомление + «состояние открытых файлов восстанавливается».
Неясно было, что значит «нет fallback» (есть ли в UI второй движок
диагностики) и что именно восстанавливается — диагностики, позиция курсора,
несохранённые правки. Полный контекст — [Q39](../questions/Q39.md). Решение
связано с составом LSP ([Q38](../questions/Q38.md),
[D18](D18-pipelines-out-lsp-mvp.md)) и единым механизмом исполнения из
редактора ([Q33](../questions/Q33.md),
[D30](D30-execution-mechanism.md)).

## Решение

1. **«Нет fallback» — нет второго движка.** При недоступности sidecar функции
   LSP (диагностика, автодополнение, семантическая подсветка) **недоступны**;
   редактор работает как обычный текстовый. Встроенной в UI альтернативы нет:
   `dar-core` доступен только через LSP ([Q33](../questions/Q33.md),
   [D30](D30-execution-mechanism.md) — локального исполнения в UI нет).
2. **Восстанавливается серверная сессия, а не «состояние» файлов.** Буферы,
   курсор, скролл и undo — клиентские (CodeMirror), падение sidecar их не
   теряет. После перезапуска клиент выполняет `initialize` и повторный
   `didOpen` по всем открытым документам с **текущим** текстом (включая
   несохранённые правки); сервер заново публикует диагностику.
3. **Ограничение автоперезапуска.** Автопопытки подряд ограничены (канон —
   **три**); после их исчерпания автоперезапуск прекращается, пользователь
   видит уведомление «Сервер языка недоступен» и может перезапустить сервер
   **вручную**. Бесконечный цикл падений исключён.
4. **Деградация не блокирует работу.** Во время недоступности LSP
   редактирование и сохранение продолжаются, буферы и несохранённые правки
   сохраняются; выполнение правила (`check.test` через MCP,
   [Q33](../questions/Q33.md)) от LSP не зависит.

## Следствия

- **Требования:** `lsp_notebook.feature` — сценарий «Перезапуск LSP при
  падении» уточнён (повторный `initialize`/`didOpen` с текущим текстом,

  как текстовый, `check.test` не блокируется) и «Повторные падения прекращают

- **SPEC:** §10 п. 6 переформулирован: «нет fallback» = нет второго движка;

## Альтернативы

- **Встроенный fallback в UI (второй движок диагностики без LSP)** —
  отклонено: дублирует ядро (`dar-core`), даёт расхождение «подсветка без LSP
  vs через LSP» и скрытые fallback-пути; противоречит единому движку
  ([Q33](../questions/Q33.md), [D30](D30-execution-mechanism.md)).
- **Безлимитный автоперезапуск sidecar** — отклонено: при устойчивом падении
  (например, битый sidecar) даёт бесконечный цикл; лимит трёх попыток подряд с
  переходом на ручной перезапуск предсказуем.
- **«Восстанавливать состояние открытых файлов» (буферы/курсор) со стороны
  сервера** — отклонено: это клиентское состояние (CodeMirror); сервер
  восстанавливает лишь свою сессию (`initialize` + повторный `didOpen` с
  текущим текстом).
- **Блокировать редактирование/сохранение до подъёма LSP** — отклонено:
  деградация не должна мешать работе; `check.test` через MCP
  ([Q33](../questions/Q33.md)) от LSP не зависит.
