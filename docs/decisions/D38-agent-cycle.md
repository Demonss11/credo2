# D38: Цикл агентов — Agile-петля, единый тестировщик, память и почта

- **Статус:** accepted
- **Дата:** 2026-09-26
- **Resolves:** [Q43](../questions/Q43.md)
- **Спека:** [`SPECIFICATION.md`](../SPECIFICATION.md) §10, решение №38
- **Affects:** [`AGENTS.md`](../../AGENTS.md) §Рабочая группа агентов;
  [`../../.opencode/agents/`](../../.opencode/agents/);
  [`.opencode/rules/review.md`](../../.opencode/rules/review.md);
  [`.opencode/rules/git-workflow.md`](../../.opencode/rules/git-workflow.md);
  [`BRIEF.md`](../BRIEF.md) (прогоны тестов — только `validator`)
- **Tasks:** [T-11](../tasks/T-11-agent-cycle/README.md)

## Контекст

Пилот T-01 прошёл маршрутом `coder → rust-expert → tester → validator →
docs-writer` (водопад) и выявил: полный `cargo test` гонялся четырьмя ролями
плюс служебной сессией (4+ прогона на задачу), обрывы сессий пришлись именно на
тяжёлые прогоны и теряли отчёты, а требования к маршруту дублировались между
`AGENTS.md`, `lead.md` и промптами ролей (расхождения «инструкция ↔ права»).
Понадобился целевой цикл команды: маршрут с возвратами, единая точка
тестирования, межсессионная память и передача отчётов. Формулировка вопроса —
[Q43](../questions/Q43.md).

## Решение

Принят цикл **Agile-петля с отдельным лидером** (требования R1–R5 — в карточке
[T-11](../tasks/T-11-agent-cycle/README.md), здесь — суть; детали и находки Н1–Н14
не дублируются, см. карточку):

- **R1. Agile-петля вместо водопада.** `coder` реализует → `rust-expert` доводит
  код (идиоматика) → `tester` **добавляет тесты** → `validator` оценивает
  покрытие, тестирует и при необходимости возвращает `coder` на доработку (цикл
  повторяется); после валидации — `docs-writer` (статусы) и `git`.
- **R2. Тестирует только `validator`.** `cargo test` и полный DoD-прогон — только
  у `validator`; компиляционная обратная связь (`cargo check`/`clippy`/`fmt`)
  тестированием не является и допустима у ролей, работающих с кодом.
- **R3. Межсессионная память роли.** У каждого агента — свой файл памяти
  `.opencode/memory/<роль>.md`: перед завершением контекст сбрасывается в файл,
  при возврате на доработку агент читает его первым.
- **R4. Межагентская почта.** Общая лента кратких отчётов задачи
  `.opencode/mail/<T-XX>.md` — «глобальная сессия»: агент дописывает отчёт,
  последующие читают в рамках задачи (один писатель на файл, append).
- **R5. Отчёт до и после тяжёлых операций.** Отчёт пишется **до** тяжёлых
  операций (тесты) и обновляется **после** — сессии обрываются именно на них.

Решения владельца (2026-09-26, см. карточку):

1. **Лидер — отдельная роль**, переработанный `lead` (не `validator`): меньше
   нагрузки на проверяющего, сохраняется независимость приёмки; `validator`
   остаётся единственным тестировщиком и приёмщиком.
2. **Компиляция разрешена** (`cargo check`/`clippy`/`fmt`) у ролей, работающих с
   кодом; любой запуск тестов — только `validator`.
3. **Почта — файл на задачу** (`.opencode/mail/<T-XX>.md`) как «глобальная
   сессия».
4. **Лимиты шагов добавляются** (`steps`); приоритет — экономия токенов;
   git — пакетное подтверждение после приёмки и идемпотентность при обрыве.

## Следствия

- `AGENTS.md` §Рабочая группа агентов — единый канон цикла; роли ссылаются на
  него, не дублируя маршрут (Q41, Н9).
- `.opencode/agents/**` пересобираются: `lead` — лидер Agile-петли с
  `question: allow` и `subagent`-правами (код/документы не правит); `validator` —
  единственная роль с `cargo test --all` и полным DoD; `coder`, `rust-expert` —
  компиляция без тестов; `tester` — пишет тесты, не запускает их; `docs-writer` —
  без cargo (промежуточное разрешение `cargo test` в рабочем дереве откатывается).
- `.opencode/rules/review.md` и `.opencode/rules/git-workflow.md` — чекпойнты,
  идемпотентность и пакетное подтверждение git.
- Память и почта — операционные данные, не канон (Q41); в `.opencode/agents/**`
  их размещать нельзя (любой `.md` там парсится как агент).
- `docs/BRIEF.md`: прогон тестов при ведении журнала выполняет только `validator`;
  `migrator` сверку с кодом вправе делать чтением.
- Реализация — задача [T-11](../tasks/T-11-agent-cycle/README.md) (DoD и приёмка —
  в карточке); пилот по новому циклу — там же.

## Сверка с кодом

Вердикт: ⚪ **не применимо** — решение процессное (маршрут команды агентов,
память и почта ролей). Контрактов, поведения и артефактов `credo2` оно не
затрагивает; кода, который бы ему «соответствовал», нет.

Что проверено (чтением, без прогонов `cargo` — R2): карточка
[T-11](../tasks/T-11-agent-cycle/README.md) и требования R1–R5 на месте; целевые
каталоги памяти/почты не пересекаются с `.opencode/agents/**`; упомянутые
затронутые файлы существуют (`.opencode/agents/`, `.opencode/rules/review.md`,
`.opencode/rules/git-workflow.md`). Расхождений, требующих продуктовой задачи,
нет: реализация процесса — это и есть [T-11](../tasks/T-11-agent-cycle/README.md).

Задач не требуется: решение процессное, вердикт ⚪; работа по внедрению цикла
оформлена отдельной задачей [T-11](../tasks/T-11-agent-cycle/README.md), а не
порождена расхождением кода с требованием.

## Альтернативы

- **(а) водопад** (как в пилоте) — отклонён: дублирует тестирование (4+ прогона
  на задачу), хрупок к обрывам сессий, отчёты теряются.
- **(б) Agile-петля с `validator`-лидером** — отклонён: совмещение «лидер +
  единственный тестировщик + приёмщик» даёт одну точку отказа и ослабляет
  независимость приёмки; `validator` остаётся read-only приёмщиком.
