## Контекст

`rest_auth.feature` и код использовали заголовок `x-api-key`, а
`evaluate.feature` — `Authorization` с текстом «ошибка аутентификации».
Неясны были нормативный заголовок, набор открытых путей и способ задания
ключа. Полный контекст — [Q22](../questions/Q22.md).

## Решение

1. **Заголовок — `x-api-key`** (канон; `Authorization` в фичах не
   используется). OAuth/JWT/mTLS — вне v0.1, кандидаты v0.2+ (Q39).
2. **Ключ — единственный серверный секрет** (`CREDO_API_KEY`), не
   идентификатор клиента: пер-клиентские ключи, квоты и аудит — v0.2+.
3. **Текст 401** (в конверте Q23: `code = unauthorized`):
   `ошибка аутентификации: неверный или отсутствующий x-api-key` — единый
   для отсутствующего и неверного ключа (не раскрывает, был ли заголовок).
   Канон текстов Q11 обновлён.
4. **Открытые пути** (без ключа): `/health`, `/docs`, `/openapi.json` — как
   в коде; зафиксировано в `rest_auth.feature`.
5. **Режим без `CREDO_API_KEY` — штатный режим демо/разработки:** API
   открыт; в проде переменная обязательна (проверка на старте — v0.2).
   Полезно для быстрого локального прогона и ручного UI-прогона на demo без
   настройки секретов.
6. **Способ задания:** флаг `--api-key <KEY>` с переменной окружения
   `CREDO_API_KEY` как источником значения по умолчанию (реализация в
   `src/main.rs`); приоритет — явный флаг выше переменной. Формат ключа в
   v0.1 не регламентирован (любая непустая строка; генерация и требования
   сложности — v0.2 вместе с проверкой на старте).

**Уточнение редакции 2 (2026-09-25): Q22 закрыт полностью.** При сверке с
кодом выявлено единственное расхождение: ответ 401 в обработчике `auth`
(`src/rest.rs`) возвращал старый плоский вид `{"error": "<текст>"}`. Это
**не новый вопрос**, а часть уже закрытого Q23: конверт
`{"error": {"code", "message"}}` с `code = unauthorized` покрывает 401
(реализовано вместе с остальными ошибками Q23). Формулировки решения не
меняются: Q22 определяет заголовок, тексты и открытые пути, форму тела
ошибки — Q23. По итогам Q22 собственных изменений кода не вносится.

## Альтернативы

- **`Authorization: Bearer <token>`** (как в раннем `evaluate.feature`) —
  подразумевает схему токенов/JWT, которой в v0.1 нет; отклонено.
- **Пер-клиентские ключи, квоты, аудит** — преждевременно для MVP;
  отложено в v0.2+.
- **OAuth/JWT/mTLS** — вне v0.1 (Q39); отклонено.
- **Разные тексты для отсутствующего и неверного ключа** — раскрывали бы
  наличие заголовка; выбран единый текст.
