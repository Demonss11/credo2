## Контекст

SPEC объявлял «файл на диске — источник истины» (`rules/*.dar`), но фактический
жизненный цикл начинался с черновика в `.credo/sandbox.json`, а публикация
писала JSON-тройку в bare-репозиторий; `.dar` в цикле не участвовал. Не было
единого потока трёх представлений правила и правила разрешения расхождений.
Полный контекст — [Q12](../questions/Q12.md).

## Решение

1. **Источник истины — `.dar`-файл рабочего контура** (`rules/`, под git).
   `.credo/sandbox.json` — **только черновик**: производный от файла или
   созданный агентом с нуля; временное состояние, которое можно
   удалить/пересоздать без потери данных; черновики не участвуют в REST
   `evaluate`.
2. **Поток строго направленный:** `rules/*.dar → черновик → артефакт
   публикации`. Обход запрещён: нельзя опубликовать то, чего нет в
   песочнице/файле; `evaluate` читает только опубликованное.
3. **Разрешение расхождения** (файл изменён вручную, черновик устарел): выигрывает
   **файл**; черновик помечается `stale` при первой операции над ним (сверка
   `source_hash` исходного `.dar`).
4. **Инвариант исходника:** черновик без привязанного `.dar`-файла при публикации
   обязан сначала сохранить текст в `rules/{name}.dar` — «у каждого
   опубликованного артефакта есть исходник».
5. **Хранение опубликованных правил для `evaluate` в MVP** — `HashMap`/`Vec`
   в памяти; будущая векторная БД — только производный поисковый индекс, не
   источник истины для исполнения.

## Следствия

- Три представления получают один владелец истины: файл workspace; черновик и
  артефакт публикации — производные, каждый со своим назначением и сроком жизни.
- Появляется вычисляемая метка `stale` (сверка `source_hash` файла и черновика);
  `check.test` при устаревшем черновике обязан исполнять текст файла, а не текст
  черновика.
- `check.publish` черновика без файла материализует `rules/{name}.dar`
  (существующий файл не перезаписывается).
- Документы `SPECIFICATION.md` §1.3/§4.3/§7 и фичи рабочего контура приводятся к
  единому потоку (правки — зона `docs-writer`).
- Поток — предпосылка P1-кодинга: расхождения в периметре MVP разведены по
  задачам `T-16` (`check.test`) и `T-08` (материализация).

## Сверка с кодом

Вердикт: 🟡 **расхождение** — основа потока уже реализована (`source_hash`,
`stale`, черновик как производное), но исполнение stale-черновика и
материализация исходника при публикации отстают от канона; расхождения в
периметре MVP покрыты задачами.

Что проверено (чтением кода и тестов, 29.09.2026), чем подтверждено:

- **Черновик, `source_hash`, `stale` — ✅ (сделано в [T-01](../tasks/T-01-draft-source-hash/README.md)):**
  - [`src/lib.rs`](../../src/lib.rs) — `Draft` с `source`/`source_hash`
    (732–751), `make_draft` считает `source_hash` (853–874);
  - `is_stale` (811–822): файла `rules/{name}.dar` нет → `false`; хэши
    совпадают → `false`; различаются → `true`;
  - юнит-тесты `stale_follows_hash_invariant_q29` (`src/lib.rs:1051-1069`);
  - [`../../tests/mcp_draft.rs`](../../tests/mcp_draft.rs) — `source_hash`
    формата `sha256:<hex>`, `.dar` не создаётся (draft-first, Q33),
    перезагрузка старого `sandbox.json`.
- **`check.test` на stale-черновике — 🟡 расхождение:**
  [`src/mcp.rs`](../../src/mcp.rs) `test(...)` (214–262) исполняет
  `evaluate_rule(&d.rule, …)` (235) — текст **черновика** из песочницы; `stale`
  лишь не блокирует тест (комментарий 234). Канон п. 3 требует при `stale`
  исполнять правило, разобранное из текста файла `rules/{name}.dar`
  (сценарий [`test_draft.feature`](../features/test_draft.feature), «Тестирование
  устаревшего черновика», строки 51–57). Тесты `src/mcp.rs:772-826`
  (`stale_true_when_dar_hash_differs_q29_inv3`) проверяют `stale = true` и что
  тест не блокируется, но **не** источник исполнения.
  → задача [T-16](../tasks/T-16-stale-check-test/README.md) (P1).
- **Материализация `rules/{name}.dar` при публикации — ⬜ не реализовано:**
  [`src/lib.rs`](../../src/lib.rs) `publish(...)` (321–409) пишет только
  `checks/{name}/{vstr}/rule.json`, `contract.json`, `meta.json` (342, 389–393);
  записи `.dar`-файла нет. Тест `src/mcp.rs:777-778` фиксирует, что
  `rules/МинимальныйВозраст.dar` не создаётся (draft-first). Канон п. 4 требует
  материализации. → задача
  [T-08](../tasks/T-08-materialize-source-file/README.md) (P2).
- **`evaluate` читает только опубликованное — ✅:** REST/MCP-исполнение берёт
  версии из `main` (см. D21 и `tests/rest.rs`: `/checks/{name}/versions/{version}/evaluate`);
  черновики в `evaluate` не участвуют.

`cargo` не запускался (§5.3, [D50](D50-dod-by-package-scope.md)): решение сверено
чтением кода и тестов; адресный прогон не требуется (правок код не порождает).

**Задач новых не требуется:** расхождения в периметре MVP уже покрыты
[T-16](../tasks/T-16-stale-check-test/README.md) (`check.test`) и
[T-08](../tasks/T-08-materialize-source-file/README.md) (материализация);

## Альтернативы

- **`.dar` — истина, черновик/публикация — полностью производные** (вариант (а)
  [Q12](../questions/Q12.md)) — близко к принятому, но не покрывает черновик,
  созданный агентом с нуля, без файла; принято как направление потока с
  оговоркой о материализации (п. 4).
- **Песочница — истина для черновиков, `.dar` — только UI-представление**
  (вариант (б)) — теряется file-first и git-история исходников; отклонено.
- **Два независимых контура в MVP** (вариант (в)) — расхождение «редактор vs
  агент», дублирование истины; отклонено.
- **Опубликованный артефакт как источник истины для `evaluate`** — отвергнуто:
  источник истины остаётся в файле, а артефакт — производная версия;
  `evaluate` читает `main`, но это не делает артефакт первоисточником.
