# D19: Две оси меток, единственный канон — `features/README.md`

- **Статус:** accepted
- **Дата:** 2026-09-24
- **Resolves:** [Q5](../questions/Q5.md) (Q6 — **закрыт попутно**, отдельного D
  нет; см. [Q6](../questions/Q6.md))
- **Спека:** [`SPECIFICATION.md`](../SPECIFICATION.md) §10, решение №19
- **Affects:** [`features/README.md`](../features/README.md) (канон статусов,
  приоритетов и счётчиков); [`SPECIFICATION.md`](../SPECIFICATION.md) §6
  (ссылки вместо дублирующей таблицы); [`tests/features_inventory.rs`](../../tests/features_inventory.rs)
  (машинная проверка инвентаризации)
- **Tasks:** — (см. «Сверка с кодом»)

## Контекст

Документация использовала две конкурирующие системы меток: `features/README.md` —
✅/🟡/⬜/⏸ (реализовано/расходится/план/отложено), `SPECIFICATION.md` §6.2 —
🔴/🟡/🟢/⏳ (обязательные/желательные/вау/отложенные). Один и тот же файл
получал разные метки (например, `rest_api.feature` — ✅ и 🔴), что выглядело как
противоречие и нарушало «один факт — один канон» (Q41). Отдельно таблица SPEC
§6.1 несла устаревшие числа (18 файлов / 93 сценария против фактических
36 / 191 на 2026-09-24). Полный контекст — [Q5](../questions/Q5.md) и
[Q6](../questions/Q6.md).

## Решение

1. **Две независимые оси меток** — они отвечают на разные вопросы и не
   смешиваются:
   - **статус реализации** (✅/🟡/⬜/⏸) — «что уже работает» в `credo2`;
   - **приоритет MVP** (🔴/🟡/🟢/⏳) — «что и когда нужно демо».
2. **Единственный канон — [`features/README.md`](../features/README.md):** у
   каждого файла в сводных таблицах обе колонки (статус и приоритет).
3. **`SPECIFICATION.md` §6 ссылается**, а не дублирует: §6.1 удалил таблицу
   инвентаризации и указывает на README, §6.2 оставляет только смысл уровней
   и привязку к фазам плана (§8).
4. **Определение «сделано» (✅)** живёт в README: поведение реализовано,
   сценарии не противоречат коду; для backend-зоны есть автотест либо явная
   пометка «ручной прогон», UI проверяется вручную по сценарию. 🟡 — расхождение
   зафиксировано в `OPEN_QUESTIONS.md`; ⬜ — план; ⏸ — вне MVP.
5. **Попутное следствие ([Q6](../questions/Q6.md)):** таблица SPEC §6.1 **не
   пересчитывается, а удалена** как дублирующая. Актуальность счётчиков
   проверяет тест [`tests/features_inventory.rs`](../../tests/features_inventory.rs),
   а не ручной пересчёт.

## Следствия

- Устранено мнимое противоречие «✅ vs 🔴»: одна сущность (`rest_api.feature`)
  получает по одной метке на каждую из двух осей, а не конфликтующие метки из
  разных документов.
- `features/README.md` — единственное место статусов, приоритетов и счётчиков;
  приоритеты файлов перенесены из SPEC §6.1, файлы без приоритета размечены по
  здравому смыслу: `lexer` ⏳; `parser`, `execution`, `explain`, `errors`,
  `semver`, `storage_paths`, `manifest`, `mcp_tools`, `testing`, `lsp_notebook`
  🔴; `immutability`, `manifest_sync`, `deprecation` 🟡.
- `SPECIFICATION.md` §6 разгружен до ссылок и смысла уровней (§6.2) и привязки
  к фазам; краткая формулировка решения — §10 №19.
- Инвентаризация стала машинно проверяемой: структура файлов, полнота перечня и
  счётчики README сверяются тестом `tests/features_inventory.rs` (Q40).
- Дальнейшее развитие — по политике Q41: новый статус/приоритет/число правится
  в README, SPEC не дублирует.

## Сверка с кодом

Вердикт: ✅ **соответствует** — документная по природе запись (канон меток),
машинно проверяемая часть подтверждена существующим тестом; код правки не
требует.

Что проверено (чтение документов и кода, 29.09.2026), чем подтверждено:

- [`SPECIFICATION.md`](../SPECIFICATION.md) §6.1 — ссылается на
  [`features/README.md`](../features/README.md) как канон перечня, статуса
  реализации, приоритета MVP и счётчиков; дублирующей таблицы нет. §6.2 —
  только смысл уровней (🔴/🟡/🟢/⏳) и привязка к фазам §8. Соответствует
  решению «ссылаться, а не дублировать».
- [`features/README.md`](../features/README.md) — шапка фиксирует «Решения
  Q5/Q40 (2026-09-24)» и две независимые оси; сводные таблицы имеют колонки
  `Статус` и `Приоритет` у каждого файла; блок «Соответствие коду» задаёт зоны
  ответственности (§5.3). Обе оси на месте.
- [`tests/features_inventory.rs`](../../tests/features_inventory.rs) — существует
  и проверяет: `# language: ru`, ровно одну `Функция:`, наличие сценариев
  (`feature_files_are_valid_documents`), полноту перечня
  (`feature_files_match_readme_inventory`), совпадение счётчиков
  (`scenario_counts_match_readme`) и итог README
  (`readme_totals_match_files`). То есть машинная часть решения (единственный
  канон счётчиков — README) покрыта тестом.
- Карта зон «Соответствие коду» — [`features/README.md`](../features/README.md):
  строка «Инвентаризация фич» указывает именно на этот тест.

Адресный прогон `tests/features_inventory.rs` — за `validator` (запрос через
`lead`); `migrator` сам `cargo` не запускает (§5.3). Вердикт основан на чтении
кода и документов.

**Задач не требуется:** расхождение снято документами (README — канон, SPEC §6
ссылается), а машинно проверяемая часть уже реализована существующим тестом.
Затрагиваемые файлы — зона `docs-writer` (`features/README.md`, §6 SPEC), но
правка требует лишь обратных ссылок `# Dn (Qx)` в шапках/нотах (§5.6), а не
кода; отдельной задачи по коду нет.

## Альтернативы

- (а) **Дублирующая таблица меток в `SPECIFICATION.md`** — отклонено:
  противоречит политике Q41, порождает расхождение «✅ vs 🔴» при каждом
  изменении требований.
- (б) **Одна смешанная ось** (объединить статус и приоритет в одну шкалу) —
  отклонено: статус отвечает «что работает», приоритет — «что нужно демо»;
  свёртка теряет обе семантики (✅-реализованное ⏳-отложенное и ⬜-запланированное
  🔴-обязательное неразличимы).
- (в) **Оставить SPEC §6.1 как исторический срез** — отклонено: устаревшие
  числа (18/93) противоречат фактическим (36/191 на 2026-09-24) и вводят
  читателя в заблуждение; историю хранит git, а не SPEC.
