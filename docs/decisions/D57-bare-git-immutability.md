# D57: Иммутабельность опубликованной версии — bare-git, без отдельного механизма версионирования

## Контекст

`immutability.feature` описывала защиту через файловый механизм
`create_dir_all`/`AlreadyExists`, а хранилище `credo2` — bare git с защитой на
проверке дубликата и атомарном `create_ref`. Какой механизм считать
нормативным и нужно ли переносить хранилище на рабочее дерево? Полный
контекст — [Q17](../questions/Q17.md).

## Решение

Оставить **bare-git**, НЕ вводя отдельного механизма версионирования (никаких
`refs/rules/...` на версию — это противоречило бы Q13/Q15/Q32).
Иммутабельность обеспечивают принятая модель реестра и поток публикации в
**три слоя**:

1. **Единица иммутабельности — каталог версии** `checks/{name}/{X}/{Y}/{Z}/`
   в `main` (Q13/Q32): только `rule.json`, `contract.json`, `meta.json`;
   исходный `.dar` в реестр не попадает (связь через `source_hash`;
   `source.dar` — v0.2). Изменение правила = новая версия (новый каталог), а
   не правка существующего.
2. **Отказ при повторной публикации** на шаге `check.publish` (Q29): если
   `checks/{name}/{X}/{Y}/{Z}/` уже есть в `main` — отказ с кодом
   `publish_failed`; downgrade запрещён (Q32); ветка
   `publish/{name}-{version}` создаётся атомарно (`create_ref` без
   перезаписи).
3. **Защита при слиянии** на шаге `credo merge` (Q15): атомарный
   `git update-ref refs/heads/main <sha> <expected-sha>` с CAS-проверкой; при
   параллельных мержах один выигрывает, второй получает отказ.

Источник истины опубликованного артефакта — git-состояние (каталог версии в
`main`), а не произвольный каталог файловой системы.

- **Доменная мотивация:** банковский аудит и доказуемость — версия,
  действовавшая в момент принятия кредитного решения, не может быть
  перезаписана, удалена или подменена задним числом; история публикаций в
  `main` — источник для аудита.
- **Терминология:** `name` — машиночитаемый латинский идентификатор
  (`CreditAgeMin`, Q13); `rule_id` не используется (Q7).
- **Поверхность ошибок:** публикация — MCP `check.publish`; отказ —
  `publish_failed` по §4.5 (не HTTP 409: 409 занят `activation_unavailable`,
  Q23).

## Следствия

- Хранилище остаётся bare-repo; рабочее дерево для реестра не вводится.
- `immutability.feature` переписывается с файлового механизма на bare-git:
  2 существующих сценария обновлены на месте, +2 новых (параллельная
  публикация; публикация новой версии не изменяет прежде опубликованные
  артефакты) — итого 4 сценария; разноска статуса/счётчика — в
  `features/README.md` (зона `docs-writer`).
- Неизменяемость опирается на существующие решения (Q13/Q15/Q32), а не на
  новый механизм; отказ при повторной публикации не зависит от контента.

## Сверка с кодом

Вердикт: 🟡 **расхождение** — механизм bare-git и отказ при повторной
публикации реализованы; каталог версии записывается плоским путём, третьего
слоя (CAS при слиянии) в коде нет — оба расхождения уже покрыты задачами.

Что проверено (чтением кода, 29.09.2026), чем подтверждено:

- **Слой 1 — каталог версии — 🟡:** [`src/lib.rs`](../../src/lib.rs) пишет
  `checks/{name}/{vstr}` (342, `debug_assert` 383, `deprecate` 462) — плоский
  путь с нормализованной версией, а не вложенный `checks/{name}/{X}/{Y}/{Z}/`;
  неизменяемая JSON-тройка `rule.json`/`contract.json`/`meta.json` (389–393)
  — ✅. Расхождение путей — известное Q32, покрыто задачей
  [T-06](../tasks/T-06-registry-path-xyz/README.md).
- **Слой 2 — отказ при повторной публикации — ✅:**
  [`src/lib.rs`](../../src/lib.rs) `publish(...)` (321–409): проверка
  существующей версии в `main` (344–351, `bail!("версия {vstr} уже
  существует …")`), запрет downgrade (353–360), ветка
  `publish/{name}-{version}` через атомарный `create_ref` с zero-oid CAS
  (397–400); сам `create_ref` — `git update-ref <ref> <commit> <zero>`
  (169–180). MCP отображает ошибку в `publish_failed`
  ([`src/mcp.rs`](../../src/mcp.rs) `publish` 282–324).
- **Слой 3 — CAS при слиянии — ⬜ не реализовано:** `credo merge` в коде
  отсутствует (нет ancestor-проверки, CAS-`update-ref`, удаления ветки);
  `src/mcp.rs:335-340` предлагает ручную команду `git update-ref` без CAS —
  покрыто задачей [T-17](../tasks/T-17-merge-command/README.md)
  (Q15/[D56](D56-merge-step.md)).
- **Источник истины — git-состояние — ✅:** реестр читается из `main`
  (`list_from_ref`, 233+), файловая система рабочего дерева в реестр не
  вовлечена.

`cargo` не запускался (§5.3, [D50](D50-dod-by-package-scope.md)): сверено
чтением кода; адресный прогон не требуется (правок код не порождает).

**Задач новых не требуется:** расхождения в периметре MVP уже покрыты
[T-06](../tasks/T-06-registry-path-xyz/README.md) (путь каталога версии,
Q13/Q32) и [T-17](../tasks/T-17-merge-command/README.md) (CAS при слиянии,
Q15).

## Альтернативы

- **Файловая защита `create_dir_all`/`AlreadyExists`** (описание в архиве) —
  не соответствует bare-хранилищу `credo2`; отклонено.
- **Отдельный механизм версионирования** (`refs/rules/{name}/{version}` на
  версию) — противоречит реестровой модели Q13/Q15/Q32, дублирует git;
  отклонено.
- **Перенос хранилища на рабочее дерево** — реестр потерял бы атомарный CAS
  и bare-git-семантику; отклонено.
- **Отказ по контенту** (отдельный сценарий «другой контент под той же
  версией») — не вводится: отказ не зависит от контента и покрыт первым
  сценарием фичи.
