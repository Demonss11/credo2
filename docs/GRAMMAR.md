# GRAMMAR — каноническая грамматика DAR {} v0.1

> **Статус:** нормативный документ. Является единственным источником истины
> по синтаксису DSL версии v0.1 (решения Q2, Q3 в `OPEN_QUESTIONS.md`,
> 2026-09-24). Любые иные описания языка (`concept.md`, `SPECIFICATION.md`
> §1.3, фичи) — производные; при расхождении действует настоящий файл.
>
> **Решение Q3:** MVP использует **regex-минимум** (реализация —
> `dar-core::parse_rule`, исторически `credo2::core::parse_rule`).
> Лексер и полноценный AST в v0.1 **не входят**. Формальное описание ниже
> задаёт язык v0.1 так, чтобы regex-парсер был его точной реализацией,
> а будущий лексер+AST (v0.2+) расширял язык без изменения синтаксиса v0.1.

## 1. Синтаксис правила v0.1

```ebnf
Правило   ::= "Правило" Пробел Имя Пробел Блок ;
Имя       ::= Letter { Letter | Digit | "_" } ;   (* в т.ч. кириллица \w+ *)
Блок      ::= "{" { WS } Если БлокУсловия { WS} "}" ;
Если      ::= "Если" { WS } "(" { WS }
              Поле { WS } Оператор { WS } Значение { WS } ")" ;
Поле      ::= Ident { "." Ident } ;               (* напр. Клиент.Возраст *)
Оператор  ::= "<" | ">" | "==" | "!=" ;           (* v0.1: без <= >= *)
Значение  ::= Число | Строка ;
Число     ::= ["-"] Digit { Digit } [ "." Digit { Digit } ] ;
Строка    ::= '"' { ЛюбойСимволКроме'"' } '"' ;
БлокУсловия ::= "{" { WS } Решение "=" Имя ";"
                [ { WS } Причина "=" Строка ";" ] { WS} "}" ;
Решение   ::= "Решение" ;
Причина   ::= "Причина" ;
Комментарий ::= "//" до конца строки ;             (* игнорируется *)
```

Пример (канонический):

```dar
// Правило возрастного ценза
Правило МинимальныйВозраст {
  Если (Клиент.Возраст < 21) {
    Решение = Отказ;
    Причина = "Возраст меньше 21";
  }
}
```

## 2. Ограничения v0.1 (regex-минимум)

| # | Ограничение | Последствие |
|---|---|---|
| 1 | Одно правило в файле | Конвейеры — вне v0.1 (Q36) |
| 2 | Одно сравнение в `Если (...)` | Нет `И`/`ИЛИ`, скобочных групп |
| 3 | Операторы только `< > == !=` | `<=`/`>=` — план v0.2 |
| 4 | Нет ключевых слов `Тогда`, `Приоритет`, doc-блоков `:::` | См. §4 |
| 5 | `Причина` опциональна (пустая строка по умолчанию) | — |
| 6 | Числа — `f64` (решение SPEC §10 п. 13), строки — в двойных кавычках | `Decimal` в v0.2 |
| 7 | Ошибки парсинга — текстовые (`String`): «отсутствует заголовок правила (Не найдено имя правила)», «Не найдено условие», «Не найдено решение» | Типизированные ошибки и позиции — план v0.2 |
| 8 | Комментарии вырезаются парсером, но не анализируются | code=doc через Notebook, не язык |

## 3. Стратегия LSP-совместимости (снимает конфликт с Q3↔LSP)

MVP-парсер на регулярках **не противоречит** планируемому LSP, если
зафиксировать три правила проектирования (обязательны с первого коммита):

1. **Толстый парсер, тонкий интерфейс.** Вся работа с `.dar` идёт только
   через `dar_core::parse_rule(source) -> Result<Rule, String>` и функции
   поверх него. Никакого regex-кода вне модуля DSL. LSP-сервер — такой же
   потребитель этого API, как REST и MCP.
2. **Внутренний AST уже есть — он приватный.** Структуры `Rule / Condition /
   Action` и есть упрощённое дерево. В v0.2 оно обогащается позициями
   (`span: Range`), типизированными ошибками (`thiserror`) и полным списком
   токенов — это *расширение* существующих типов, а не замена архитектуры.
   Публичный контракт функции при этом не ломается (ошибка становится
   `ParseError`, реализующим `Display` ↔ текущий `String`).
3. **Грамматика назад совместима.** EBNF выше — подмножество целевого языка:
   всё, что принимает v0.1, примет и v0.2-парсер. Поэтому LSP можно строить
   итеративно: diagnostics/hover поверх `parse_rule` доступны сразу,
   автодополнение по реальному лексеру — после v0.2.

**Вывод:** для MVP отдельный лексер писать не нужно; нужен лишь дисциплинированный
модуль DSL, который позже заменится внутренностями без изменения вызывающего кода.
