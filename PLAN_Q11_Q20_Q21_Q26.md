## 3. Задачи

### Задача 1 (Q21). `build_manifest`: `active`, `supported`, `deprecated`

**Файл:** `src/lib.rs` (`ManifestEntry`, `build_manifest`).

**Что сделать:**

1. `supported` собирать **по убыванию** версий (сейчас — по возрастанию,
   поэтому `supported[0]` — минимальная версия).
2. `active = supported[0]`; если `supported` пуст (все версии deprecated) —
   `active = ""` (сейчас — `supported.last().or(deprecated.last())`).
3. `deprecated` — по убыванию (предсказуемость ответа и OpenAPI).
4. `service_hash` не менять: хэш считается по набору
   `name|version|status|checksum`, порядок обхода — по возрастанию, как
   сейчас; смена порядка в JSON на хэш не влияет.

**Тесты (unit, `src/lib.rs`):**

- `supported_is_descending_q21`;
- `active_is_first_supported_q21`;
- `active_is_empty_when_all_deprecated_q21`;
- `every_version_in_exactly_one_list_q21` (инвариант Q21).

**Критерий приёмки:** сценарии `manifest.feature` (active = 1.0.1,
supported = [1.0.1, 1.0.0], deprecated = [1.1.0]) и обновлённые сценарии
`dashboard.feature`.

### Задача 2 (Q21). `GET /checks`: канонический состав ответа

**Файл:** `src/rest.rs` (`list_checks`).

**Что сделать:**

1. Добавить в ответ `schema_version` (из `Manifest`).
2. Ключи ответа — ровно канон: `schema_version`, `count`, `service_hash`,
   `checks`; `generated_at` в `/checks` не возвращать (он остаётся в
   `GET /version`).
3. Выделить чистую функцию `manifest_response(&Manifest) -> JsonValue`,
   чтобы её можно было покрыть unit-тестом без HTTP.

**Тест:** unit — точный набор ключей верхнего уровня и точный набор полей
каждого элемента `checks` (`name/active/supported/deprecated`).

**Критерий приёмки:** сценарий «GET /checks возвращает манифест»
(`rest_api.feature`) и сценарий «Получение манифеста через REST»
(`evaluate.feature`).

### Задача 3 (Q11/Q20/Q21). Семантика deprecated-версии и «активации»

**Файлы:** `src/rest.rs` (`eval_version`, `eval_active`, `eval_inner`,
`list_versions`, `openapi`).

**Что сделать:**

1. `eval_version` (`POST /checks/{name}/versions/{version}/evaluate`): если
   `meta.deprecated_at.is_some()` — **410 Gone** с телом
   `{"error": "версия выведена из эксплуатации: {name}@{version}"}`
   (статус и текст зафиксированы 2026-09-25, Q11).
2. `eval_active` (`POST /checks/{name}/evaluate`): проверка есть, но
   `active == ""` (все версии deprecated) — **409 Conflict**
   `{"error": "активация недоступна: {name}"}`; проверки нет — 404
   «проверка не найдена: {name}».
3. `list_versions`/`eval_active`: убрать кавычки в 404 — канон
   «проверка не найдена: {name}» (сейчас «проверка '{name}' не найдена»).
4. Конверт ошибок `{"error": msg}` **не менять**: структура `code/message` —
   решение Q23 (открыт). Тексты 401 — решение Q22 (открыт).
5. OpenAPI: для deprecated-версий уже стоит `post.deprecated = true` —
   добавить описание ответа 410; для active — 409.

**Тесты (integration, новый `tests/rest.rs`):**

- deprecated-версия → 410 и текст; активная → 200;
- все версии deprecated → active-эндпоинт 409 «активация недоступна»;
- несуществующая проверка → 404 «проверка не найдена: X».

**Подготовка к тестам:** выделить `pub fn app(state, cache) -> Router` из
`rest::serve` и вызывать через `tower::ServiceExt::oneshot`
(dev-dependency `tower = { version = "0.5", features = ["util"] }` —
сейчас в `Cargo.toml` только `tempfile`).

**Критерий приёмки:** сценарии «Выполнение deprecated-версии отклоняется»
(410, `evaluate.feature` и `rest_api.feature`) и «Нет active-версии —
активация недоступна» (409, `rest_api.feature`).

### Задача 4 (Q20). Аудит состава REST и OpenAPI

**Файлы:** `src/rest.rs` (`serve`, `openapi`); `SPECIFICATION.md` §4.4
(уже обновлён).

**Что сделать:**

1. Зафиксировать MVP-минимум: versioned evaluate, `GET /checks`,
   `/health`, `/version`, `/openapi.json`; всё остальное — вне минимума
   (см. §4.4 SPEC).
2. **Зафиксировано (2026-09-25):** уже реализованные
   `POST /checks/{name}/evaluate`, `GET /checks/{name}/versions`,
   `GET /checks/{name}/versions/{version}` — вне MVP-минимума. В рамках
   MVP их **не удалять и не развивать**; вопрос сохранения/удаления —
   решение пост-MVP, не задача MVP.
3. Проверить инварианты Q20 (изменений не требуют, только контроль):
   - `evaluate` читает только `main` через `ServiceCache` — да;
   - серверной агрегации/сведения решений нет — да;
   - пути не имеют алиасов и варианта «имя в теле» — да.

**Тест:** `openapi` содержит канонический путь
`/checks/{name}/versions/{v}/evaluate` и схему запроса из контракта
(существующая проверка расширяется ассершеном).
