# Шаблон разбора сессии агента (`*-session.md`)

**Назначение:** единообразный служебный отчёт-разбор сессии субагента по
материалам транскрипта и артефактов — чтобы хронология, расход шагов,
отказы/срезы и выводы были проверяемыми, а предложения — адресными.
**Вход:** экспорт сессии (`*.json`) + отчёт фактов (`*.report.txt`) + артефакты
задачи (лента, память, state, досье, приёмка, коммиты).
**Выход:** один markdown-файл
`docs/analysis/<T-XX>-run<N>-<роль>-session.md`.
**Статус:** улика, не канон (Q41); правки канона не содержит — только предложения.

---

## Часть I. Инструкция (до заполнения)

### 1. Когда заводить

- После прогона роли (или серии прогонов на одной задаче), когда есть что
  зафиксировать: обрывы/упоры в `steps`, отказы прав, срезы `token-guard`,
  отклонения от брифа, находки для меморандума/реестра.
- «Пустой» прогон без событий — тоже допустим (короче), если он нужен как
  контроль или для метрики прогона.

### 2. Кто и чем пишет

- Сервисная сессия (владелец): у ролей `node` нет в allowlist.
- Инструменты: `.opencode/scripts/session-analysis/` — `find-subagents.mjs`
  (ID дочерних сессий), `export-session.mjs` (выгрузка), `analyze-session.mjs`
  (факты), `fix-encoding.mjs` (старые выгрузки).
- ID сессии — из parent-сессии, ленты или `progress.yaml`; `opencode session
  list` показывает только top-level. Переход корень → дети:
  `find-subagents.mjs <ses_корень>` (маркер `<subagent sessionID=…>` в
  транскрипте родителя), при необходимости `--export` — выгрузка всех детей.

### 3. Порядок работы

**Быстрый путь (полный цикл):**
`node .opencode/scripts/session-analysis/agent-report.mjs <ses_корень> <роль>`
— сам найдёт сессию(и) агента в транскрипте корня, выгрузит транскрипт,
соберёт факты (`*.report.txt`) и **черновик отчёта** (`*.draft.md`: шапка и
§1–§3 заполнены). Дальше — дополнить черновик по этому шаблону и сохранить в
`docs/analysis/`; посмотреть сессии агента — `--list`, взять только последнюю —
`--last`.

**Вручную, по шагам:**

1. Найти ID сессии (`find-subagents.mjs <ses_корень>`, лента или
   `progress.yaml`) и выгрузить:
   `node .opencode/scripts/session-analysis/export-session.mjs <ses_…>` →
   JSON в `%TEMP%\opencode\sessions\`.
2. `node .opencode/scripts/session-analysis/analyze-session.mjs <json>` →
   `*.report.txt` (факты, секции `LEGEND`…`BOUNDARY TEXTS`).
3. Прочитать `.opencode/agents/<роль>.md` (лимит `steps`, зоны записи, порядок
   ролей) и `.opencode/memory/<роль>.md`.
4. Пройти `*.report.txt` и выписать факты: сегменты, финалы, отказы, срезы, числа.
5. Сверить с артефактами: лента, `state/current/{progress,receipts}.yaml`,
   досье, приёмка (архив — git), коммиты (`git show --stat`).
6. Заполнить скелет (Часть II) — без пересказа, только факты с последствиями.
7. Пройти чек-лист (Часть III) и проверить ссылки.

### 4. Откуда что берётся (анализатор → отчёт)

| Раздел отчёта | Источник |
|---|---|
| §1 Сводка | `SESSION` (времена/токены/цена), `PROMPTS`, `SEGMENTS` (шаги), `TOOL TOTALS`, `TOKEN-GUARD CUTS`, `FINISH…`; лимит — из `agents/<роль>.md` |
| §2 Хронология | `MESSAGES` (индексы), `USER MESSAGES` (бриф/продолжения), `BOUNDARY TEXTS`, `FINISH/SUSPICIOUS` |
| §3 Ошибки/срезы | `FLAGGED TOOL CALLS`, `SHELL CALLS`, `TOKEN-GUARD CUTS`, `FINISH/SUSPICIOUS` |
| §4 Оценка | `USER MESSAGES` (критерии), `TAIL TEXTS` (отчёт роли), `MESSAGES` + канон роли |
| §5 Сверка | файлы: лента, память, state, досье, приёмка, коммиты |
| §6–8 | выводы автора разбора |
| Приложение | пути temp-артефактов и команды |

### 5. Правила честности

- **Шаг = ассистентское сообщение;** `[i]` — индекс сообщения в экспорте, не шаг.
- Числа — только из транскрипта/файлов (шаги, байты срезов, токены); оценки
  помечать как оценки.
- Срез считается **по маркеру** `…[token-guard] срез: опущено …`, а не по слову
  `token-guard` (цитаты в текстах — не срез).
- `permission.rejected` — не «баг», пока не сверено с каноном
  (`review.md`, allowlist): чаще это канонное поведение прав.
- Каждое предложение — с последствием и адресатом (сервисная сессия /
  `migrator` / роль). Кандидаты F-записей **предлагаются**, не вносятся.
- Различать: факт транскрипта / вывод роли / вывод разбора. Нет находок —
  «критичных проблем нет», не выдумывать.

### 6. Имя и размещение

- `docs/analysis/<T-XX>-run<N>-<роль>-session.md`; для отдельного пакета —
  уточнение в шапке (пример: сессия `git` с пакетом `branch_end`).
- Примеры разборов (пять сессий Run 5) — архив git.

### 7. Вариации по роли (акцент §4)

- код (`coder`/`tester`): состав правок, качество юнит/интеграционных тестов,
  границы `tests/**`;
- приёмка (`validator`): цифры DoD, дисциплина находок (P1/P2/P3), B1 и срезы;
- аудит (`auditor`): «инструкция ↔ права», бюджет файлов/`rg`, `debug agents`;
- git (`git`): идемпотентность, состав пакета, хеши, отсутствие `--force`;
- документы (`docs-writer`/`migrator`): ссылки, статусы, дубли канона (Q41).

## Часть IV. Типовые ошибки

1. **Хроника вместо выводов.** Пересказ шагов без «факт → оценка → предложение».
2. **Шаг ≠ индекс.** Счёт `[i]` шагами искажает лимит и «точки останова».
3. **Авто-продолжение ≠ resume.** Не отмечено, сбросился ли бюджет `steps`
   (обычно нет — свежий бюджет даёт новый вызов).
4. **`permission.rejected` как «баг».** Часто это канонное поведение прав;
   сверять с `review.md`/allowlist роли.
5. **Ложные срезы.** Считать по слову `token-guard` в сообщениях коммитов или
   цитатах; считать только маркер `… срез: опущено …`.
6. **Находка без последствия.** «Стиль» без однострочной правки — не находка.
7. **Кандидат F внесён разбором в реестр.** Сначала предложение; вносит `migrator`.
8. **Устаревшие пути.** Проверять фактические имена (пример:
   `memorandum-W9-run5.md` не существует — том переименован в W8-run5).
9. **Недоказуемые выводы.** Нет ссылок «стр. ленты / коммит / стр. `report.txt`» —
   вывод нельзя проверить.
