## Наблюдения (сервисная сессия)

- **Shell-шейр:** 130 вызовов на 6 пакетов (≈22/пакет при минимуме ~7 нужных).
- **Избыточные проверки:** `git ls-files --eol`, байтовые чтения файла (3 отказа
  прав + повторные попытки — сессия TRACEABILITY), `git diff --check`,
  `git show --stat`, пост-push `status -sb`/`log` — после push хеши уже есть в
  выводе `push`.
- **Дорогие чтения:** лента операции и память читаются целиком (десятки КБ) на
  каждом шаге; лента `service-docs-hygiene` к концу ≈60 КБ.
- **Reasoning-выброс:** сессия TRACEABILITY — 12 528 reasoning-токенов на
  **один файл** (разбор отказов прав и байтовых проверок).
- **Основной расход — `cache.read` 3.52M** (контекст × шаги): сокращение шагов и
  контекста даёт кратный эффект. Для сравнения: самый дорогой пакет — не волна
  из 86 файлов (`…qjTrs`), а коммит одного файла (`…kNeP`).

## Гипотезы сокращения (к проверке `auditor`)

1. Канонический минимум шагов: `status` → `log -3` (идемпотентность) → 2 записи
   (чекпойнт+лента) → `add` точными путями → `diff --cached --name-status` →
   commit → push; убрать eol/byte/`diff --check`/`show --stat`/post-push-проверки.
2. Чтения — только хвосты ленты и памяти (`offset`/`limit`), не целиком.
3. Промпт `lead` — короткая ссылка на пакет в ленте (состав и подтверждение уже
   там), без дублирования списка путей.
4. Опционально: read-only хелпер `.opencode/scripts/git-check.mjs`
   (status+log+staged одним вызовом) с allowlist у роли.
5. Организационное: один git-пакет на волну (как в этой серии) вместо коммита
   после каждого шага — меньше накладных сессий.

**Ориентир:** steps 16–25 → 7–9 (−60%), shell 15–34 → 6–7 (−70%),
`cache.read` −65–75%, суммарные токены/стоимость −70–80%; с хелпером и
пакетной организацией — до −85–90%.

### Целевой чек-лист роли `git` (процессный пакет «коммит + push»)

Цель: **≤ 8 шагов, ≤ 7 shell, 2 edit, 0–1 read** (сейчас 16–25 шагов, 15–34 shell).

1. `git status -sb` — состав + синхрон (один вызов даёт и файлы, и `ahead/behind`)
   — 1 shell.
2. `git log -1 --oneline` — база/идемпотентность — 1 shell. `--grep` — один,
   только с `=` и значением в кавычках.
3. Записи до `add` (F43): append отчёта в ленту + чекпойнт памяти — 2 edit (1 шаг).
4. `git add` точными путями пакета — 1 shell.
5. `git diff --cached --name-status` — сверка staged = N — 1 shell.
6. `git commit -m "…"` — вывод даёт число файлов — 1 shell.
7. `git push origin develop` (таймаут ≥ 5 мин) — вывод даёт диапазон хешей — 1 shell.
8. Ответ `lead` текстом; **post-push git-команд нет** (F43).

Запрещено в пакете: `git ls-files --eol`, байтовые чтения, `git diff --check`,
`git show --stat`, `git diff --stat` (дубль `--numstat`), серии `--grep`,
post-push `status`/`log`/`rev-parse`. Для пакетов задач добавляются операции
ветки (`switch`/`pull`/`merge --no-ff`/`branch -d`) — та же дисциплина,
изменяющие — под `ask`.

### Оценка сокращения

Расчёт по данным ленты: `cache.read` ∝ шаги × контекст; средний контекст на шаг
≈ 3.52M / 117 ≈ **30 К`. Средние на пакет: 19.5 шага, 21.7 shell.

- Устранение избыточных проверок/чтений: shell 21.7 → 6 (−72%), шаги 19.5 → 8
  (−59%): 6 пакетов × 8 × 30 К ≈ 1.44M → **−60%**.
- + хвостовые чтения и короткие промпты (контекст 30 К → ~18 К): ≈ 0.86M →
  **−75%**.
- + хелпер и урезанная память (→ ~15 К, 45 шагов): ≈ 0.68M → **−80%**.

**Реалистичный диапазон:** −60–70% (только устранение избыточности, без правок
канона) … **−75–85%** (полный набор: чек-лист + хвосты + короткий промпт +
хелпер). **−90% — оптимистично:** упирается в фиксированный контекст шага
(`git.md`+правило+лента/память), который шагами не сжать.

### Риски / побочные эффекты

1. Снятие post-push проверок → нет независимого подтверждения синхрона;
   митигация: `push` печатает `a..b branch -> branch`, хеши — в `progress.yaml`
   (`lead`), F43 критерий проверяют `validator`/`auditor`, а не сам `git`.
2. Короткий промпт → риск расхождения с лентой; митигация: лента остаётся
   каноническим источником состава и подтверждения, промпт ссылается на §.
3. Хелпер → новая поверхность; требование: read-only, изменяющие команды — под
   `ask`, паритет `review.md`; без research-обоснования allowlist не расширять
   (`dispatch-loop.md` §«Команды и права»).
4. Урезание памяти → потеря resume-контекста; митигация: «Знание» + последние
   3–5 чекпойнтов, хроника — в `state/`/ленте (уже канон); правит сервисная сессия (F35).
5. Пакетная организация → крупные коммиты хуже для `bisect`; для
   `chore(process)` приемлемо, продуктовые `code(T-XX)` — по одному.
6. `status -sb` вместо `status --porcelain`: short-формат (2 символа) короче и
   даёт синхрон; для машинного счёта путей достаточно.
