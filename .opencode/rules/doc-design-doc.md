# Правила: Design Doc

**Когда читать:** оформление или правка design-документа (проектного
описания системы/подсистемы).

## Расположение

- Проектные описания — в `docs/**` или `.gitverse/docs/**` (архитектура).
- Состояние design-документа для MCP-сервера живёт в `.myagent/**` с
  секциями `.myagent/doc/sections/*.md` — схема и жизненный цикл в
  `README.md` §Пояснения и `AGENTS.md` §Жизненный цикл секции.
- Общее — `doc-common.md`.

## Структура

```md
# <Название системы/подсистемы>

- Статус: <черновик | принято>
- Дата: <ГГГГ-ММ-ДД>
- Связано: <ссылки>

## Контекст

## Цели и нецели

## Архитектура

## Модули

## Альтернативы

## Риски и ограничения

## Открытые вопросы

## План работ
```

## Соглашения для `.myagent/**`

Чтобы `doc.check_completeness` и `doc.check_consistency` работали
детерминированно (`README.md` §Соглашения для агентов):

- в тексте секции повторяй формулировки `must_answer` или ставь маркер
  `answer: <вопрос>`;
- модули помечай явно: `module: executor`, `modules: scheduler, executor`,
  `<!-- module: vm-core -->`;
- секция модулей должна иметь `id` или `title` со словом `module`.

## Правила содержания

- Каждое решение обосновано; альтернативы перечислены с причиной отказа.
- Открытые вопросы вынесены явно, а не спрятаны в тексте.
- Диаграммы — по `doc-common.md`; не дублировать сведения из ADR, а
  ссылаться на них.

## Чек-лист

- [ ] Цели и нецели заданы.
- [ ] Модули и границы описаны.
- [ ] У решений есть альтернативы и обоснование.
- [ ] Открытые вопросы перечислены.
- [ ] Для `.myagent/**` соблюдены маркеры `answer:`/`module:`.
