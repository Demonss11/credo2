# Правило: git-workflow (credo2)

**Когда читать:** перед любой работой с git — ветки, коммиты, слияния.
Основа — git-flow рабочего пространства DAR; ниже — адаптация для `credo2`.

## Роли

- `@git` — единственная роль, выполняющая git-команды: read-only — свободно,
  изменяющие и сетевые — по подтверждённому пакету (`ask`).
- Пользователь — владелец истории: подтверждает пакет один раз (через `lead`).
- Остальные роли git не трогают: они готовят файлы, коммит делает `@git`.

## Модель ветвления (git-flow)

| Ветка | Назначение | Откуда | Куда |
|---|---|---|---|
| `master` | стабильный релиз | `release/*`, `hotfix/*` | — |
| `develop` | интеграция | `feature/*` | `release/*` |
| `feature/<идент>` | задача (`T-XX-<слаг>`), доработка журнала (`Dn-<слаг>`, `Qn-<слаг>`) | `develop` | `develop` |
| `release/*` | подготовка релиза | `develop` | `master` + `develop` |
| `hotfix/<идент>` | срочный фикс | `master` | `master` + `develop` |

- Имя ветки **обязательно содержит идентификатор** дорабатываемого артефакта:
  задача — `feature/T-03-check-create`, решение — `feature/D38-agent-cycle`,
  вопрос — `feature/Q43-agent-cycle`, хотфикс — `hotfix/T-21-<слаг>`.
- Прямые коммиты в `master` и `develop` запрещены (кроме служебной очистки
  логов — см. «Подтверждение и очистка логов»): работа — в `feature/<идент>`,
  интеграция — слиянием с сохранением истории (`--no-ff`).
- После слияния ветка удаляется (локально и на `origin`).
- Слияние в `master` сопровождается аннотированным тегом `vX.Y.Z` и записью
  в `docs/CHANGELOG.md` (CHANGELOG ведёт `docs-writer`).
- `origin` — GitHub; ветка публикуется `git push -u origin <ветка>`.

## Формат коммитов

| Префикс | Когда | Пример |
|---|---|---|
| `docs(Qn): …` | перенос вопроса в журнал | `docs(Q2): перенос в журнал` |
| `docs(Dn): …` | решение, структура документации | `docs(D15): ссылки и трассировка` |
| `code(T-XX): …` | задача кода | `code(T-10): workspace dar-core + credo-server` |
| `chore: …` | конфиг, агенты, служебное | `chore: рабочая группа агентов` |
| `chore(process): …` | процессные записи прогона (ленты, память, state) | `chore(process): run5 — записи прогона` |

- Одна запись журнала — один коммит (`.opencode/rules/journal.md` §5.7); одна задача — один коммит.
- Описание — по-русски, кратко, без «WIP».

## Старт задачи

1. Лента задачи открывается при планировании (`analyst`), 🚧 ставит
   `docs-writer` по действию плана.
2. `lead` получает подтверждение на ветку (действие `surface_to_user` плана)
   и вызывает `git`:
   `git switch develop` → `git pull origin develop` →
   `git switch -c feature/T-XX-<слаг> develop` →
   `git push -u origin feature/T-XX-<слаг>`.
3. **Только после этого** задача уходит исполнителям: все работы и коммиты
   задачи идут в её ветке.

## Пакет и подтверждение

1. Пакет (точные пути, сообщения, шаги ветки) формируется при планировании
   (`analyst`) и лежит в плане; перед показом сверяется со снимком
   `git status --porcelain` (расхождение — re-plan; `lead` пакет не
   расширяет). `lead` показывает пакет пользователю и получает **одно**
   подтверждение (`question`), затем фиксирует подтверждённый пакет в ленте
   задачи. Владелец может отменить/сузить пакет: выполненная часть
   фиксируется, остаток — в план, возобновление — новым подтверждением
   (`.opencode/rules/dispatch-loop.md`). **Промпт `lead` (шаблон, 5–8 строк):**
   операция; ссылка на запись пакета в ленте (состав не дублировать — Q41);
   база `HEAD`; режим («коммит + push»); сообщение коммита.
2. `git` сверяет подтверждение по ленте (пользователя сам не спрашивает) и
   выполняет шаги идемпотентно; команды `add`/`commit`/`switch`/`merge`/`push`
   — под `ask`.
3. «Подтверждено» без записи в ленте не бывает: нет подтверждения — роль
   возвращает пакет `lead` и изменяющие команды не выполняет.
4. **Записи пакета — до коммита** (F43): отчёт роли `git` в ленту и чекпойнт
   памяти формируются **до** `git add` и входят в пакет; после `push` роль не
   пишет в отслеживаемые файлы — итог с хешами возвращается ответом `lead`
   (хеши — в `progress.yaml`; в ленте/памяти их может не быть — восстановимы
   из `git log`). Критерий приёмки пакета: новых правок **от роли `git`** после
   `push` нет (`git status` их не показывает). «Грязь» других ролей и остатки,
   возникшие вне пакета, отдельным «догоняющим» коммитом **не коммитятся** —
   подхватываются следующим плановым пакетом.

## Минимальный цикл `git`

Для процессного пакета (коммит + push): `status -sb` → `log -1 --oneline` →
записи до `add` (F43) → `add` точными путями → `diff --cached --name-status` →
`commit` → `push`; ответ — текстом, post-push git-команд нет. Сверку состояния
можно выполнить одним вызовом:
`node .opencode/scripts/git-check.mjs [--staged] [--expect=N]` (read-only).

**Избыточное (не выполнять):** `ls-files --eol` и байтовые чтения newline,
`diff --check`, `show --stat`/`diff --stat`, серии `--grep`, пост-push
`status`/`log`. Ленту и память читать хвостами (`offset`/`limit`).

## Завершение задачи

По подтверждённому пакету (после приёмки и закрытия статусов):

1. `git switch develop` → `git pull origin develop`;
2. `git merge --no-ff feature/T-XX-<слаг> -m "Слияние feature/T-XX-<слаг> в develop"`;
3. `git push origin develop`;
4. `git push origin --delete feature/T-XX-<слаг>` → `git branch -d
   feature/T-XX-<слаг>`. `branch -d` может отказать из-за устаревшего upstream
   (коммит задачи в ветку не пушился) — тогда сначала удалить remote (порядок
   выше — рабочий, T-12/T-13/T-04).

Хеши closeout фиксируются в ответе `git` и `progress.yaml` (в ленте/памяти их
может не быть: записи пакета делаются до коммита и входят в него — F43).

`release/*` и `hotfix/*` — как в эталонном процессе (тег `vX.Y.Z`, слияние в
`master` и `develop`). Ветки публикаций CREDO (`.credo/published-repo`,
`publish/{name}-{version}`) роль `git` не мержит — это делает человек.

## Синхронизация

```sh
git fetch --prune

git switch develop

git pull origin develop
```

## Идемпотентность и таймауты

- Проверка состояния — минимальной: `git status -sb` и `git log -1 --oneline`
  (или одним вызовом `node .opencode/scripts/git-check.mjs`); уже
  сделанное пропусти, продолжай с первого невыполненного. Серии
  `git log --all --grep` не использовать (при необходимости — одна проверка,
  шаблон в кавычках).
- `git push` — с таймаутом не менее 5 минут; обрыв — повторить статус и
  продолжить, не переписывая историю.

## Ограничения

- `git add` — точными путями, не «`git add -A` по привычке».
- Запрещены `--force`, `push --force`, `reset --hard`, `rebase` и любое
  переписывание опубликованной истории; конфликты слияния разрешаются
  отдельным шагом, с объяснением решения.
- Одна команда за вызов; составные команды, пайпы и перенаправления запрещены
  (движок отклоняет их целиком). `git -C <путь>` не использовать — паттерны
  матчатся от начала команды; рабочая директория — `workdir`.
- Коммит — после успешной приёмки (`validator`), не раньше.
- `target/`, `.credo/`, `node_modules/` не коммитятся.
- **Продуктовый коммит задачи — без процессных файлов.** `code(T-XX): …`
  включает код (`src/**`, `tests/**`) и документы задачи (`docs/**`); память,
  почта и состояние (`.opencode/memory/**`, `.opencode/mail/**`,
  `.opencode/state/**`) — отдельным процессным коммитом (`chore(process): …`)
  по решению `lead` в составе пакета прогона. Смешение составов в одном коммите
  — отклонение (F22).
- **`state/**`** — в процессном коммите (по закрытию задачи или перед стартом
  следующей); после внедрения session-commit (T-15 фаза C) правило уточняется
  (F30).

## Подтверждение и очистка логов

- Подтверждение пакета — запись `lead` в актуальной ленте **до** вызова `git`.
- Если пакет удаляет саму ленту (очистка логов), подтверждение фиксируется до
  удаления, а `git` сверяет его из истории: `git show HEAD:<лента>` — проверка
  выполняется после коммита подтверждения и до коммита очистки.
- Очистку в пакете выполняет `git`: `node .opencode/scripts/clean-logs.mjs`
  (по умолчанию с бэкапом в `<temp>/opencode/logs-backup-<ts>/`); содержимое
  удалённых лент остаётся в истории git.
- Сервисные операции без задачи ведутся в ленте `.opencode/mail/service-<тема>.md`.
- Служебная очистка логов коммитится **служебным коммитом прямо в `develop`** —
  исключение из «Прямые коммиты в `master` и `develop` запрещены» (см. «Модель
  ветвления»); удаление ленты оформляется двухшаговым пакетом — см. пункт о
  сверке подтверждения из истории выше.
